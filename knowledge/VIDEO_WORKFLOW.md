# 영상 제작 표준 워크플로우

마지막 갱신: 2026-09-04

이 문서는 롱폼, 시즌 Track A·B, 채널 쇼츠 C를 제작할 때 공통으로 따르는 단계와 완료 조건이다. 각 영상 프로젝트는 루트에 `STATUS.md`를 두고 이 문서의 10단계 상태를 기록한다. 채팅 기억이나 작업자의 추측보다 `STATUS.md`의 현재 단계와 다음 행동을 우선한다.

## 상태 값

| 상태 | 의미 |
|---|---|
| `not_started` | 아직 시작하지 않음 |
| `in_progress` | 현재 작업 중 |
| `review` | 자동 작업은 끝났고 사용자 확인 대기 |
| `approved` | 사용자가 방향·내용을 승인함 |
| `complete` | 해당 단계의 산출물과 검증이 모두 완료됨 |
| `blocked` | 외부 입력이나 사용자 결정 없이는 진행할 수 없음 |
| `skipped` | 이 영상에는 불필요하며 이유가 기록됨 |

한 단계가 끝났다고 다음 단계가 자동 승인되는 것은 아니다. 일정, 공개, 최종 렌더처럼 중요한 판단은 사용자 확인 후 상태를 변경한다.

## 전체 흐름

```text
1. 제작 우선순위
→ 2. 기획·콘셉트
→ 3. 대본·구성안·스토리보드
→ 4. 음성·타이밍
→ 5. 디자인·모션 명세
→ 6. 미디어 준비
→ 7. HyperFrames 제작
→ 8. 동기화·사운드
→ 9. 검수·렌더링
→ 10. 업로드·성과 분석
→ 다음 영상의 1단계
```

## 1. 제작 우선순위 결정

### 순서 (2026-08-26 확정)

1. **아이디어 추천** — 경쟁 채널 동향(`node scripts/market-demand.mjs`, `data/youtube/market-demand.json`)과
   채널 자체 성과 데이터(`npm run content-opportunity`, `data/youtube/`)를 근거로 소재 후보를 뽑는다.
   감으로 정하지 않는다. 두 점수는 축이 달라 곱하지 않는다 — market-demand는 일반 검색 키워드 기준,
   content-opportunity의 byRule/byRole은 우리가 이미 만든 포맷 기준이라, 후보 소재를 관련 키워드와
   사람이 직접 매칭해서 판단한다([결정 기록](decisions/2026-08-29-market-demand-score.md)).
2. **5개를 표로 제시** — 소재/각도별로 5개, 사용자가 하나를 고른다.
3. 고른 소재로 아래 "확정할 것"을 채운다.

### 확정할 것

- 콘텐츠 유형: 롱폼 / Track A / Track B / 채널 쇼츠 C.
- 지금 제작해야 하는 이유와 채널에서의 역할.
- 연결할 롱폼 또는 이전·다음 영상.
- 기존 제작물·예약 일정·공개 공백을 고려한 우선순위.

### 산출물

- `knowledge/now.md`의 현재 우선순위.
- 프로젝트 `STATUS.md`의 `content`, `objective`, `current_stage`, `next_action`.

### 완료 조건

- 다른 미완성 영상보다 먼저 해야 하는 이유를 한 문장으로 설명할 수 있다.
- 소재 선택이 리서치/성과 데이터 또는 그걸 근거로 한 5개 후보 중 사용자 선택에서 나왔다.
- **`data/youtube/idea-board-history.json`에 이 소재가 `status: "selected"`로 기록돼 있다**
  (2026-09-07 확정). 대시보드 기획 보드의 "이 주제로 진행 →" 버튼을 눌렀으면 자동으로 기록되니
  확인만 하면 되고, 대시보드를 거치지 않고 다른 경로로 소재를 정했다면 직접 기록한다 — 렌더까지
  끝난 뒤에야 기록하면, 그 사이 후보를 다시 생성했을 때 같은 소재가 또 추천될 수 있다(EP13이
  실제로 며칠간 미등록 상태였던 사례 있음).

## 2. 기획·콘셉트 확정

### 확정할 것

- 기획 의도와 한 편을 본 뒤 얻어야 할 한 가지 이해.
- 핵심 시청자와 영상의 역할: 도달, 구독, 롱폼 이동, 시청 시간 중 우선 목표.
- 콘셉트·톤앤매너·색감·스타일·리듬.
- 레퍼런스와 각 자료에서 참고할 것·사용하지 않을 것.
- 성공 판단 지표.
- 제작 시작일, 초안 검토일, 렌더 목표일, 업로드 예정일.
- 외부 TTS·이미지·음악·유료 소스 비용과 승인 필요 여부.
- **제목·썸네일(문구+이미지)을 대본보다 먼저 확정한다.** `knowledge/thumbnail-strategy.md` 체크리스트
  (효과/숫자/타깃/명확성/길이/궁금증/역할분리, addiction-loop, 3-step viewer psychology)로 6열 표
  (제목/썸네일 문구/프롬프트 한글·영문/하이퍼프레임 스토리보드/내 생각) 5안을 제시하고 사용자가 고른다.
  이미지는 사용자가 직접 생성해서 고른다(Claude가 API로 대신 생성하지 않음).
- **썸네일 이미지 파일을 저장할 위치도 이 단계에서 함께 정한다.** 썸네일이 확정된 순간 아이디어
  단계는 끝난 것이므로, 저장 위치를 나중 단계에서 물어보지 않는다. 업로드 패키지ID(`s{시즌}-ep{NN}-{종류}`)가
  아직 없으면(콘텐츠 JSON·업로드 패키지 미생성 단계) `videos/<프로젝트>/thumbnail.png`에 즉시 저장하고,
  10단계에서 `build-upload-package.mjs` 실행 시 `output/upload-packages/<패키지ID>/thumbnail.png`로 옮긴다.

### 산출물

- HyperFrames 프로젝트의 `BRIEF.md`.
- 레퍼런스는 원본 경로와 적용 판단을 `BRIEF.md` 또는 에피소드 문서에 기록.
- 확정된 제목·썸네일 문구·이미지(다음 단계인 대본이 이 훅에 맞춰 쓰인다).
- 저장된 썸네일 이미지 파일(`videos/<프로젝트>/thumbnail.png`, 위치는 `BRIEF.md`에 기록).

### 완료 조건

- 목적, 대상, 결과물, 레퍼런스, 일정, 비용, 금지 사항에 미확정 값이 없다.
- 미확정 값은 추측하지 않고 `미확정`으로 표시한다.
- 제목·썸네일이 확정됐다 — 대본 단계로 넘어가기 전에 완료돼야 한다.
- 썸네일 이미지 파일이 실제로 저장돼 있다 — "나중에 저장 위치를 정한다"로 미루지 않는다.

## 3. 대본·구성안·스토리보드

### 확정할 것

- **목차·대본에 쓰는 구체적 예문·발음 현상은 웹 검색으로 사실관계를 확인한 뒤 쓴다**
  (2026-09-07 확정). 채널 자체 데이터(`audience-dna.json`의 painPoint/question, 경쟁사 대본
  분석)에서 이미 근거를 찾았더라도, 그 경쟁 채널의 설명 자체가 언어학적으로 정확한지는 별개
  문제다 — 웹 검색(사전·발음 교육 자료 등)으로 한 번 더 대조해서, 제목·썸네일 문구가 건 약속을
  틀린 내용으로 채우지 않는다. EP14에서 실제로 이렇게 검증한 사례: 시청자DNA에 있던 "made it"→
  "메이릿"(Flap T) 예시를 언어학 자료로 검색해 "T/D가 모음 사이·뒷모음이 약세일 때 탄설음이
  된다"는 정식 규칙임을 확인 후 채택.
- **대본에 넣는 구체적 예시 상황은 `BRIEF.md`의 `audience`가 실제로 겪는 상황인지 확인한다**
  (2026-09-07 확정). EP14(리스닝 정체기 학습자 대상)에서 Frame 11에 "원어민과 직접 대화하다가"를
  넣었다가 사용자가 "일반 초보가 원어민과 대화할 일이 몇 번이나 있겠냐, 대부분 영화·유튜브 듣고
  공부하는 거 아니냐"고 지적해 삭제한 사례가 있다 — 리스닝 중심 채널인데 스피킹/실전 회화
  시나리오를 예시로 쓰면 시청자가 "내 얘기가 아니다"라고 느껴 몰입이 깨진다. 리스닝 중심
  타겟에는 영화·유튜브·팟캐스트 시청 같은 **입력(듣기) 시나리오**를 쓰고, "원어민과 직접 대화"
  같은 **출력(말하기) 시나리오**는 스피킹이 그 영상의 명시적 소재가 아닌 이상 쓰지 않는다.
- 내레이션, 화면 문구, 자막, 강조 철자·한글 음절, CTA.
- 도입→전개→결론 또는 질문→생각→정답→원리→복습→CTA 구조.
- 각 장면의 목적, 초점, 발화, 동작, 전환.
- **나레이션 구조에 중독 루프(Stakes → Big Question → Head Fake)를 적용한다.** 도입에서
  이해관계(Stakes)를 만들고, 구체적인 질문(Big Question — 막연한 티저 금지)을 던지고, 예상을 깨되
  납득되는 반전(Head Fake)으로 답한다.
  **Frame 1(훅/Stakes)에는 공감뿐 아니라 호기심·시청자 이득도 항상 챙긴다**(2026-09-10 확정,
  EP15 제작 중 사용자 지적 — 초안엔 시청자가 겪는 상황 공감만 있고 "그래서 뭘 얻는지"가 빠져
  있었음). 세 요소를 이렇게 나눠서 챙긴다: (1) **공감** — 시청자가 실제로 겪는 구체적 상황
  (막연한 감정이 아니라 "대충 읽었는데 맞는지 확신이 안 서는" 식의 구체적 순간). (2) **호기심**
  — 명시적 "왜?" 질문까지는 필요 없다("왜?"는 보통 바로 다음 장면인 Big Question이 전담하므로
  Frame 1에서 반복하면 중복됨). "숨어 있는 규칙/원리"처럼 뭔가 있다는 걸 암시하는 표현 정도로
  충분하다. (3) **시청자 이득** — "이 영상을 보면 무엇을 할 수 있게 되는지"를 반드시 한 문장
  넣는다. "확실한 규칙을 알려드릴게요"처럼 무엇을 가르쳐줄지만 말하고 끝내지 말고, "그럼 ~하실
  수 있게 되실 거예요"처럼 결과·이득까지 명시한다. 단, **페이오프(보통 후반부 프레임)에서 쓸
  구체적 숫자나 핵심 반전까지 여기서 다 풀지는 않는다** — Stakes 단계에서 결론을 다 주면 뒤쪽
  카타르시스가 약해진다(예: 제목이 "단어 100개"를 약속했어도 Frame 1은 "긴 단어도 자신 있게
  읽게 된다" 정도로만 이득을 말하고, "100개"라는 구체적 숫자는 페이오프 프레임까지 아껴둔다).
  **Rehook(다음 편으로 이어지는 구체적 여운) 규칙은 2026-09-03/04에 정정됨** — 진짜로 정해진 다음
  편(실제 "시즌"으로 묶인 시리즈)이 있을 때만 구체적 Rehook을 쓰고, **아이디어 보드로 고른 "단편"
  에는 특정 다음 소재를 절대 예고하지 않는다**([단편/시즌 분류 정리 결정](decisions/2026-09-03-standalone-vs-season-episodes.md)).
  예전엔 반대로 "결말을 완전히 닫지 않아야 한다"고 적혀 있었는데, 그 예시로 든 "시즌2 WANT TO
  테스트"가 실제로는 EP11(GONNA)이었고 예고했던 WANT TO는 EP12로 이어지지 않았다(전혀 다른 소재로
  감) — 특정 소재를 미리 못 박아두는 게 오히려 위험하다는 게 실증됨(EP11 Frame 13, EP12 Frame 10
  둘 다 "다음에도 자주 헷갈리는 발음 또 풀어드릴게요"류의 소재 안 못 박는 마무리로 정정, 2026-09-04).
- **대본은 2단계에서 이미 확정된 제목·썸네일 훅에 맞춰 쓴다** — 순서가 중요하다: 썸네일이 먼저,
  대본은 그다음(2026-08-26 확정, 이전엔 "대본 단계에서 같이 정한다"고 잘못 적었었음). Head Fake의
  반전과 Rehook은 **제목·썸네일 캡션이 건 약속을 실제로 지키는 내용**이어야 일관성이 생긴다
  (2026-09-07 문구 정정 — "같은 표현을 그대로 재사용"이라고 적혀 있어서 문장을 복사-붙여넣기
  하라는 뜻으로 오독된 사례가 있었음. 진짜 요구사항은 **문구 재사용이 아니라 약속 이행**이다 —
  예: 제목이 "왜 이렇게 될까"라고 물었으면 Head Fake가 그 이유를 실제로 답해야 하고, 썸네일
  카피가 특정 결과를 약속했으면 본문 어딘가(주로 페이오프·마무리)가 그 결과를 실제로 만들어내야
  한다. 표현이 자연스럽게 겹치면 좋지만 억지로 같은 문장을 끼워 넣을 필요는 없다).
- **길이는 "썸네일·제목이 약속한 걸 충분히 풀어주는 데 필요한 만큼"이지, 다른 편 길이를 참고하는 게
  아니다.** 시즌1 다른 편 분량에 맞추려고 관련 없는 소재를 끼워 넣지 않는다 — 특히 **다음 편 Rehook의
  소재를 이번 편에서 먼저 설명해버리면 안 된다**(실제로 WANT TO·GOTTA를 같은 영상에 넣으려다 걸러낸
  사례 있음, 2026-08-26). 분량을 늘려야 하면 같은 주제를 더 깊게 판다 — 예외 상황, 예측형 미니 퀴즈,
  격식·캐주얼 구분, 리스닝 트레이닝(실제 속도 문장에서 직접 찾기), 소리 내어 따라 하기 같은 항목을
  후보로 제시하고 사용자가 고른다.
- **종결어미를 다양하게 섞는다.** 존댓말 안에서도 문장마다 "~요"로만 끝나면 TTS로 들었을 때 단조롭다
  — "~습니다/입니다", "~죠", "~네요", "~요"를 섞어 리듬을 만든다.

### 작성 순서 — 목차 → 장면별 대본 → 스토리보드 (2026-09-04 확정)

대본을 한 번에 통째로 써서 보여주지 않는다. 아래 순서를 매 장면 사용자 승인 없이 건너뛰지 않는다:

1. **목차(장면 개요)를 먼저 작성해 검수받는다.** 전체 장면 목록을 각 장면 제목·한 줄 요약·핵심
   메시지·(있다면) Stakes/Big Question/Head Fake/예외/퀴즈 같은 역할만 표로 제시한다 — 실제
   나레이션 문장은 아직 안 쓴다. 사용자가 장면 구성·순서·개수를 확인·수정한다.
2. **목차가 승인되면, 장면 하나씩 순서대로 실제 나레이션을 작성한다.** 한 장면분 대본을 쓰고
   제시 → 사용자 검수(수정 요청 반영 또는 승인) → 다음 장면. 여러 장면을 한꺼번에 미리 써서
   보여주지 않는다 — 앞 장면에서 나온 피드백(톤, 종결어미, 정보량 등)이 뒷장면에 바로 반영되게
   하기 위함이다.
3. **모든 장면 대본이 완성되고 전체 검수를 통과하면 스토리보드 작성으로 넘어간다.** 이때부터
   `STORYBOARD.md`(장면별 모션·전환)와 함께 **이미지/비주얼 요소도 포함해서** 작성한다 — 대본
   확정 전에 미리 스토리보드나 이미지를 만들지 않는다(순서를 앞당기면 대본이 바뀔 때 재작업이
   생긴다).

**대안 — 전체 대본 한 번에 작성 + 파일 코멘트 검수 (2026-09-07, EP14에서 처음 채택)**: 위
2번(장면 하나씩 승인)이 기본값이지만, 사용자가 요청하면 목차 승인 후 **12씬 전체 나레이션을
한 번에 써서 `SCRIPT.md`에 저장**하고, 사용자가 그 파일에 직접 코멘트를 달면 그걸 보고 수정하는
방식으로 대체할 수 있다. 이 방식을 쓸 때 지킬 것:

- **코멘트 위치·형식**: 각 `## Line N` 섹션 맨 아래(다음 씬으로 넘어가기 전)에
  `**코멘트:** ...` 라벨로 남긴다. 파일 전체에서 "**코멘트:**"만 검색하면 어디에 뭐가
  달렸는지 바로 찾을 수 있다.
- **반영 후에도 코멘트를 지우지 않는다.** 처음엔 반영 끝나면 지웠다가 "무슨 요청으로 왜
  이렇게 바뀌었는지 기록이 사라진다"는 지적을 받았다 — 코멘트 줄 끝에
  `→ ✅ 반영됨(날짜) — 무엇을 어떻게 바꿨는지 한 줄`을 이어 붙이고 원문은 그대로 둔다. 아직
  반영 안 한 코멘트는 "✅ 반영됨"이 없는 상태로 남아서, 파일을 훑으면 뭐가 남았는지 바로 보인다.

### 산출물

- 장면 목차(중간 산출물, 파일로 꼭 남기지 않아도 되지만 사용자 승인 기록은 남긴다).
- `SCRIPT.md`: 시간, 내레이션, 화면 동작이 연결된 확정 원고 — 위 순서대로 장면별 승인을 거쳐 완성.
  Head Fake/Rehook 대사가 2단계에서 정한 썸네일 문구·제목과 동일한 표현을 쓴다.
- `STORYBOARD.md`: 두 장면 이상이면 필수. 한 프레임 실험도 비트가 여러 개면 작성한다. 대본 전체
  승인 후에 작성하며, 이미지/비주얼 요소를 포함한다.
- `BRIEF.md`의 `storyboard`와 실제 파일 상태를 일치시킨다.

### 완료 조건

- 목차가 먼저 승인됐고, 장면별 대본이 한 번에 다 나오지 않고 순서대로 각각 승인을 거쳤다.
- 화면 문구와 발화 문구가 구분되어 있다.
- 퀴즈 질문 발화에는 목표 영어 단어의 정답 발음이 없고, 정답은 생각 시간 뒤의 별도 발화로만 공개된다.
  **"단어를 소리 내어 말하는 것 자체가 정답인 퀴즈"는 질문 구간에서 그 영어 단어를 아예 발화하지
  않는다**(2026-09-10 확정, EP15 Frame 8·11 사고 — TTS 생성 후 사용자가 "나레이션이 답을 알려주고
  있음"이라고 지적해서 발견). EP12~14류 퀴즈(TURN ON→터논처럼 단어 두 개를 "어떻게 연결하는지"를
  묻는 퀴즈)는 단어 자체를 말해도 안전하다 — 연결 방식은 별개의 정보라 단어 발음에 안 들어있다.
  하지만 **정답이 "이 단어 자체가 어떻게 발음되는가"인 퀴즈(예: EP15의 -sion 전/션 구분)는 얘기가
  다르다** — CONFUSION을 영어로 정확히 발음하는 순간 그 자체가 "전"이라는 정답이므로, 질문에서
  "CONFUSION은 어떻게 읽을까요?"처럼 그 단어를 소리 내어 언급하면 TTS가 실제 영어 발음으로
  읽어버려 정답이 미리 새어나간다. 판별법: **"이 단어를 소리 내어 말하면 그 자체로 정답이 드러나는가?"**
  를 자문해서, 그렇다면 질문·생각 시간 구간에서는 "이 단어", "하나 더 볼까요"처럼 화면에 이미
  보이는 단어를 가리키는 대명사로만 지칭한다. 대본을 다른 편의 퀴즈 구조에서 그대로 본떠 쓸
  때도 이 판별법을 매번 다시 적용할 것 — "저번 편에서 이 구조가 안전했다"가 이번 편에도 안전
  하다는 보증이 아니다.
  **정답 공개 순간에도, 화면에 이미 그 단어 철자가 보이는 상태라면 영어 단어를 다시 발화하지
  않고 한글 발음만 공개한다**(2026-09-10 추가 확정 — 위 판별법의 1차 수정판은 "정답 공개
  순간에만 영어 발음과 한글 정답을 같은 문장에 묶어 공개"하라고 적었었는데, 실제로 EP15
  Frame 8·11에 적용해보니 "CONFUSION은 '컨퓨전'입니다"처럼 화면에 이미 떠 있는 단어를 나레이션이
  또 영어로 말하는 게 중복으로 들려 사용자가 다시 지적함 — "이 단어 보이시죠? '컨퓨전'입니다"
  처럼 화면 철자 + 나레이션 한글 발음만으로 충분하다). 화면에 그 단어가 아직 없는 채로 정답을
  공개하는 경우(예: 화면에도 없던 완전히 새로운 정보를 발화로만 전달할 때)는 이 규칙 대상이
  아니다 — 오직 "화면에 이미 보이는 단어를 나레이션이 또 영어로 말하는" 중복 상황에만 적용.
- 왕초보 기준으로 한 문장에 하나의 정보만 있다.
- **다른 장면에서 이미 다룬 가설·질문을 표현만 바꿔 반복하고 있지 않은지 확인한다**(2026-09-07
  확정). EP14 Frame 4 원안이 Frame 3에서 이미 던진 "대충 하는 걸까요?" 가설을 "일부러 어렵게
  말하는 줄 알았다"로 형태만 바꿔 다시 쓴 사례가 있었다 — 장면별로 순서대로 작성하면 앞 장면
  내용을 놓치기 쉬우므로, 전체 승인 전에 화자 가설·질문이 장면 간에 겹치지 않는지 한 번 훑는다.
- 이 영상이 진짜 "시즌"(정해진 다음 편이 있는 시리즈)인지 "단편"(아이디어 보드가 매번 최상의
  개별 소재를 고르는 방식)인지 먼저 확인했다. 시즌이면 나레이션에 구체적 Rehook이 있는지 확인하고,
  단편이면 특정 다음 소재를 예고하지 않는 따뜻한 마무리인지 확인한다(2026-09-04 정정).
- Head Fake·Rehook 대사가 2단계에서 확정한 썸네일 문구·제목과 표현이 맞는다.
- 대본과 스토리보드가 `approved` 상태다.

## 4. 음성 제작·타이밍 분석

### 작업

- 확정 대본으로 TTS 또는 실제 음성을 준비한다.
- 발음, 목소리 일관성, 앞뒤 무음, 속도를 실제로 듣고 확인한다.
- **⚠️ 프레임(컴포지션) 코드를 짜기 전에, whisper.cpp로 각 씬 음성 파일을 먼저 분석해서
  핵심 철자·한글 음절·정답 공개 등 화면에 맞춰야 하는 모든 지점의 실제 발화 시각을 뽑는다
  (2026-09-06 확정)**. EP13 제작 중 실제로 겪은 문제: 프레임을 먼저 **추정** 나레이션
  길이로 만들고 나중에 실제 음성이 나오면 통째로 비율(RATIO)을 곱해 늘리는 방식을 썼더니,
  전체 길이는 맞아도 개별 글자 타이밍이 최대 6초 넘게 어긋났다(예: "B는..."이라고 말하기도
  전에 화면에 B가 먼저 떠 있었음) — 학습자가 소리와 화면 중 뭘 먼저 봐야 하는지 헷갈리게
  만드는 실질적 문제였다. **whisper 분석을 나중에 검수 단계에서 하는 게 아니라 프레임을
  만들기 전에 먼저 해서, 애초에 정확한 시각으로 코드를 짠다.**
- 실제 발화 길이를 영상 시간축으로 사용한다.

### whisper 타임스탬프를 SCRIPT.md에 기록하는 형식 (2026-09-06 확정)

각 "Line N — ... (Frame N)" 섹션의 나레이션 문단 바로 아래에 별도 소제목으로 추가한다.
나레이션 문단 자체는 손대지 않고(가독성 유지), 타이밍 데이터만 표 형태로 따로 둔다:

```
**타임스탬프 (whisper 실측, 프레임 자체 음성 기준 초)**:
- B는 = 21.30s
- A는 = 26.05s
- G는 = 31.09s
- "b, a, g 이 됩니다" = 38.60s
```

**시간 기준은 반드시 "그 프레임 자체 음성 파일의 0초부터"다 — 영상 전체 기준 분:초가
아니다.** 각 프레임의 GSAP 컴포지션도 자기 자신의 0초부터 시작하므로, 이렇게 적어두면
프레임 코드를 짤 때 뺄셈 없이 그대로 복사해서 쓸 수 있다. (영상 전체 기준으로 적으면
프레임 코드에 넣기 전에 매번 "그 프레임의 `data-start`를 빼는" 계산이 필요해서 실수가
잘 난다 — EP13 제작 중 실제로 이 계산 실수가 반복됐다.)

### 산출물

- 프로젝트 내부의 최종 음성 파일.
- `SCRIPT.md`의 각 Line 섹션에 위 형식으로 기록된 whisper 실측 타임스탬프.

### 완료 조건

- 잘못 읽힌 TTS가 없고, 화면을 추정 길이에 억지로 맞추지 않는다.
- 질문 TTS만 따로 들어도 정답 발음이 노출되지 않으며, 질문 뒤 생각 시간이 확보돼 있다.
- **화면에 나오는 모든 핵심 철자·단어·정답이 whisper로 실측한 실제 발화 시각을 근거로
  하고 있다 — 추정치나 균일 비율(RATIO) 스케일링에 의존하지 않는다.**

## 7. HyperFrames 제작

### 작업

- 입력과 목적에 맞는 워크플로를 선택한다.
- `BRIEF.md`, `SCRIPT.md`, `STORYBOARD.md`, `frame.md`를 기준으로 구성한다.
- **화면에 특정 단어·철자·정답이 등장해야 하는 프레임은 4단계에서 SCRIPT.md에 기록해 둔
  whisper 실측 타임스탬프를 그대로 GSAP 타이밍에 쓴다 — 추정 나레이션 길이로 먼저 짜고

- **스케치 패스(와이어프레임, 빈 타임라인) 단계에서 `npx hyperframes snapshot --at <시간들>`로

  한 번 먼저 확인한다 — 2026-08-25 결정.

### 완료 조건

- 모든 장면과 음성 트랙이 Studio 타임라인에서 확인된다.
- 디자인·구조 초안이 사용자 검토 가능한 상태다.
- 스케치 패스 콘택트시트를 사용자가 확인했다(레이아웃·비트 순서 승인, 최종 룩앤필은 다음 단계에서 확인).

## 9. 검수·수정·렌더링

### 자동 검수

- `npx hyperframes check` 통과.
- 런타임, 넘침, 충돌, 모션, 대비 오류가 없다.

### 사람 검수

- 소리를 켜고 처음부터 끝까지 한 번 재생한다.
- 무음으로 다시 재생해 자막과 시각적 이해를 확인한다.
- 시작·중간·끝 프레임과 모바일 가독성을 확인한다.
- TTS 발음과 음량 균형을 확인한다.
- 각 퀴즈에서 질문 음성 → 생각 시간 → 정답 음성 순서를 실제 청취로 확인한다.

### 수정 사항 기록 — TASKS.md (2026-09-06 확정)

**사람 검수에서 나온 지적 사항은 그 자리에서 고치고 끝내지 말고, 프로젝트 루트에 `TASKS.md`를
만들어 단계별로 남긴다**(EP13에서 처음 정식으로 적용, `videos/ep13-tongue-shortcut/TASKS.md`
참고). 목적은 두 가지다:

1. **그 영상 안에서**: 지적 사항이 여러 개일 때 한꺼번에 다 고치지 않고, 배경(왜 문제가
   생겼는지) → 단계별 체크리스트 → 각 단계 결과 기록 순서로 정리해서, **한 단계 고치고
   보여주고 검수받은 뒤 다음 단계로** 진행한다.
2. **다음 영상에서**: TASKS.md에 적힌 지적 사항 중 **이 영상만의 문제가 아니라 앞으로도
   반복될 수 있는 일반 교훈**(예: "RATIO 균일 스케일링은 개별 타이밍이 부정확해진다",
   "새 카탈로그 부품은 설치 전에 반드시 실제로 `add`해봐서 검증할 것" 같은 것)은 완료 후
   `CLAUDE.md`/`AGENTS.md`나 이 문서·`production-rules.md`로 끌어올려 영구 규칙화한다(이미
   있는 "여러 PC/세션에 걸쳐 적용돼야 하는 설정은 즉시 기록" 원칙의 구체적인 실행 창구가
   TASKS.md인 셈이다).

**기대 효과와 현실적 한계**: 이렇게 쌓인 규칙이 많아질수록, 다음 영상을 만들 때 사용자가 매번
같은 지적을 반복하지 않아도 되는 부분(동기화 방식, 컴포넌트 선택 기준, BGM/SFX 선정 기준,
리듬 배분 등 **기술적·절차적 반복 문제**)은 확실히 줄어든다. 다만 **그 영상만의 창작적 판단**
(이번 소재에 어떤 비유가 맞는지, 어떤 장면에 어떤 실사 이미지가 어울리는지 등)은 매번 다르므로
검수 자체가 없어지지는 않는다 — TASKS.md 습관이 목표로 하는 건 "검수 0회"가 아니라 "같은
기술적 실수를 매번 처음부터 다시 겪지 않는 것"이다.

### 완료 조건

- 사용자 `render_approved: true` 기록 전에는 최종 렌더하지 않는다.
- 렌더 후 파일 존재, 크기, 길이, 재생 가능 여부를 확인한다.
- **렌더 저장 위치는 `production-rules.md`의 "출력 폴더" 절 관례를 따른다** — `-o`로
  `output/upload-packages/`에 바로 렌더하지 말고, 먼저 프로젝트 자체의 `renders/` 폴더에
  기본 경로로 렌더한 뒤 최종본만 `output/upload-packages/<project>-longform/video.mp4`로
  복사하는 2단계로 할 것(2026-09-10 확정 — EP14에서 이 순서를 건너뛰어 사용자가 지적한 뒤
  정정함).

## 10. 업로드·성과 분석

### 업로드

- 제목, 썸네일, 설명, 태그, 고정 댓글, 관련 영상, 재생목록, 예약 시각을 확정한다.
- **롱폼은 다국어 자막·번역 메타데이터도 확정한다**(2026-09-18 확정, EP17부터 기본 산출물 —
  상세: `production-rules.md` "업로드 패키지 변경 완료 조건" 절). 파일명 규칙만 지키면
  대시보드가 자동으로 읽으므로 코드 작업은 보통 불필요하다.
- 콘텐츠 원본 JSON과 통합 업로드 요약 HTML을 함께 갱신한다.
- 공개 후 고정 댓글, 엔딩 화면, 관련 영상 연결을 확인한다. **엔딩 화면 연결 영상은 항상 직전
  편(previous episode)** — production-rules.md "공개 일정과 엔딩 화면 연결 규칙" 참고, "다음
  편"이 아니다. 이 항목은 렌더 파일의 3초 키프아웃 처리(같은 문서의 하위 절)와는 별개로 유튜브
  Studio에서 사람이 직접 설정해야 하는 항목이라, 업로드 체크리스트를 만들 때 빠뜨리기 쉽다 —
  EP13 체크리스트에 이 항목이 누락됐던 걸 2026-09-08에 발견해 추가한 뒤 이 규칙도 명시적으로
  보강함. 새 에피소드의 `upload-checklist.txt`를 만들 때마다 이 항목을 반드시 넣을 것.
- **`data/youtube/idea-board-history.json`의 해당 소재 항목을 최종 상태로 갱신한다**
  (2026-09-07 확정) — 1단계에서 `status: "selected"`로 자동 기록된 그 항목을 찾아
  `episodeSlug`(`ep{NN}-{슬러그}`)·`episodeLabel`(`단편 EPxx` 등)·`status: "scheduled"`(예약

## 매 작업 시 상태 갱신 규칙

1. 작업 시작 전 프로젝트 `STATUS.md`에서 `current_stage`와 `next_action`을 확인한다.
2. 단계가 바뀌거나 승인·실패·새 결정이 생기는 즉시 `STATUS.md`를 갱신한다.
3. 사용자 승인이 필요한 값은 임의로 `approved` 또는 `complete`로 바꾸지 않는다.
4. 같은 정보는 `STATUS.md`에 짧게, 상세 근거는 `BRIEF.md`·에피소드 문서·월별 로그에 둔다.
5. 작업 완료 전 `npm run wiki:lint`를 실행한다.
