# Phase 1~5: 데이터 분석, 유형 선택 및 소재 발굴 가이드

이 문서는 에피소드 기획의 초기 단계(Phase 1 ~ Phase 5)를 상세히 규정합니다.

---

## PHASE 1 — 라이브 데이터 분석 (캐시 금지)

이번이 몇 번째 기획이든, **이 단계의 숫자는 이번 세션에서 직접 다시 받아온 값만 쓴다.**

0. **다음 기획 입력 파일부터 읽는다 (2026-11-12 사용자 결정: 모은 데이터는 반드시 기획에 쓰인다)**: 아래 1번의 `/api/sync`를 부른 직후 `npm run next-input`으로 `data/youtube/next-episode-input.md`를 새로 만들고 처음부터 끝까지 읽는다. 이 파일은 매일 루프가 만드는 한 장짜리 요약이다. 지금까지의 판정, 같은 형식 영상의 상·하위 비교(7일 조회·노출 클릭률·평균 시청 비율·제목 특징), 우리 채널 검색어, 우리 시청자 댓글, 경쟁 영상 시청자 고민 순위(AI 추측 제외), 최근 리뷰 교훈이 들어 있다. 소재·제목·썸네일·대본 판단은 이 파일에서 출발하고, 쓴 항목은 Phase 5 "기획 근거"의 `다음 기획 입력` 줄에 절 번호와 함께 옮긴다. "작은 표본"이라고 적힌 비교는 가설로만 쓴다. 데이터별 쓰임은 `knowledge/data-consumption-map.md`.
1. **우리 채널 현재 상태(라이브)**: 분석 대시보드 서버(포트 3001)가 떠 있는지 확인하고, 없으면 `npm run analytics`로 띄운다.
   - `POST http://localhost:3001/api/sync` 로 강제 새로고침을 먼저 호출한다(캐시된 스냅샷이 아니라 지금 유튜브 API에서 새로 받아오게 하기 위함).
   - 그 직후 `GET http://localhost:3001/api/dashboard`, `/api/episodes/summary`로 조회수·구독자·트래픽 소스·검색어·영상별 시청 지속률을 받는다.
   - `data/youtube/analytics-latest.json` 등 파일을 열어서 그 안의 숫자를 바로 인용하지 않는다 — 반드시 `/api/sync` 직후 응답값을 근거로 쓴다. 범위(최근 N일/3개월/누적)를 혼동하지 않도록 매번 응답의 `range` 필드를 확인하고 표에 명시한다.
2. **이미 다룬 소재 확인(라이브)**: `GET /api/catalog` 또는 `/api/episodes/summary`의 실제 제목 목록과 `videos/*/BRIEF.md`를 스캔해서 지금까지 다룬 발음 규칙 목록을 새로 뽑는다. 이 목록을 `idea-board-history.json`과 대조해, 공개됐거나 예약됐는데 이력에 없는 편이 있으면 그 자리에서 등록한다(아래 Phase 5 "소재 이력 등록"). 2026-11-11 기준 EP22~29가 빠져 있었다. 대시보드 기획 보드가 없어진 뒤로는 이 스킬만 이 파일을 채운다.
3. **시청자 고민 (누적 데이터 + 웹 검색)**:
   - 먼저 다음 기획 입력 파일 5절(경쟁 영상 시청자 고민·질문 순위)을 본다. 더 찾을 때만 `audience-dna.json`을 읽는다. `updatedAt`이 14일을 넘었으면 08 인사이트 1절을 먼저 돌려 새로 채운다(Gemini 호출이라 비용·한도를 먼저 알린다).
   - 이번에 검토할 발음 규칙·단어와 관련된 항목만 뽑는다. **`sources`가 전부 `competitorScript`인 항목은 시청자 말이 아니라 대본 분석 AI의 추측이므로 시청자 고민 근거로 쓰지 않는다**(2026-11-12 확인: 26개). 근거로 쓸 때는 출처 영상 수와 출처 영상(`sources`)을 같이 적고, 1개 영상에서만 나온 항목은 "가설"로 표시한다. 발음과 상관없는 항목(학습 습관, 다른 채널 이야기)은 뺀다.
   - 그다음 WebSearch를 실행해서 이 파일에 없는 표현, 즉 한국 성인 학습자가 실제로 검색하고 질문하는 말을 확인한다. 웹에서 찾은 것은 "웹"으로 표시한다.
   - 경쟁 채널 분석은 여기서 하지 않고 Phase 3에서 한다.
4. **산출물**: 아래 표로 "지금 채널의 진짜 현실"을 정리한다 — 숫자마다 어느 API 호출/어느 검색에서 나왔는지 출처를 반드시 붙인다.

   | 항목 | 값 | 출처 |
   |---|---|---|
   | 다음 기획 입력 만든 때 | | `data/youtube/next-episode-input.md` 첫 줄 |
   | 같은 형식 상·하위 영상의 차이(가설 재료) | | 다음 기획 입력 2절 |
   | 조회 범위 | (API 응답의 range) | /api/sync 응답 |
   | 롱폼 vs 쇼츠 조회수 비중 | | |
   | 최근 에피소드 시청 지속률 추이 | | |
   | 상위 트래픽 소스 3개 | | |
   | 검색 유입 비중 | | |
   | 이미 다룬 발음 규칙 목록 | | |
   | 소재 이력에 새로 등록한 편 | | `idea-board-history.json` |
   | 이번 소재 관련 시청자 고민 상위 3개 | | `audience-dna.json` (갱신일) / 웹 |
   | 형식 배분 판정 | | `npm run growth-check` |

   **표를 본 뒤 바로 판정한다 (2026-11-06)**: 한 형식이 조회수의 70% 이상인데 최근 14일 공개가 0개면 **다음 제작은 그 형식부터** 한다. 쇼츠라면 새 소재를 기획하기 전에 이미 만든 롱폼에서 장면을 고른다(Phase 12). 이미 만든 영상의 공개 일정은 그대로 둔다. 판정은 `npm run growth-check` 4절에 나오고, 사용자가 다르게 정하면 따른다.

5. **막힌 곳 확인 (Phase 0 연계)**: `npm run growth-check`로 업로드 대기열과 밀린 리뷰를 본다. 이 스크립트는 `status.json`이 아니라 동기화된 `catalog.json`으로 공개 여부를 판단한다. 업로드 대기 3편 이상 또는 밀린 리뷰 3편 이상이면 **새 기획 전에 Phase 0-A를 먼저 하자고 제안한다**(`00-unblock-and-weekly.md`). 7일·28일 리뷰가 밀린 영상이 있으면 묻지 않고 Phase 11을 먼저 하고, 그 판정과 성공 패턴을 Phase 4 근거로 쓴다.

끝나면 표를 보고하고 Phase 2로 계속한다. 사용자가 단계마다 멈추길 원하면 멈춘다.

## PHASE 2 — 콘텐츠 유형 선택

두 가지를 정한다. 이 선택이 **스캔 대상 채널, 아웃라이어 기준, 나중의 성과 비교**를 모두 정한다.

### ① 방식 — 영상이 무엇을 하는지
- **강의**: 규칙을 설명하고 가르친다. 예: "왜 CAT은 캣인데 KING은 킹일까?" (우리 채널 기본)
- **듣기**: 계속 틀어놓고 들으면서 익히는 콘텐츠다(2026-10-04 사용자 정의). 긴 대화·팟캐스트, 또는 같은 문장 패턴을 반복해서 들려주는 집중 연습이 해당한다. **나레이션은 설명이 필요한 프레임과 반복 시작 전 한 줄에만 넣는다**(2026-10-04 사용자 지침). 설명 프레임은 규칙, 예외, 정리다. 단어와 문장을 반복하는 동안에는 나레이션을 넣지 않는다. 초등학생에게 가르치듯 핵심만 말한다. 음성은 학습 대상 음성(원어민 음성)이다. 이 영상이 어떤 학습용인지는 제목·썸네일·화면 카드로 알린다. 듣기형 채널 상위 영상은 전부 26~30분 롱폼이었다.
- **혼합**: 듣기 자료에 규칙 해설을 음성으로 붙인다. 나레이션 규칙을 그대로 적용한다. 검증된 채널이 아직 없어서 **가설로만** 쓴다.

### ② 형식 — 영상 길이와 역할
- **롱폼**: 신뢰 형성, 깊은 학습, 수익화 시청 시간 확보 (`knowledge/channel-strategy.md`).
- **쇼츠**: 신규 시청자 도달, 구독자 획득.
- **세트**: 쇼츠로 들어와서 관련 롱폼으로 연결한다(채널 전략의 "쇼츠 CTA는 롱폼으로 연결" 원칙).

### 기본 추천
- **방식은 강의가 기본이다.** 우리 채널이 강의형이고, 이번 스캔의 토픽 근거는 강의형 채널에서만 나오기 때문이다.
- **형식은 Phase 1의 형식 배분 판정을 먼저 따른다.** 판정이 없으면 소재마다 역할로 고른다. 도달이 목적이면 쇼츠, 깊이가 목적이면 롱폼이다. 우리 쇼츠 상위 5개 중 4개가 테스트형이라서, 도달형 소재는 테스트 쇼츠가 근거가 있다.
- **듣기 방식을 고를 수 있는 조건 (2026-11-06)**: EP24~29 중 먼저 공개한 2편의 7일 리뷰가 끝나기 전에는 새 듣기 영상을 기획하지 않는다. 그 뒤에도 새로 기획한 듣기 영상은 2편 연속까지만 만들고, 다음은 강의형이나 쇼츠로 섞는다. 사용자가 명시적으로 정하면 예외로 한다. 이유는 유튜브가 대량 생산처럼 보이는 템플릿 영상을 수익 창출에서 빼기 때문이다(`CLAUDE.md` "같은 틀의 영상을 찍어 내지 않는다").
- **검증 게이트 표 (2026-11-06, 모든 방식에 적용)**: 유형을 정하기 전에 `videos/*/REVIEW.md`를 읽어 아래 표를 보고한다. "실제 결과가 있는 편"은 REVIEW.md 실제 칸에 숫자가 있는 편과, REVIEW.md가 없는 영상 중 대시보드 `videoPerformance`에 공개 7일이 지난 성과가 있는 편을 센다. 쇼츠와 옛 강의형 영상은 REVIEW.md가 없어도 결과가 있기 때문이다. REVIEW.md가 있는데 공개 7일이 지나도록 칸이 비어 있으면 결과로 세지 않고 Phase 11을 먼저 한다.

  | 방식 × 형식 | 만든 편 수 | 실제 결과가 있는 편 수 | Phase 11 중단 규칙에 걸림? | 이번에 고를 수 있나 |
  |---|---|---|---|---|

  - 결과 없이 이미 2편 이상 만든 방식·형식은 이번 후보에서 뺀다(결과가 나올 때까지 같은 걸 더 쌓지 않는다).
  - 듣기 방식은 이 표의 결과와 상관없이 위의 "듣기 방식을 고를 수 있는 조건"을 따른다.
  - 중단 규칙(`05-performance-review.md` 4절)에 걸린 방식·형식도 뺀다.
  - 쇼츠는 이미 만든 롱폼에서 장면을 고르는 것부터 한다(Phase 12). 새 소재는 그다음에 "세트"나 쇼츠 단독으로 기획한다(2026-11-06 기준 9월 2일 이후 쇼츠 공개 0개, 완성된 롱폼 대기 중).

### 방식에 따른 스캔 대상 매핑
| 방식 | 스캔 대상 | 쓰는 근거 |
|---|---|---|
| 강의 | 강의형 채널 (`채널 방식 태그` 표 참고) | 토픽 + 형식 |
| 듣기 | 듣기형 채널 | **형식만.** 토픽 근거로 쓰지 않는다 |
| 혼합 | 두 그룹 모두 | 형식 + 토픽 (가설로 표시) |

### 형식별 주의
- **롱폼**: 현재 스캔 방식(채널별 상위 5개) 그대로 쓸 수 있다.
- **쇼츠**: 스캔은 롱폼과 쇼츠의 상위 5개를 따로 저장한다(`topOutliersByFormat`). 쇼츠 판정은 유튜브의 쇼츠 전용 재생목록(`UUSH…`) 기준이다. 길이만 보면 61~180초 쇼츠를 놓치기 때문이다. 최근 50개 중 쇼츠가 0개인 채널은 "쇼츠 근거 없음"으로 적는다.
- **세트**: 같은 소재로 쇼츠와 롱폼을 함께 만든다. 스캔은 형식마다 한 번씩 본다.

선택 결과(방식, 형식, 이유)를 스캔 문서 맨 위에 적고, `videos/<프로젝트>/REVIEW.md`의 "예측" 칸 위에도 적는다.
끝나면 검증 게이트 표와 선택 결과를 보고하고 Phase 3으로 계속한다. 사용자가 다른 유형을 말하면 그걸 따른다.

## PHASE 3 — 경쟁 채널 스캔 & 성과 연동 자율 레이더

경쟁 채널은 사람이 수동으로 일일이 추가/삭제하지 않고, **자동화 우선 원칙(Automation-First, 2026-11-11)**에 따라 시스템이 무인 자율 라이프사이클(`발굴 ➔ 성과 판정 ➔ 황금광산 고정 ➔ 소진 시 자동 삭제`)로 관리한다.

### 자율 라이프사이클 4단계
1. **자동 발굴 (Candidate/Probation)**:
   - YouTube Analytics API의 추천 영상 유입(`trafficSources.suggestedVideos`)에서 우리 채널 시청자가 시청한 외부 채널을 자동으로 감지해 후보군에 등록한다.
   - 사용자가 직접 대화 중 채널 주소를 제공한 경우에도 후보군에 자동 편입된다.
2. **소재 채굴 및 영상 제작 연계**:
   - 후보 채널의 최근 60일 내 아웃라이어(채널 평균 대비 3배 이상 조회수) 소재 중 우리 채널이 다루지 않은 주제를 추출하여 Phase 4 소재 후보에 연결한다.
3. **7일 차 성과 연동 판정 (승격 or 차단)**:
   - 해당 채널 소재를 활용해 제작한 영상이 공개 7일 후:
     - **성과 우수 (같은 포맷 조회수 중앙값 대비 1.5배 이상)** ➔ **`🏆 황금 광산 (Gold Mine)`**으로 자동 고정. 모든 유효 아웃라이어를 소진할 때까지 우선 채굴한다.
     - **성과 부진 (노출 확보 후에도 중앙값 0.5배 미만)** ➔ 1회 경고 후, 2회 연속 부진 시 **`🚫 자동 차단 (Blocked)`** (90일 쿨다운).
4. **소재 소진 시 자동 삭제/졸업 (Graduated)**:
   - 황금 광산 채널이라도, 벤치마킹 가능한 최근 아웃라이어 중 우리 채널 미커버 주제가 0개가 되면(다 써먹었으면) 자동으로 리스트에서 **`🎓 명예 졸업 (자동 삭제/보관)`** 처리한다.

### 채널 방식 태그
- **강의/소리훈련**: 발음, 소리 차이, 연음, 리스닝 원리, 입모양, 규칙 설명 (우리 채널 토픽 벤치마크).
- **듣기/반복**: 긴 오디오 반복 듣기, 팟캐스트, 쉐도잉 (형식 및 길이 참고용).

### 상태를 근거로 쓰기 전에 확인할 것 (2026-11-11 갱신)
- 경쟁 채널 상태(황금 광산·차단·졸업)는 이제 손으로 넣지 않는다. 대시보드 동기화(`/api/sync`)마다 7일 순환이 자동으로 돈다. 순환은 공개 7일이 지난 우리 영상의 판정(`scripts/planning-outcome.mjs`)을 그 영상 `BRIEF.md` "기획 근거" 칸에 적힌 채널에만 반영한다. 2026-11-11에 손으로 넣었던 상태 6개는 모두 "후보"로 되돌렸다.
- 판정은 표본이 작으면 "보류"다(비교 숫자는 공개 후 첫 7일 조회수이고, 그 영상이 100회 미만이거나 같은 형식 최근 3편 중앙값이 300회 미만이면 보류. 지금 롱폼은 보류, 쇼츠는 판정이 나온다). 보류는 채널 상태를 바꾸지 않는다. 그래서 지금 채널 크기에서는 상태가 거의 바뀌지 않는 것이 정상이다.
- 그래도 황금 광산·차단을 소재 우선순위 근거로 쓸 때는 대시보드 "기획 근거 성적표" 탭이나 `market-demand.json`의 `d7AutonomousCycle.applied`에서 그 상태를 만든 편과 배수를 확인하고 표에 같이 적는다.
- 판정이 "기록 없음"으로 나오면 그 편 `BRIEF.md`에 "기획 근거" 칸이 없다는 뜻이다. Phase 4 선택 직후 이 칸을 빠뜨리지 않는다. 이 칸이 없으면 루프가 어느 경쟁 채널 소재가 통했는지 배우지 못한다.

### 스캔 절차
1. **실행**: `market-demand.json`의 `updatedAt`이 7일을 넘었으면 `node scripts/market-demand.mjs --sync-all-tracked`로 추적 채널을 먼저 갱신한다(채널당 약 4 unit). 새 채널은 `--channel="<주소>"`로 넣는다. 캐시 없이 최신 데이터를 읽는다.
2. **타겟 필터링**:
   - 현재 상태가 `gold_mine` 또는 활성 `candidate`인 채널의 최신 아웃라이어만 평가한다. 차단(`blocked`)되거나 졸업(`graduated`)된 채널은 제외한다.
   - 최근 60일 이내에 업로드된 영상 중 채널 기준선 대비 **3배 이상** 터진 영상을 아웃라이어로 판정한다.
   - 롱폼 근거는 `topOutliersByFormat.long`, 쇼츠 근거는 `topOutliersByFormat.short`를 분리해서 읽는다.
3. **소재 잔여율 계산**:
   - 아웃라이어 영상 제목과 우리 채널 `catalog.json` / `BRIEF.md`의 키워드 유사도를 대조하여 이미 다룬 소재를 제외한 **실질 잔여 소재 수**를 계산한다.
4. **산출물**:
   - `황금 광산 채널의 잔여 추천 소재`, `신규 자동 발굴 후보 채널`, `자동 차단/졸업 내역`을 표로 보고하고 Phase 4로 계속한다. 상태마다 이유(`statusReason`)와 위 확인 결과(근거 확인됨 / 근거 미확인)를 같이 적는다.

**경쟁 영상 소재를 쓰는 편은 대본·제목·썸네일을 정하기 전에 비교 시트를 먼저 만든다 (2026-11-12 사용자 결정)**: EP22~29 기획 15건 중 14건이 경쟁 영상 소재만 가져오고 제목·썸네일·훅·구성·화면의 이유는 옮기지 않았고, 롱폼 첫 7일 조회 중앙값이 6회였다. 시트는 `data/youtube/transform-sheets/<경쟁 영상ID>.json`이고 `/transform-sheet/<ID>`에서 좌우로 비교해 본다. 절차:
1. 경쟁 영상의 합친 리포트(`/outlier-report/<ID>`)를 읽는다. 없으면 `npm run outlier-report -- <ID>`로 만든다.
2. **한 편만 보지 않는다.** 같은 소재·유형의 다른 리포트(최소 1편)에서 항목별로 가져올 것을 고르고, 가져와도 되는지 **관문**을 통과시킨다: ① 이 소재에 실제로 해당하는가 ② 근거(출처·표본 수, 작은 표본은 "가설") ③ 우리 규칙(3060 국내 학습자, 전문용어·해외 일화 금지, 직전 3편과 구성 겹침). 통과하면 `borrowed`(이유·근거 필수), 못 하면 `rejected`(뺀 이유 필수)에 남긴다. 실패·기각도 데이터다.
3. 7개 항목(제목, 썸네일, 첫 15초, 전개, 화면 연출, 시청자 반응 지점, 끝맺음)마다 경쟁 쪽과 우리 쪽을 같은 행에 쓰고 **바꾼 이유**를 적는다. 우리 쪽은 대비가 같아지도록 출시 수준으로 만든다: 썸네일 시안과 핵심 장면은 `npm run image`(AI Studio Nano Banana 2.1, 워터마크 없음)로 실제 이미지를 만든다. 그림 속 글자는 만든 뒤 눈으로 읽어 철자·한글을 확인한다(2026-11-12 chocolate에서 사라지는 모음을 첫 o로 잘못 쓴 그림 3장을 이렇게 잡았다).
3-1. **컷도 글자가 아니라 이미지로, 리듬 있게 (2026-11-12 사용자)**: 화면 연출 행에는 `cutPlan.cuts[]`(컷마다 시각·카드 틀·이미지)를 쓰고, 시트 화면이 경쟁 컷 프레임과 우리 컷 카드를 시간 순서 필름스트립으로 나란히 보여 준다. 규칙(시험): 컷마다 이미지 파일이 있어야 하고, 우리 컷이 1분당 경쟁의 절반 이상이어야 하며, 컷 간격이 거의 일정하면(변동 15% 미만) 실패한다 — 긴 컷과 짧은 컷이 섞여야 한다. 경쟁 컷은 `npm run outlier-frames`가 영상에서 재서(`pacing.times`) 컷마다 프레임(`cut-NN.jpg`)을 이 PC에 만든다. **글자가 핵심인 카드(철자·강조 글자)는 AI 이미지로 만들지 않고 코드로 그린다**: `scripts/sheet-card-templates.mjs`의 카드 틀에 사라지는 글자는 단어와 위치(`drop:[시작,끝]`)로만 적고(조각은 코드가 계산), `npm run render-cards -- <영상ID>`로 PNG를 만든다. AI 이미지 모델은 단어 하나는 맞게 그리지만, 글자 일부만 흐리게 하라는 지시는 4번 틀렸다(2026-11-12 chocolate). 복잡한 그림·사진 느낌·썸네일은 계속 `npm run image`(AI Studio). 같은 틀은 나중에 HyperFrames 컴포지션 화면으로 이어 쓴다.
3-2. **완성형 시트: 컷 대본까지 한 번에 (2026-11-13 사용자: 다음 비교 시트는 단계별이 아니라 완성형으로)**: `schemaVersion: 2`인 시트는 `cutPlan.cuts[].narration`(그 컷에서 읽는 대본)이 컷마다 있어야 한다. 시트 화면은 컷 이미지 바로 아래에 컷 대본을, 맨 아래에 컷 대본을 이어 붙인 전체 대본을 보여 준다(전체 대본을 따로 쓰지 않으므로 어긋나지 않는다). 규칙(시험): 컷마다 대본이 있고, 영어로 시작하지 않으며(AI 음성 억양), 한글 글자 수가 컷 길이 1초당 7자를 넘지 않는다. 대본은 이 문서의 말투 규칙(AGENTS.md 스크립트 작성 원칙)과 사실 확인(`FACT-CHECK.md`, 없으면 음성 금지)을 따른다. 시트는 컷 계획·이미지·대본·제목 후보·썸네일 시안·사실 확인 목록이 한 번에 갖춰진 상태로 보고한다.
4. **썸네일 글자 수는 고정하지 않는다.** 경쟁 썸네일 여러 개의 글자 수·구성을 근거로 정하고, 근거가 약하면 2~3안을 만들어 유튜브 제목·썸네일 테스트로 가린다. 기본값 5단어는 근거 없을 때의 기준일 뿐이다(2026-11-12 사용자: 2단어로 이길 수 있으면 그렇게, 아니면 더 전달되게).
5. **우리 정체성은 고정하지 않는다.** `identityShare`에 우리/경쟁 비율과 근거를 적는다. 우리 영상 확정 판정이 쌓이기 전에는 경쟁에서 잘된 요소를 더 많이 섞는다(2026-11-12 사용자: 정체성을 찾아가는 중이라 하나를 정해 두면 지금까지처럼 된다).
6. 시트는 제안이다. 사용자가 고치고 확정하면 `status`를 `approved`로 올리고, 공개되면 `published`, 7일 성적이 나오면 `outcome`에 자동 판정 값을 적는다. `pending`에 적힌 것(사실 확인, 직전 편과 비교표)은 대본 전에 끝낸다.
`비교 시트:` 줄은 경쟁 영상(`경쟁 영상:` 줄)을 근거로 쓰는 EP30부터 필수이고 빠지면 `npm test`가 실패한다.

`다음 기획 입력` 줄은 EP30부터 필수다(2026-11-12). 빠지면 시작 브리핑의 자동 루프 점검(`brief-input`)과 `npm test` 의도 명세가 알린다.

## PHASE 5 — 분량/포맷 세부 결정

- **롱폼을 고른 경우**: 기본 길이는 8~10분이다. **프레임 수는 고정돼 있지 않다** (비트에 맞춤, 11~15개 등 다양). 길이를 늘릴지(15~30분) 사용자가 직접 결정한다.
- **쇼츠를 고른 경우**: 훅으로 쓸 장면을 정한다. 롱폼 연계형(세트)이면 마지막 장면이 어느 롱폼 에피소드로 이어지는지 미리 설계한다.
- **이 영상에만 있는 코너 (필수, 2026-11-06)**: 이 소재에서만 할 수 있는 코너를 1개 이상 정해 `BRIEF.md`에 적는다. 다른 소재에 그대로 옮겨도 말이 되면 다시 정한다. 예: R과 L은 문장에서 한 단어만 바뀌는 듣기 문제, -S는 houses처럼 앞소리까지 바뀌는 단어.
- **비주얼 스타일 1차 결정 (2026-11-06, Phase 9에서 앞당김)**: 소재가 정해지면 스타일도 대부분 정해진다(예: 혀·입 위치 설명이면 스케치노트). `04-visual-and-assets.md` 2절의 5개 옵션 중 이 소재에 맞는 것을 이유와 함께 추천하고, 직전 3편과 같은 스타일이면 그 사실을 함께 적는다. Phase 9에서는 대본을 본 뒤 이 결정을 확인만 한다.
- **쇼츠 세트와 연결 (2026-11-06)**: 쇼츠 2개를 어떤 장면으로 뺄지 후보만 적고(Phase 12 1절), 엔드스크린·재생목록 연결을 `BRIEF.md` "연결" 칸에 적는다(Phase 12 3절).

**멈춤 지점 1 — 기획 확정**: 소재, 방식·형식, 고유 코너, 추천 스타일, 쇼츠 세트를 한 표로 보고하고 사용자 승인을 받는다. 승인되면 바로 아래 "소재 이력 등록"을 `status: "selected"`로 한다.

### 소재 이력 등록 (2026-11-11)

`idea-board-history.json`은 다음 기획이 같은 소재를 다시 고르지 않게 막는 목록이다. 아래 세 때에 묻지 않고 등록한다. 같은 `topic` 문자열로 다시 보내면 상태만 바뀌므로, 처음 등록한 `topic`을 `BRIEF.md` "기획 근거" 칸 첫 줄에 그대로 적어 둔다. 2026-11-11 이전 편처럼 그 줄이 없으면 이력에서 `episodeSlug`로 찾아 그 `topic`을 쓰고, 이력에도 없으면 `BRIEF.md` 제목으로 새로 등록한다.

| 때 | `status` | 누가 |
|---|---|---|
| 멈춤 지점 1 승인 | `selected` | 이 단계 |
| 업로드 예약이 확인됨 (`status.json`이 scheduled) | `scheduled` | Phase 13 끝, 또는 Phase 1·0-B에서 빠진 것을 찾았을 때 |
| 공개 확인 (`catalog.json`에 공개로 나옴) | `published`, `producedAt`에 공개일 | Phase 11, 또는 Phase 1·0-B에서 빠진 것을 찾았을 때 |

대시보드 서버(포트 3001)의 기존 등록 통로를 쓴다. 한글이 깨지지 않게 요청 본문은 스크래치 폴더에 JSON 파일로 저장해 보낸다.

```bash
# body.json 예시
# {"topic":"R과 L, 혀끝이 닿느냐 마느냐","angleOrHook":"<훅 한 줄>","targetAudience":"<타겟 한 줄>",
#  "dataSourceRefs":[{"source":"competitorOutlier","detail":"<채널>·<영상 ID>·<배율>배"},{"source":"audienceDna","detail":"<항목> (<n>회)"}],
#  "episodeSlug":"ep26-r-vs-l","episodeLabel":"EP26","status":"selected"}
curl -s -X POST http://localhost:3001/api/idea-board/history/register \
  -H "Content-Type: application/json" --data-binary @<스크래치 폴더>/body.json
```

- 응답의 `entries`에 방금 보낸 `topic`이 있는지 확인한다. 서버가 꺼져 있으면 켜고 다시 보낸다(파일을 직접 고치지 않는다. 서버가 같은 파일을 쓰고 있어 동시에 고치면 내용이 날아갈 수 있다).
- 쇼츠는 롱폼과 같은 소재면 따로 등록하지 않는다. 쇼츠만 단독 소재로 만든 경우에만 등록한다.
