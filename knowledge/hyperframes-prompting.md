# HyperFrames 프롬프트 운영 기준

마지막 갱신: 2026-08-23

이 문서는 HyperFrames 공식 Prompt Guide를 우리 채널 제작 방식에 맞게 압축한 실행 기준이다. 원문 기능을 모두 사용하는 것이 목적이 아니라, 왕초보가 이해하기 쉬운 영상을 일관되게 만드는 것이 목적이다.

## 1. 먼저 워크플로를 고른다

- 새 대본·주제에서 시작하는 영어 교육 영상: `/faceless-explainer`
- 기존 음성·영상·참고 디자인을 조합하는 맞춤형 작업: `/general-video`
- 3~10초 무나레이션 인트로·정답 공개·CTA 부품: `/motion-graphics`
- 기존 토킹헤드 영상 자막: `/embedded-captions`
- 기존 토킹헤드에 동기 그래픽 추가: `/talking-head-recut`
- 판단이 애매하면 반드시 `/hyperframes`로 시작해 라우팅한다.

워크플로 선택표의 전체 기준은 [제작 규칙](production-rules.md#hyperframes-워크플로-선택)을 따른다.

## 2. 프롬프트의 표준 구조

한 번에 모든 기술을 나열하지 않는다. 아래 순서로 결과를 결정하는 정보만 준다.

1. **경로와 결과물** — 워크플로, 롱폼/쇼츠, 비율, 대략적인 길이
2. **시청자와 결과** — 3060 왕초보가 영상 뒤에 무엇을 이해해야 하는지 한 문장
3. **원본** — 확정 대본, 음성, 이미지, 참고 영상의 정확한 파일 경로
4. **고정할 것** — 대본을 그대로 쓸지, 요약·재배열해도 되는지, 음성을 교체해도 되는지
5. **장면 구조** — 한 장면 한 개념, 질문→생각→설명→확인의 학습 흐름
6. **디자인 기준** — `frame.md`의 팔레트·폰트·강조색을 단일 기준으로 사용
7. **모션 기준** — 이해 구간은 안정, 전환·예시 구간은 리듬, 동시에 움직일 요소 제한
8. **음성·자막** — 실제 발화 타이밍 기준, 영어 철자와 한글 발음의 강조색 지정
9. **금지 사항** — 작은 글자, 과도한 3D·글리치·파티클, 모든 전환 효과음, 의미 없는 이동
10. **완료 기준** — 미리보기 검토, `lint`, `check`, 소리 켠 재생, 무음 재생

## 3. 길이와 장면 밀도

- 확정 대본이나 TTS를 쓰는 영상은 `60초`처럼 고정하지 않고 `약 60초`라고 쓴다. 실제 길이는 발화가 결정한다.
- 장면마다 초점은 하나만 둔다. 한 장면에 규칙·예외·퀴즈를 함께 넣지 않는다.
- 화면이 비어 보인다고 개념을 추가하지 않는다. 하나의 핵심 요소, 이해를 돕는 보조 요소, 채널 공통 장식만 둔다.
- 시각 밀도는 장면 목적에 맞춘다. 설명 구간은 정보 계층이 먼저고, 장식 밀도는 그다음이다.

## 4. 디자인과 참고 자료

- `frame.md`는 색상·폰트·강조 관계의 단일 기준이다. `고급스럽게`, `브랜드답게` 같은 말만 쓰지 않는다.
- 브랜드에서 고정하는 것은 팔레트·폰트·굵기 관계다. 화면 구성·여백·모션은 영상 매체에 맞게 확대·재구성한다.
- 디자인 파일에서 정지해도 되는 로고·아이콘·질감·그림은 이미지로 유지한다.
- 텍스트·색·배치·상태가 시간에 따라 바뀌거나 그림의 부분들이 따로 움직이면 HTML/SVG 요소로 다시 만든다.
- 참고 이미지는 최종 프레임이 아니라 디자인 문법의 근거다. 색, 구도, 글자 위계, 질감, 모션 원리를 분리해 재해석하고 원본을 그대로 복제하지 않는다.
- 실사·사진·유기적 일러스트는 파일로 공급하거나 생성한다. 말로만 사진처럼 그리라고 요구하지 않는다.

## 5. 우리 채널의 모션 문법

- 기본 감각은 `smooth`, 일반 등장 시간은 약 0.4초다. 질문·정답처럼 빠른 박자만 `snappy`와 약 0.2초를 쓴다.
- 중요한 설명이 시작되면 요소가 제자리에 안착한 뒤 움직임을 줄인다.
- 여러 요소는 동시에 나타나지 않고 의미 순서대로 들어온다. `A가 완전히 사라진 뒤 B가 등장`처럼 겹침 여부를 명시한다.
- 카메라 이동은 한 장면의 초점을 강화할 때만 쓴다. 기본은 4~8%의 느린 push-in보다도 정적인 구도가 우선이다.
- 장면 전환은 이야기 연결이 있을 때만 사용한다. 전환 효과의 존재보다 앞뒤 개념의 연결이 먼저다.
- 3D는 깊이·조명·카메라가 실제 학습에 필요한 경우에만 Three.js로 사용한다. 장식 목적의 3D는 쓰지 않는다.
- VFX, liquid glass, 글리치, 강한 컬러 그레이딩은 채널 기본 스타일이 아니다.

## 6. 자막과 강조

- **나레이션이 Gemini TTS면 하단 단어별 자막 바를 넣지 않는다.** Gemini TTS는 단어별 타임스탬프를
  안 줘서 whisper 재정렬이 필요한데, 한글 문장 속 영어 목표 단어(예: Want/Won't)를 잘못 인식해
  타이밍이 부정확해진다(EP12 실측: 10줄 중 6줄이 근사치로 대체됨). 문장/구 단위 포커스 문구는
  이 문제와 무관하니 그대로 쓴다. 나레이션이 HeyGen TTS(단어별 타임스탬프 직접 제공)면 이 제약이
  없다. 상세: [결정 기록](decisions/2026-09-04-no-word-level-captions-with-gemini-tts.md).
- 한 섹션에는 한 가지 자막 정체성만 사용한다. 서로 다른 자막 스타일을 섞지 않는다.
- 전체 문장을 유지하면서 실제 발화 단어만 차례로 강조하는 방식이 기본이다.
- 영어 철자 발화 강조는 `#FF0000`, 한글 발음 강조는 `#008EFF`를 사용한다.
- 모든 단어에 효과를 추가하지 않는다. 학습 대상 철자·발음·정답에만 색상이나 짧은 모션을 준다.
- 자막은 실제 음성 전사로 타이밍을 잡고, 고유 철자와 한글 발음은 사람이 청취해 교정한다.
- 쇼츠는 9:16과 상·하단 안전영역을 명시한다.

## 7. 음성·효과음·음악

- 음성이 영상의 시간축이다. 화면과 자막을 음성에 맞추며, 음성을 임의의 장면 길이에 맞춰 자르지 않는다.
- 배경음악은 음성을 방해하지 않는 수준에만 둔다. 교육 내용의 이해를 돕지 않으면 생략한다.
- 효과음은 질문, 정답, 핵심 연결, CTA처럼 의미 있는 사건에만 배치한다.
- 음원·효과음·이미지는 프로젝트 내부 경로로 고정한다. 렌더 도중 외부 URL에 의존하지 않는다.

## 7-1. 나레이션 애니메이션은 whisper 실측 타임스탬프로 처음부터 만든다 (필수, 예외 없음)

**TTS를 생성한 뒤 화면 애니메이션을 짤 때, 추정 시간(글자수 비례 계산이나 STORYBOARD.md의
"추정" duration)으로 먼저 만들고 나중에 실제 길이에 맞춰 고치지 않는다.** 순서는 항상 이렇다:

1. 그 씬의 나레이션 wav 파일이 나오면 **바로** whisper.cpp(word-level, `-ml 1`)로 전사해서,
   애니메이션이 반응해야 할 각 핵심 단어·구절이 **실제로 발화되는 시작/끝 시각**을 뽑는다.
2. 그 실측 시각을 애니메이션 코드에 **직접** 쓴다. 추정치 상수를 먼저 넣고 나중에 비율로
   늘리거나 줄이지 않는다.
3. 나레이션을 여러 조각으로 나눠 생성하는 씬(EP13 Frame 9의 한국어+영어 분리 생성처럼)은 각
   조각의 실제 길이를 생성 시점에 이미 알고 있으므로, 그 값을 그대로 쓰면 되고 별도 whisper
   작업이 필요 없다.

**왜 이게 필수인가**: EP13에서 "추정 시간으로 먼저 만들고, 실제 길이가 나오면
`RATIO = 실제/추정`을 곱해서 늘린다" 방식을 썼는데, **전체 길이는 맞았지만 개별 단어 등장
시점은 최대 6.3초까지 어긋났다**(발화 속도가 균일하지 않아서 — 쉬는 구간·강조 구간마다
다름). 결국 6개 프레임(5/6/7/8/10/11)을 whisper 실측으로 전부 다시 만들어야 했다(상세:
아래 §9-1, `videos/ep13-tongue-shortcut/TASKS.md`). **처음부터 이 순서로 만들면 그 재작업
자체가 없어진다** — §9-1은 "이미 추정치로 만들어버렸을 때 고치는 법"이지, 원래 따라야 할
순서가 아니다.

## 8. 스토리보드와 반복 작업

- 두 장면을 넘는 영상은 기본적으로 `STORYBOARD.md`를 먼저 작성한다.
- 스토리보드는 완성 이미지를 나열하는 문서가 아니라 장면별 목적, 화면 초점, 발화, 동작, 전환을 정하는 문서다.
- 사용자 피드백은 `더 좋게`처럼 넓게 처리하지 않는다. 대상 장면·요소·문제·원하는 결과를 좁혀 수정한다.
- 한 번에 한 종류만 바꾼다: 타이밍, 배치, 색, 자막, 오디오를 분리해 검토한다.
- 레퍼런스 재현은 먼저 정지 구도, 다음 타이포그래피, 다음 모션, 마지막 질감 순으로 접근한다.

## 9. 템플릿과 공용화

- 디자인이 승인되기 전에는 변수화하거나 공용 컴포넌트로 고정하지 않는다.
- 승인 후 반복해서 바뀌는 제목·단어·발음·색만 명시적 변수로 만든다.
- 화면 크기, 프레임률, 전체 영상 길이, 출력 코덱은 변수로 만들지 않는다.
- 템플릿은 서로 크게 다른 두 값으로 두 번 렌더해 실제 화면이 바뀌는지 확인한다.
- 쇼츠·롱폼·썸네일은 같은 브랜드 값을 공유해도 레이아웃 템플릿은 분리한다.

## 9-1. (사후 대처) 추정치로 이미 만들어버렸을 때 — GSAP `timeScale()`은 안 먹는다

> **§7-1을 따랐다면 이 절은 필요 없다.** 이건 이미 추정 시간으로 애니메이션을 다 만들어버린
> 뒤에 실제 음성이 나온 경우의 사후 수습 기록이다 — 앞으로 새 씬을 만들 땐 §7-1대로 whisper
> 실측 시각을 처음부터 쓸 것.

TTS를 나중에 생성하면 실제 길이가 대본 단계 추정치보다 훨씬 길어지는 경우가 흔하다(EP13은 12개
씬 평균 63% 초과, 심한 씬은 +115%). 이때 씬 내부 애니메이션(글자 등장 타이밍 등)을 실제 길이에
맞춰 늘려야 하는데, **GSAP `tl.timeScale(원래길이/실제길이)`를 타임라인에 걸어도 HyperFrames
렌더러가 이를 무시한다** — 애니메이션은 원래(짧은) 속도 그대로 다 끝나버리고, 남는 시간은 그냥
마지막 프레임이 정지해서 채워진다(EP13에서 실측 확인, 2026-09-06). `check`는 이 상태를 에러로
잡지 않는다 — 반드시 스냅샷을 여러 지점 떠서 눈으로 확인해야 발견된다.

**1차 완화책(임시방편, 부정확함)**: 타임라인 생성 직후 `tl.to`/`tl.fromTo`/`tl.set`/`tl.call`을
감싸서, 숫자로 넘어오는 position 인자를 직접 비율만큼 곱해준다:

```js
var RATIO = 실제길이 / 원래길이;
var _to = tl.to.bind(tl), _fromTo = tl.fromTo.bind(tl), _set = tl.set.bind(tl), _call = tl.call.bind(tl);
tl.to = function (t, v, p) { return _to(t, v, typeof p === "number" ? p * RATIO : p); };
tl.fromTo = function (t, f, v, p) { return _fromTo(t, f, v, typeof p === "number" ? p * RATIO : p); };
tl.set = function (t, v, p) { return _set(t, v, typeof p === "number" ? p * RATIO : p); };
tl.call = function (fn, params, p) { return _call(fn, params, typeof p === "number" ? p * RATIO : p); };
```

이후 기존 코드의 개별 타임스탬프(`14.0`, `t + 0.3` 등)는 전혀 손댈 필요 없다 — `SCENE2 + 0.3`
같은 표현도 계산된 숫자 전체가 그대로 스케일된다. 문자열 position(`"+=0.5"`, 라벨 등)은
`typeof p === "number"` 체크로 자동 제외되므로 안전하다.

**예외**: `<video>`/`<audio>`처럼 `data-start`를 직접 갖는 HyperFrames 자체 타임드 엘리먼트는
이 JS 타임라인과 별개 시스템이라 위 래퍼가 적용되지 않는다 — `data-start` 값도 같은 RATIO를
곱해서 손으로 맞출 것(EP13 Frame 5의 B롤 영상 사례).

**⚠️ 이 RATIO 방식 자체가 부정확하다 — 최종 방법이 아니다(2026-09-06/07 실측으로 확인).**
전체 길이는 정확히 맞지만, **실제 발화는 균일한 속도로 늘어나지 않는다**(쉬는 구간·강조
구간마다 다름). EP13에서 RATIO 방식으로 1차 처리했던 6개 프레임(5/6/7/8/10/11)을 나중에
whisper.cpp 실측 시각과 대조해보니, Frame 5의 B/A/G chip 등장 시점이 최대 **6.3초**나 일찍
나오는 등 전 프레임에서 개별 단어 타이밍이 실제 발화와 어긋나 있었다(`videos/ep13-tongue-shortcut/TASKS.md`
1~7단계에 프레임별 상세 기록). "전체 지속시간만 맞으면 된다"는 가정 자체가 틀렸다는 뜻이다.

**정답 패턴 — whisper.cpp로 실측 시각을 직접 코드에 박아넣기**: RATIO 계산을 아예 걷어내고,
그 프레임의 음성 파일을 whisper.cpp(word-level, `-ml 1`)로 전사해서 **각 단어가 실제로
발화되는 시점**을 뽑은 뒤, 그 값을 타임라인에 직접 하드코딩한다(이 프로젝트가 Remotion
시절부터 써 온 "whisper 시계 보정 + LCS 매칭"과 같은 원리). **나레이션을 여러 조각으로 나눠
생성하는 씬(EP13 Frame 9처럼 한국어+영어를 분리 생성하는 경우)은 애초에 각 조각의 실제
길이를 알고 있으므로 이 문제가 처음부터 없다** — RATIO는 "한 통짜리 음성 파일 안에서 특정
단어가 정확히 몇 초에 나오는지 모를 때"만 쓰는 근사치이고, 결국 whisper로 실측해서 교체하는
게 정답이라는 걸 전제하고 써야 한다. 씬을 새로 만들 때는 아예 처음부터(생성 직후) whisper로
실측해서 정확한 값으로 짜는 게, 나중에 RATIO로 짰다가 다시 통째로 고치는 것보다 빠르다.

## 10. 렌더 전 필수 검수

1. `npx hyperframes lint`
2. `npx hyperframes check`
3. 미리보기에서 처음부터 끝까지 소리 켜고 재생
4. 무음으로 다시 재생해 자막과 시각적 이해 확인
5. 시작·중간·끝 프레임 직접 확인
6. 최종 렌더 파일의 존재, 크기, 재생 가능 여부 확인

`check`의 겹침·가림 경고를 넓은 예외 속성으로 숨기지 않는다. 예외가 필요하면 가장 작은 요소에만 적용하고, 대비 검사 수가 줄지 않았는지 확인한다.

## 11. 금지 패턴

- `/hyperframes` 또는 선택한 전용 워크플로 없이 일반 HTML 영상처럼 만들기
- React·Vue 컴포넌트를 요구하기
- 대본 발화 길이를 확인하지 않고 정확한 초 수를 강제하기
- 실제 자산 경로를 주지 않고 `내 로고`, `그 음성`처럼 지시하기
- 모든 요소를 동시에 움직이거나 모든 단어에 효과를 주기
- 참고 화면을 슬라이드 이미지로 이어 붙이고 모션이라고 부르기
- 미리보기만 보고 `check` 없이 렌더하기
- 디자인이 확정되지 않았는데 공용 템플릿부터 만들기
- 기본 교육 영상에 4K·60fps·3D·VFX를 습관적으로 적용하기

## 12. 채널용 기본 프롬프트 골격

```text
Using /hyperframes, route this request to /faceless-explainer.

결과물: [롱폼 1920x1080 / 쇼츠 1080x1920], 약 [길이].
시청자: 3060 국내 거주 영어 왕초보.
학습 결과: 영상이 끝나면 시청자가 [한 가지 이해]를 할 수 있어야 한다.

원본:
- 확정 대본: [경로]
- 음성: [경로, 유지/교체 가능 여부]
- 이미지·참고 자료: [경로]
- 디자인 기준: frame.md를 색상·폰트의 단일 기준으로 사용.

구조: 한 장면 한 개념. [질문 → 생각 → 원리 → 예시 → 확인] 순서.
화면: 큰 글자, 높은 대비, 전문 용어 최소화. 영어 철자 강조 #FF0000,
한글 발음 강조 #008EFF. 실제 음성 타이밍과 동기화.
모션: 이해 구간은 안정, 전환·예시에서만 smooth/snappy 리듬.
효과음: 질문·정답·핵심 연결에만 작게.

금지: 작은 글자, 의미 없는 이동, 모든 단어 강조, 과도한 3D·글리치·파티클,
모든 장면의 효과음, 음성과 맞지 않는 고정 타이밍.

두 장면 이상이므로 먼저 BRIEF.md와 STORYBOARD.md를 작성해 검토 가능한 상태로 만들고,
승인 후 제작한다. 렌더 전 lint와 check를 통과시킨다.
```
