## 제작 단계와 상태 기록

- 모든 영상은 [영상 제작 표준 워크플로우](VIDEO_WORKFLOW.md)의 10단계를 따른다.
- 새 영상 프로젝트는 루트에 `STATUS.md`를 만들고 [STATUS 템플릿](templates/STATUS.template.md)의 상태 값과 승인 게이트를 사용한다.
- 작업 시작 시 `STATUS.md`의 `현재 단계`와 `다음 행동`을 먼저 확인한다.
- 대본, 스토리보드, 디자인, 렌더, 업로드 승인은 서로 독립적으로 기록하며 추정해서 승인하지 않는다.
- **영상 렌더링 임의 실행 절대 금지 (2026-09-20 확정)**: 컴포지션 작성 및 `npx hyperframes check` 통과 후 에이전트가 임의로 `render`를 실행하는 것을 엄격히 금지한다. 영상 렌더링은 20분 이상의 고부하 리소스가 소모되므로, 반드시 린터 통과 결과와 화면 구성 요약을 보고하고 **사용자의 직접 검수 및 명시적 승인("렌더링 진행해" 등)**을 획득한 뒤에만 착수한다.
- 단계가 바뀌거나 실패·새 결정이 생기면 `STATUS.md`를 즉시 갱신하고 상세 근거는 관련 에피소드 문서와 월별 로그에 둔다.

## 쇼츠 화면

- 1080×1920.
- 상단·하단 플랫폼 UI 안전영역을 지킨다.
- 사용자의 결정에 따라 우측 버튼 안전영역은 별도로 비우지 않는다.
- **새 쇼츠의 하단은 13% 이상 비운다(2026-11-07)**: 아이폰 실제 화면 1장과 그 쇼츠의 원본 레이아웃을 맞춰 재 보니, 영상은 폭의 약 108%로 확대되어 화면 맨 위부터 채워지고(좌우가 약 40px씩 잘림) 채널 이름, 제목, 관련 동영상 링크가 1920 기준 y 약 1680 아래를 가렸다(한 기기 기준 추정치). 자막과 카드는 y 1600 위에, 화살표 끝은 y 1640 위에 둔다. 상단은 검색 아이콘 때문에 y 230 아래부터 쓴다. 관련 동영상 링크는 채널 이름과 제목 아래, x 약 80~880의 알약 모양이다. 좌우 끝이 잘리므로 양옆 60px은 비운다.
- 영어 철자 발화 시 해당 철자 색을 변경한다.
- 한글 발음 발화 시 해당 음절 색을 변경한다.
- 핵심 이해 구간에서는 요소 위치를 안정시키고, 전환·예시 구간에서 리듬을 만든다.
- 효과음은 모든 장면 전환에 넣지 않고 질문·정답·CTA 등 의미 있는 박자에만 사용한다.
- **튀는 등장(바운스)은 단어 펄스에만 쓴다(2026-11-11, unslop 점검)**: 소리에 맞춰 단어가 1.15배 튀는 펄스는 학습 효과 때문에 필수지만, 뱃지·썸네일 카드·알약·손 그림까지 전부 `back.out`으로 튀어나오면 "AI가 만든 범용 효과"처럼 보인다(파티클 효과를 뺀 것과 같은 이유). 그 밖의 등장은 `power3.out` 같은 부드러운 감속으로, 크기는 0.9 → 1 정도로만 바꾼다. 점검 출처: heydamir/unslop 스킬의 "bouncy springs" 지적(영상에 맞는 항목만 적용 — 글자 굵기 500 이하 같은 웹 앱 기준은 휴대폰 영상 가독성과 맞지 않아 쓰지 않는다).
- **안전선은 값으로 확인한다(2026-11-11)**: 새 쇼츠를 만들 때 위 알약 top ≥ 232, 자막·카드 아래 끝 ≤ 1600을 숫자로 맞춘다. EP24 두 번째 쇼츠에서 알약 212·자막 끝 1608로 짰다가 규칙을 다시 읽고 고쳤다.

## 롱폼 단어 드릴 및 듣기 영상 시각화 표준 (2026-10-09 정정 확정)

- **영어 단어 음절 분리 표기(가운뎃점 `·`) 필수 표출 (한글 억지 쪼개기 영구 금지)**:
  - **한글 발음 억지 쪼개기 엄격 금지**: 영어 1음절 단어(`sheep`, `pool`, `right`)를 한글로 `[쉬 · 입]`, `[푸 · 울]`, `[롸 · 이트]`처럼 쪼개 표기하는 행위를 영구 금지한다 (학습자에게 불필요한 모음 첨가 및 2~3음절 왜곡 조장).
  - **2음절 이상 영어 단어는 영어 철자 자체에 가운뎃점(`·`)으로 음절 경계 표기**:
    - `cof · fee [커피]`, `let · ter [레러]`, `wa · ter [워러]`, `ri · ver [리버]` vs `li · ver [리버]`
    - `ho · ping [호핑]` vs `hop · ping [하핑]` (모음 장단음이 갈리는 음절 원리 체화)
  - **1음절 단어 표기**:
    - 영어 단어는 그대로 1음절 유지 (`sheep`, `ship`, `pool`, `pull`, `right`, `light`).
    - 발음기호 장음 표시(`ː`) 및 쉬운 말 뱃지(`입꼬리 당김` vs `힘 뺌`, `허공 0%` vs `잇몸 100%`)로 호흡을 명확히 전달하고, 한글 독음은 자연스러운 1음절(`[쉽]`, `[풀]`, `[롸이트]`)로 표기.
  - 적용 범위: 훅 카드(F01), 원리 설명(F02), 본문 드릴 카드(F03~F06), 셔플 퀴즈 정답(F08), 1장 요약표(F09), 앵콜 총복습(F10) 전 프레임.

- **실전 대화 프레임 문장 내 타겟 단어 시각적 강조 및 펄스 바운스 필수**:
  - 문장 전체를 밋밋한 단색 플랫 텍스트로 표출하는 것을 엄격히 금지한다.
  - 문장 내 학습 타겟 짝단어(sheep/ship, R/L 등)는 반드시 고대비 컬러/밑줄/배경 하이라이트(`<span class="hl-tense">`, `<span class="hl-lax">`, `<span class="hl-r">`, `<span class="hl-l">`)로 시각적 대비를 준다.
  - 원어민 오디오 발화 시점에 맞춰 해당 타겟 단어가 1.15~1.2배 튀어오르는 바운스/펄스(scale) 애니메이션을 결합한다.
  - 카드 하단에는 해당 문장의 짝단어 소리 팁(`💡 right (허공 0%) vs light (잇몸 100%)`)을 반드시 함께 표출한다.

- **컴포지션 UI 텍스트 자동 줄바꿈 절대 방지 (`white-space: nowrap`, 2026-10-09 확정)**:
  - 상단 알약(`eyebrow-pill`), 팁 뱃지(`tip-badge`), 카드 상단 라벨(`card-label`), 메인 영문 단어(`word-text`)는 예기치 못한 줄바꿈으로 레이아웃이 깨지거나 글자가 찌그러지지 않도록 반드시 `white-space: nowrap;` 및 `flex-shrink: 0;`를 강제한다.
  - 상단 알약 설명 문구는 간결하게 정돈하여 가로폭을 절대 초과하지 않게 하고, 긴 단어는 폰트 크기(`4.0cqw~4.2cqw`)를 사전에 계산해 안전 마진을 둔다.

- **타겟 학습 음소·접미사(-ED, -S 등) 분리 강조 필수 (2026-10-09 확정)**:
  - 단어 전체를 통색으로 칠해 정작 가르쳐야 할 핵심 접미사(-ed)나 타겟 음소가 묻히는 것을 영구 금지한다.
  - **어간은 뉴트럴 차콜 블랙(`<span class="word-base">walk</span>`, `#111111`) + 타겟 접미사에만 규칙별 고대비 강조 컬러(`<span class="word-ed ed-t">ed</span>`) 및 밑줄/뱃지 효과**를 적용하여 시청자의 시선이 0.1초 만에 접미사 끝소리에 꽂히도록 한다.
  - 사운드 매핑: [t] 코랄 레드(`#DC2626`), [d] 스카이 블루(`#2563EB`), [ɪd] 에메랄드 그린(`#059669`), [ɪd] 형용사 예외 앰버 골드(`#D97706`).

- **불필요한 메타 설명 문구(남·여 교차 N회 반복 등) UI 표출 금지 (2026-10-09 확정)**:
  - 컴포지션 화면(단어 드릴 카드, 퀴즈 카드 등)에 "남·여 교차 6회 반복", "TTS 3회 반복", "원어민 발음 듣기" 같은 제작자/시스템 관점의 사족 메타 설명 문구를 텍스트 라벨(`.dot-label` 등)로 노출하는 것을 엄격히 금지한다.
  - 시청자는 오디오와 시각적 닷(dots, 점) 애니메이션 반응을 통해 반복 구조를 자연스럽게 체화하므로, 불필요한 텍스트 라벨은 시각적 노이즈를 유발한다. 반복 횟수는 오직 시각적 인디케이터(점/진행바)로만 깔끔하게 노출한다.

## AI 생성 미디어(비디오·이미지) 플랫폼 로고/워터마크 노출 절대 금지 및 반입 전 무결점 검수 원칙 (2026-10-09 확정)

- **AI 생성 에셋 워터마크 노출 Zero Tolerance**: AI 툴(Google Veo/Gemini, Runway, Sora, Pika, Kling, Midjourney, Imagen 등)로 생성한 배경 비디오나 일러스트를 영상 컴포지션에 사용할 때, 플랫폼 워터마크·로고(Gemini 4각 별 스파클 아이콘, Runway 마크 등)가 시청자 화면에 1픽셀이라도 노출되는 것을 엄격히 금지한다.
- **프롬프트 네거티브 지침 의무화**: 모든 이미지/비디오 생성 프롬프트 끝에 `no watermark, no AI logos, no Gemini logo or sparkle icons, clean corners without stamps or overlays, ultra-clean edges` 네거티브 지시를 필수 포함한다.
- **에셋 반입 시 4방 모서리 전수 시각 검수**: AI로 생성한 비디오나 이미지를 프로젝트 `assets/` 디렉토리에 복사/배치하기 전에, 에이전트가 직접 모서리 4방(특히 우측 하단/상단)에 워터마크나 스파클 아이콘이 찍혀 있는지 시각적으로 확인(프레임 캡처 후 `view_file`)한다. 무검수로 컴포지션에 직결하는 행위를 일체 불허한다.
- **워터마크 발견 시 ffmpeg 고화질 크롭/스케일 후처리 필수**: 플랫폼 워터마크가 찍혀 있을 경우, ffmpeg를 사용하여 워터마크 영역이 화면 밖으로 완전히 잘려나가도록 미세 크롭 및 1080p 스케일(`crop=1696:954:0:0,scale=1920:1080:flags=lanczos`)하여 워터마크가 0.1픽셀도 없는 클린 에셋으로 재인코딩한 후 반입한다.
- **컴포지션 CSS 2중 안전망**: 배경 비디오 및 이미지 컨테이너에는 반드시 `overflow: hidden`을 지정하고, 배경 비디오 태그(`.bg-video`)에 `transform: scale(1.05); transform-origin: center center;` 등 미세 여백 안전망을 두어 브라우저나 디바이스 차이로 인한 모서리 누출 위험을 2중으로 원천 차단한다.

## 이미지 생성 2단계 원칙: 자체 모델 우선 및 한도 소진 시 브라우저 컨트롤 폴백 (2026-11-10 확정)

1. **1단계 (자체 모델 우선 사용)**: 이미지/일러스트 제작 시 에이전트의 **자체 모델(`image-generator` 서브에이전트 / Gemini API / MCP 이미지 생성 도구)을 1차로 우선 사용**한다.
   - **Antigravity Gemini 에이전트 전용이다**(2026-11-11 사용자 확인). Claude Code처럼 자체 이미지 모델이 없는 에이전트는 바로 2단계로 만든다. 외부 유료 생성 MCP(Higgsfield, Abracadabrax 등)는 자체 모델이 아니므로 사용자 지시 없이 쓰지 않는다. 기준 문서: `AGENTS.md` 같은 절.
2. **2단계 (자체 모델 한도 소진 시 브라우저 컨트롤 폴백)**: 자체 모델의 한도 소진(429 Quota Exhausted, 크레딧 소진 등) 발생 시, 코드로 어설픈 그래픽을 그리거나(SVG/Canvas/Chrome 스크린샷 렌더 등) 대체하지 않고 즉시 **브라우저 컨트롤(`scripts/generate-web-gemini-image.mjs` / Chrome CDP 연동 Web Gemini Pro)**을 사용하여 고품질 Imagen 3 이미지를 자동으로 제작·다운로드하여 프로젝트에 반입한다.
   - **도구 우선순위 (2026-11-11 사용자 알림, 2026-11-12 시험 반영)**: 이미지는 Google AI Studio(워터마크 없음), 영상은 AI Studio의 Omni 1.2 Flash(눈에 보이는 워터마크 없음 확인), 배경음악(BGM)은 **AI Studio의 `Lyria 3.5` (`new_music?model=lyria-3.5`) 1순위**(무료·192kbps·오디오 워터마크 없음 확인), 효과음·음악 비디오·프롬프트 참고는 `flowmusic.app`(2순위, **하루 무료 크레딧 안에서만 무료** — 크레딧이 떨어지면 다음 날로 넘기며 커뮤니티 피드 인기작 프롬프트 참고). `gemini.google.com`은 첫 장 이후 워터마크가 찍혀(EP24 두 번째 쇼츠 썸네일에서 확인) AI Studio 자동화가 준비되기 전까지만 쓴다. 상세 표: `AGENTS.md` 이미지 생성 2단계 원칙.


## TTS

- TTS 기본 보이스: **남성 `Gero`**, **여성 `Olin`**을 채널 공식 표준으로 사용한다 (2026-11-09 사용자 결정. 이전 Charon에서 변경). 언어 `ko-KR`, 최신 모델 `gemini-3.8-flash-tts`.
- 쇼츠는 자연 발화보다 약간 빠르게 하되 설명은 또렷하게 한다.
- 퀴즈의 질문 나레이션에는 화면에 제시된 영어 단어의 **정답 발음이나 정답 단어를 절대 넣지 않는다**. 영어 철자는 화면으로만 보여주고, 음성은 `첫 번째 단어입니다. 어떻게 읽을까요?`처럼 문제 순서와 질문만 말한다.
- 퀴즈는 `정답이 포함되지 않은 질문 → 1.2~1.6초 생각 시간 → 정답 발음 공개 → 원리 설명` 순서를 지킨다.
- 대본 검수 때 화면 문구를 보지 않고 질문 음성 문장만 따로 읽어도 정답을 추론하거나 들을 수 없는지 확인한다.
- 무료 한도를 넘는 호출은 비용 견적과 사용자 승인 없이 실행하지 않는다.
- TTS는 익숙한 영어 발음을 자동 교정할 수 있으므로 오답 예시는 반드시 실제 청취한다.
- `커머시알`은 `커머. 시. 알?`처럼 문장 경계로 분리해야 자동으로 `커머셜`이 되는 것을 막을 수 있었다.
- 음성을 교체하면 해당 `.whisper-scratch` 캐시를 삭제한 뒤 다시 전사한다.
- Whisper 전사문은 발음 판정의 최종 근거가 아니다. 실제 청취가 우선이다.
- 벌거벗은 영어 접미사/조각(`TION`/`TURE`/`IC`/`SION`뿐 아니라 `-ate`처럼 하이픈 붙은 조각도 동일 계열
  버그다)이 한글 조사에 바로 붙으면 `narration-lint.mjs`의 하드코딩 패턴에 안 걸려도 오발음 위험이
  있다 — "소리"/"철자" 같은 완충 명사를 조각과 조사 사이에 끼워 넣을 것(EP19 Frame 3/7/11, `-ate에`→
  `-ate 소리에`, `-ate로`→`-ate 철자로`).
- **SCRIPT.md를 사람이 직접 고친 뒤, 그 파일을 실측 타임스탬프 반영 등으로 재생성하는 스크립트가
  나중에 다시 돌면 그 수정이 조용히 원상복구될 수 있다**(EP19에서 실제 발생 — narration 문단과
  `caption-pill` 불릿 양쪽 모두 원본으로 되돌아갔었음, 나레이션 문단과 캡션 불릿 두 군데가 같은
  문장을 중복 보관하므로 둘 다 확인해야 함). TTS를 이미 생성했다면 `scripts/gen-tts-*.mjs`의
  `LINES` 배열이 "실제로 음성이 된 문장"의 확정본이다 — SCRIPT.md와 이 배열이 어긋나 보이면
  배열 쪽을 정답으로 놓고 SCRIPT.md를 맞춘다(반대로 하면 이미 만든 음성과 문서 텍스트가 서로
  달라진다). STORYBOARD.md/frame.md를 쓰기 전에 SCRIPT.md가 최신 검수 반영본인지 다시 확인할 것.
- **`caption-pill`(하단 자막 알약 배경) CSS에 `white-space: nowrap`을 쓰면 긴 나레이션 문장이
  화면 밖으로 흘러넘친다**(2026-09-22 EP20에서 12개 프레임 전체 발견 — 자막이 짧은 문구가
  아니라 실제 완결된 나레이션 문장이라 40~90자짜리도 흔한데, `nowrap`+`overflow: visible`+
  `max-width` 조합이면 max-width를 넘는 순간 줄바꿈 없이 그대로 삐져나온다). `hyperframes check`
  레이아웃 검사가 이 패턴을 못 잡으므로 자동 검수 통과를 믿지 말 것. 새 프레임 작성 시
  `.caption-line`류 자막 pill에는 `white-space: nowrap`을 넣지 말고(줄바꿈 허용), 2줄이 돼도
  자연스럽도록 `border-radius`는 100px급 완전 캡슐이 아니라 32~40px 정도로 잡을 것.
- **나레이션 첫 단어 상투적 클리셰('솔직히') 남발 금지 및 핵심 목적격 조사('을/를') 필수 표기 원칙 (2026-10-09 확정)**:
  - 영문 첫머리 방지용 순수 한국어로 시작할 때, 매 에피소드마다 기계적으로 `솔직히`를 첫 단어로 박아넣는 행위를 엄격히 금지한다 (시청자에게 판에 박힌 AI 공식 대본 티를 냄). 상황에 맞는 다양한 자연스러운 첫머리(`학창 시절에...`, `영어 단어를 보다 보면...`, `우리가 흔히...`, `혹시...`, `분명히...` 등)를 활용한다.
  - 실시간 오디오 청취 환경에서 문장 인지 부하를 줄이기 위해, 핵심 캐치프레이즈나 술어부의 목적격 조사를 절대 생략하지 않고 명확하게 발음하도록 작성한다 (예: ❌ `귀 뚫어 드리겠습니다` ➔ ⭕ `귀를 뚫어 드리겠습니다`).

## HyperFrames 제작 기준

- **프레임마다 홀드/이동, 밀도(density), 여백(silence) 배분을 다르게 줘서 단조로움을 피한다**
  (2026-09-06, 롱폼 포함 전 포맷 공통 — 기존엔 `production-rules.md`의 "쇼츠 화면" 절에만
  비슷한 문장이 있었고 롱폼엔 명시된 적이 없었다). 완전히 다른 색·폰트·화풍(예: 손그림 스타일
  카탈로그 부품)을 중간에 섞어서 "지루함"을 없애려 하지 않는다 — 채널 아바타 인트로 클립을
  EP12에 넣으려다 "그래픽 타이포 씬 ↔ 실사 인물 화면 사이의 시각적 이질감 자체가 문제"라서
  보류했던 전례가 있다(`knowledge/decisions/2026-09-03-avatar-intro-clip-setup.md`). 대신
  **같은 색·타이포 시스템 안에서** 씬마다 정지 구간 vs 활발한 구간, 카드 밀도, 색 강조 타이밍을
  의식적으로 다르게 설계한다(EP13 `frame.md`의 "Frame Treatments" 표가 이 원칙을 프레임별로
  구체화한 예시 — 매번 이렇게 표를 만들 것).
- HyperFrames 프로젝트 폴더의 HTML·자산·타임라인은 하나의 동일한 원본이다. Studio에서 한 편집도 같은 소스에 반영되므로 별도 복사본으로 취급하지 않는다.
- 나레이션 영상은 `BRIEF.md`(목적), `STORYBOARD.md`(장면 순서), `SCRIPT.md`(확정 원고), `frame.md`(시각 기준), `index.html`/`compositions/`(실제 결과)를 함께 둔다.
- 승인된 구조에서만 제목·단어·색 등 반복되는 항목을 변수로 만든다. 디자인 검증 전에는 무리하게 공용화하지 않는다.
- 최종에 필요한 음성·이미지·영상·폰트는 반드시 프로젝트 내부에 복사하고, 원본과 가공본은 이름으로 구분한다. 임시 URL·브라우저 세션·렌더 시점 네트워크 파일은 쓰지 않는다.
- **영상 내 시각적 도파민을 위한 일러스트 적극 생성 및 역할 분담 (2026-09-20 확정, 로컬 ComfyUI는 2026-11-12 삭제)**: 상황 설명 일러스트, 비유 컷, 사물 오브젝트 등 시각적 도파민을 채울 수 있는 모든 구간에는 웹 Gemini·Google Flow·Imagen 등 AI 이미지 도구로 이미지를 생성해 배치한다(로컬 ComfyUI/SD 파이프라인은 2026-11-12 코드·PC에서 전부 삭제됨). 코드로 텍스트 카드만 띄우거나 빈 화면을 때우지 않고, 일러스트(시각적 실체) 위에 스톱모션 및 코드 모션(동적 생명력)을 결합하여 생동감을 구현한다.
- **캐릭터 일관성 기준 (2026-09-20 확정, 2026-10-28 아바타 중단)**: 2026-10-28 결정에 따라 신규 영상에서는 아바타를 쓰지 않고 단어 비교 카드·소리 인포그래픽·타이포그래피로 제작한다. 옛 영상 재작업 시에는 Google Flow(Ingredients 기준 이미지) 방식으로 캐릭터 일관성을 유지한다(기존 로컬 ComfyUI Img2Img / IP-Adapter / OpenPose / LoRA 스크립트는 2026-11-12 삭제).
  **Google Flow(Ingredients 기준 이미지) 방식으로 캐릭터 프롬프트를 쓸 때, 머리카락 길이처럼
  수염(FACIAL HAIR)도 명시적으로 "고정"이라고 못 박지 않으면 컷마다 수염 모양·유무가
  제멋대로 바뀐다**(2026-09-22 EP20 Frame 2 프롬프트 작성 중 사용자 발견). 기준 이미지만
  믿지 말고, 공통 캐릭터 묘사 문단에 모자/후드티/머리길이와 동일한 수준으로 "FACIAL HAIR
  (strict, do not deviate): 정확히 어떤 수염 스타일(길이·숱)"을 명시하고, NEGATIVE 문단에도
  "clean-shaven, no facial hair, different beard style" 등을 넣을 것. 상세 예시:
  `videos/ep20-world-rl/prompts/frame01-image-prompts.md`·`frame02-image-prompts.md`.
- **구강 단면·해부도 등 복잡한 일러스트는 코드로 무리하게 그리지 말고 AI 이미지 생성으로 제작해 프레임에 넣는다**(2026-09-18 확정, 사용자 지침) — 구강 단면도, 복잡한 인체 부위, 정밀한 손그림 일러스트처럼 시각적 완성도와 자연스러움이 핵심인 그래픽은 SVG `<path>`나 CSS 도형으로 수십~수백 줄을 어설프게 직접 짜려고 하지 않는다(부자연스럽고 시간 소모가 큼). 채널 톤(스케치노트, 따뜻한 파스텔 톤, 클린 라인)에 맞춰 AI 이미지 생성 도구(`generate_image` / Imagen 등)로 고품질 그래픽 이미지를 먼저 생성한 뒤(`assets/images/`에 저장), 프레임 컴포지션에 `<img>`로 배치하고 그 위에 화살표·콜아웃 뱃지·하이라이트 등 동적 요소만 오버레이하여 애니메이션한다.
- **연음·탄설음처럼 "자음+모음이 만나서 소리가 붙는" 규칙을 설명하는 프레임엔 글자 단위
  자음(자)/모음(모)/무음 라벨을 화면에 같이 표시한다**(2026-09-07 확정, EP14에서 처음 적용).
  초보 학습자는 어떤 철자가 자음·모음인지 한눈에 안 보이는 경우가 많아서(예: MADE의 마지막
  글자는 E지만 무음이라 실제 마지막 소리는 D), 라벨 없이 말로만 설명하면 어떤 글자가 실제로
  붙는 소리인지 헷갈릴 수 있다 — 실제로 EP14 대본 검수 중 "T가 모음 사이에 끼면"이라는 설명이
  MADE IT에는 안 맞는 오류(진짜로 붙는 건 IT의 T가 아니라 MADE의 D)를 사용자가 잡아낸 뒤 나온
  아이디어. **적용 조건**: 예문이 실제로 단일 글자 단위 자음+모음 구조일 때만 라벨링한다(예:
  AN APPLE, MADE IT, GET IT) — WHERE WE처럼 뒷단어가 자음으로 시작해 다른 현상(약화/reduction
  등)이 작동하는 경우는 억지로 라벨을 붙이지 말고 그 현상에 맞는 별도 시각 표현을 쓴다. 상세
  예시: `videos/ep14-connected-speech/SCRIPT.md` Frame 5·7·8·10의 화면 노트.
- **화면 문구가 도중에 바뀌는 연출(자막 절 교체, 정답 공개 등)은 `tl.call()`로 `textContent`를
  한 번에 바꾸지 말고, 같은 자리에 겹친 두 엘리먼트를 opacity로 크로스페이드한다**(2026-09-08
  확정, EP14 Frame 5에서 발견). `tl.call()`은 순방향 재생에서는 문제없이 보이지만, **Studio
  미리보기에서 사용자가 뒤로 스크럽하면 글자가 안 돌아간다** — GSAP 트윈(opacity/scale/color
  등)은 시간의 함수라 어느 방향으로 시간을 옮겨도 항상 그 시점에 맞는 값을 다시 계산하지만,
  `.call()`은 한 번 실행되는 일반 스크립트라 "되돌리는 법"이 없다. 실제로 사용자가 재생 중
  뒤로 돌렸다가 "N이 아직 안 넘어갔는데 병합된 발음 글자가 떠 있다"고 착각한 사례가 있었다 —
  독립적으로 그 시각을 다시 찍어보면 재현이 안 돼서 처음엔 원인 파악이 어려웠다(스냅샷 도구는
  매번 새로 열어서 한 번만 찾아가므로, "정방향 재생 후 되감기"라는 스크럽 고유의 상태를 애초에
  안 만든다). **색상·크기 등 스타일만 바뀌고 텍스트 자체는 안 바뀌는 경우**엔 이 문제가 없다 —
  GSAP가 직접 관리하는 CSS 속성 트윈은 원래도 스크럽 안전하므로, `.call()`로 `el.style.xxx`를
  건드리던 것도 똑같이 `tl.to()`/`tl.fromTo()` 트윈으로 바꾸면 된다(텍스트 자체를 바꿀 때만
  두 엘리먼트 크로스페이드가 필요). 폰트 크기를 트윈할 땐 `fontSize` 대신 `scale`을 쓸 것 —
  `fontSize` 트윈은 텍스트 리플로우 때문에 정수 픽셀에 스냅되어 스크럽 시 끊겨 보인다고
  `npm run check`의 GSAP 린터가 잡아준다.
- **GSAP `fromTo`는 시작값과 끝값에 같은 속성을 모두 적는다**(2026-11-09 확정, EP25 쇼츠).
  `tl.fromTo(el, {scaleX: 0, opacity: 1}, {scaleX: 1})`처럼 `opacity`를 시작값에만 넣으면, 처음부터
  앞으로만 재생할 때는 멀쩡하지만 렌더러·스냅샷 도구가 영상 끝까지 한 번 갔다가 되돌아오면 그 요소가
  투명한 채로 남는다. EP25 쇼츠에서 첫 칸(pool)이 뒤집힌 뒤 계속 빈칸으로 나왔고, 일반 브라우저로
  열어 보면 재현되지 않아 찾기 어려웠다(끝으로 갔다 돌아오는 순서로 재생해야 재현됨). 보이게 만드는
  것만 따로 필요하면 `tl.set(el, {opacity: 1}, 시각)`을 쓴다. 새 프레임을 짠 뒤 `grep -n "fromTo"`로
  시작값에만 있는 속성이 없는지 본다.
- **퀴즈에서 글자를 가림판으로 덮을 때는 그 글자 자체도 정답 전까지 숨긴다**(2026-11-09 확정, EP26
  쇼츠). 글자 안에 배경색 상자(`l`의 하늘색 강조 등)가 있으면 상자가 가림판 위아래로 삐져나와 답이
  비친다. EP26 쇼츠 첫 렌더에서 하늘색 조각이 보여 다시 렌더했다. 가림판을 벗기기 직전에
  `tl.set(글자, {opacity: 1})`로 보이게 한다.
- **한 프레임에서 발견된 레이아웃·타이밍 버그는 같은 템플릿으로 만든 다른 프레임에도 거의
  확실히 반복돼 있다 — 지적받은 그 프레임만 고치고 끝내지 말 것**(2026-09-09 확정, EP14에서
  실제로 겪음). Frame 5의 "자막이 화면 위쪽에 고정돼 있고 나머지가 텅 빈" 버그(나중에 나올
  콘텐츠 자리를 피하려 위로 붙여놨는데, 실제로는 그 콘텐츠가 나오기 전에 자막이 이미 다 사라져서
  피할 필요가 없었던 경우)를 사용자 지적으로 고친 뒤, 정작 사용자가 **다른 시점 스크린샷 여러
  장**을 보여주며 "이것들의 문제는?"이라고 물어서 확인해보니 Frame 6·7·9·10에 **완전히 같은
  버그**가 그대로 남아 있었다 — 여러 프레임을 같은 캡션 템플릿을 복사해서 만들다 보니 같은
  실수가 그대로 번진 것. **대응**: 프레임 하나의 레이아웃/타이밍 버그를 고치고 나면, 곧바로
  `grep`으로 같은 CSS 패턴(예: 특정 `top:Ncqh` 값, 같은 클래스 이름 접두사)을 전체 프레임
  파일에서 검색해서 다른 프레임에도 있는지 먼저 확인한 뒤 사용자에게 보고할 것 — 사용자가 매번
  스크린샷을 여러 장 찍어서 하나씩 알려주게 만들지 않는다. 단, 겉보기엔 같은 패턴이라도 **프레임마다
  겹침 여부는 다를 수 있으니 반드시 개별적으로 타이밍을 재확인**할 것(EP14 Frame 10의
  `.f10-prompt`는 같은 `top:` 위치를 썼지만 다이어그램과 의도적으로 동시에 떠 있는 정상
  케이스였음 — 기계적으로 똑같이 고치면 새 버그가 생겼을 것).

## HyperFrames 워크플로 선택

### 기본 원칙

- 워크플로는 화면 스타일이 아니라 **입력과 제작 목적**으로 고른다. 먼저 맞는 전용 워크플로가 있는지 확인하고, 없을 때만 `General Video`를 쓴다.
- 새 대본으로 만드는 영어 교육 영상은 기본적으로 `Faceless Explainer`다. 실제 촬영 영상이 없고, 초보자가 하나의 발음 원리를 이해하도록 타이포그래피·도식·예시를 새로 구성하는 현재 채널의 정상 제작에 가장 맞는다.
- 이미 만든 음성·참고 디자인·여러 자산을 조합해 구조를 직접 설계하는 실험 또는 맞춤형 편집은 `General Video`로 만든다. EP8 Softboard 테스트가 이 경우다.
- 한 번 선택한 워크플로는 결과와 무관하게 고집하지 않는다. 입력 조건이 바뀌면 아래 표로 다시 판정하고, 변경 이유를 해당 에피소드 문서에 남긴다.

| 입력·목적 | 기본 워크플로 | 우리 채널에서의 사용 |
|---|---|---|
| 확정 대본 또는 주제, 실제 촬영 영상 없음, 한 가지 원리를 설명 | `Faceless Explainer` | 새 롱폼과 새 쇼츠의 기본. 대본 → 스토리보드 → 그래픽·도식·자막·음성 순으로 제작 |
| 기존 내레이션·참고 이미지·복수 자산을 조합하거나, 장면 구조를 직접 실험 | `General Video` | Softboard 같은 설명 장면 실험, 기존 영상 재구성, 전용 시퀀스 |
| 3~10초짜리 독립 그래픽, 나레이션 없음 | `Motion Graphics` | 인트로 스팅, 퀴즈 정답 공개, 규칙 임팩트, CTA 전환용 부품. 본편 전체에는 사용하지 않음 |
| 실제 토킹헤드 영상은 그대로 두고 자막만 추가 | `Embedded Captions` | 향후 사람 출연 영상에만 사용 |
| 실제 토킹헤드 영상에 발화 동기 그래픽을 추가 | `Talking-head Recut` | 향후 사람 출연 영상을 바꾸지 않고 보강할 때만 사용 |
| 음악의 박자가 영상 구조를 결정 | `Music-to-Video` | 음악 중심 오프닝·브랜드 영상처럼 예외적인 경우만 사용 |
| 웹사이트·앱 화면을 소개 | `Product Launch Video` | 채널 교육 영상에는 기본적으로 해당 없음 |
| 리더십·내부 검토용 클릭형 자료 | `Slideshow` | MP4가 아니라 탐색형 발표 자료가 필요할 때만 사용 |
| GitHub PR 변경 내용을 설명 | `PR to Video` | 채널 제작과 무관; 개발 공유에만 사용 |

### 제작 요청에 반드시 확정할 항목

새 영상 요청은 아래 여섯 가지를 짧게 확정해 `BRIEF.md`에 남긴다. 다음 작업자는 채팅을 다시 읽지 않고 이 문서에서 재개한다.

1. 시청자와 한 편을 본 뒤 얻어야 할 한 가지 이해
2. 플랫폼·비율·목표 길이(롱폼 16:9 / 쇼츠 9:16)
3. 대본 상태(초안 또는 확정), 실제 음성을 반드시 유지해야 하는지
4. 제공 자산과 수정 금지 자산
5. 화면 리듬·모션 톤, 피해야 할 표현·효과
6. 두 장면 이상이면 스토리보드를 먼저 검토할지, 자동 제작으로 바로 초안을 만들지

### 검수와 반복

- 미리보기를 켠 상태에서 작은 수정 단위로 반복한다. 미리보기 없는 수정은 결과를 보지 못한 추측이다.
- 렌더 전 `lint`와 `check`를 모두 통과해야 한다. `check`는 런타임 오류, 넘침, 충돌, 모션, 대비를 검사하므로 생략하지 않는다.
- `Motion Graphics`로 만든 짧은 부품도 본편에 넣기 전 실제 나레이션·자막·전환과 함께 재생해 타이밍을 확인한다.

## 미디어·음성·자막

- 미디어마다 역할을 하나만 둔다: 음성은 설명, 이미지는 한 개념의 이해, 음악은 리듬, 효과음은 의미 있는 행동 보강이다. 역할이 겹치면 더 분명한 하나를 남긴다.
- 영상과 자막은 실제 음성 전사와 동기화한다. 자동 전사 뒤 고유 단어·철자·한글 발음·문장 구분을 반드시 확인한다.
- 내레이션이 중심인 영상은 실제 발화 타이밍에 화면을 맞춘다. 추정 씬 길이에 화면을 억지로 맞추지 않는다.
- 음악은 음성 아래에 두고, 효과음은 질문·정답·핵심 연결처럼 의미 있는 순간에만 쓴다. 침묵은 필요하면 그대로 둔다.
- **이미 생성된 TTS 문장에서 단어 일부만 잘라내는 건 클릭음은 막을 수 있어도 억양까지는 못
  고친다**(2026-09-10, EP15 Frame 8·11 사례). whisper 단어 타임스탬프로 특정 구간만 정밀 삭제
  하고 크로스페이드까지 넣어도, 그 문장 전체가 원래 그 단어가 있는 채로 한 호흡에 생성됐다면
  남은 부분의 억양 곡선이 미묘하게 안 맞아 어색하게 들릴 수 있다(실제로 사용자가 듣고 "어색하다"
  고 판단해 재생성으로 전환한 사례). **문구 자체를 바꿨다면, 특히 재생성 비용이 적을 때는(이
  경우 두 프레임 합쳐 ₩61) 오디오 편집보다 새로 생성하는 쪽을 먼저 시도할 것** — 오디오 트림은
  "텍스트는 그대로인데 순수 편집상 필요"(예: 무음 구간 다듬기)에는 여전히 유효하지만, 문장
  구조 자체가 바뀌는 수정에는 재생성이 더 안전하다.
- **배경음악(BGM) 선곡 기준(2026-09-06)**: 지루하게 늘어지지 않도록, **약간 템포가 빠르고
  집중력을 높여주는 느낌의 트랙**을 고른다(축 처지는 잔잔한 무드 음악보다, 시청자가 계속 집중해서
  따라오게 만드는 쪽). 다만 나레이션보다 시끄러워지면 안 되므로 볼륨은 기존 규칙대로 음성 아래에
  두고, `hyperframes-audio` 더킹(아래 참고)으로 나레이션 구간에서 더 낮춘다.
- **BGM 기본 볼륨(2026-09-07, EP13 실측 확정)**: `data-volume="0.06"`(더킹과는 별개로 적용되는
  베이스 볼륨). 처음엔 EP12를 따라 `0.12`로 시작했는데, 실제로 들어보니 여전히 크다는 피드백을
  받아 절반인 `0.06`으로 낮췄다 — **다음 영상도 이 값에서 시작하고, 곡 자체 음량이 유난히 크거나
  작으면 거기서 미세 조정**할 것(무조건 0.12부터 다시 시작하지 않는다).
- **BGM 제작 방식 — 루트에 하나, 12개 나레이션을 한꺼번에 분석해 더킹(2026-09-11 확정,
  2026-09-07의 "프레임별 슬라이스" 방식을 대체)**: 이전엔 나레이션 `<audio>`가 각 프레임
  파일 안에 개별로 들어있다는 이유로 BGM도 프레임마다 잘라 넣고 carve.mjs를 12번 따로
  돌렸는데, **이 방식 자체가 근본적으로 잘못됐었다** — carve.mjs는 매 실행마다 더킹
  곡선을 그 파일의 `t:0`에서 "안 눌림" 상태로 새로 시작시키기 때문에, 프레임 경계마다
  실제로는 하나로 이어져야 할 곡이 인위적으로 12번 리셋되는 꼴이었다. 나레이션이 프레임
  끝까지 거의 여백 없이 이어지는 이 채널 대본 특성상 그 리셋이 컷마다 음량·톤이 훅 튀는
  걸로 들렸다(2026-09-11, EP15 사용자 지적: "배경음악 프레임 넘어갈 때 앞 프레임 구간
  bgm과 연결이 안되고 다른 끊이는 느낌남" → "각 프레임으로 짜르는게 아니고 쭉 이어지다가
  bgm이 끝나면 bgm 다시 넣고 하는게 맞지 않을까?"). 처음엔 각 프레임의 꼬리만 0으로
  강제로 되돌리는 패치 스크립트로 땜질했었지만, 근본 원인(애초에 왜 12조각으로
  나눴는가)을 사용자가 다시 짚어줘서 구조 자체를 고쳤다. **새 방식**:
  1. `media-use` `resolve.mjs`(신곡 리졸브 시) 또는 로컬 BGM 라이브러리 파일을 골라서
     `assets/bgm/`에 놓는다. 곡 길이가 영상 전체 길이보다 짧으면 ffmpeg `-stream_loop`으로
     영상 총 길이만큼(+여유분) 반복해 **하나의 파일**(`track.loop.mp3`)로 만든다.
  2. **`index.html`(루트)에 BGM `<audio>`를 딱 하나만 둔다** — `data-start="0"`,
     `data-duration`은 영상 전체 길이, `data-media-start="0"`. 프레임별 사본은 만들지
     않는다(12개 서브 컴포지션 파일에는 BGM을 아예 두지 않음 — 루트와 프레임 양쪽에 다
     두면 EP13에서 실제로 겪은 것처럼 두 배로 겹쳐 들리는 버그가 난다).
  3. 나레이션 더킹은 `hyperframes-audio` 스킬의 `carve.mjs`를 **딱 한 번**, 루트
     `index.html`에 대해 실행한다 — 단, carve.mjs는 bgm과 voiceover가 **같은 파일 안에**
     있어야 관계를 분석하므로, 실제 나레이션은 프레임별 서브 컴포지션 안에 있는 채로 두고,
     **루트 파일에 임시로** 12개 나레이션 wav를 각자의 전체 영상 기준 시작 시각에
     `data-audio-group="voiceover"`로 걸어서 잠깐 추가한다(예: `<audio id="carve-voice-05"
     src="assets/voice/05.wav" data-start="101" data-audio-group="voiceover"></audio>`).
     `hyperframes-audio` 스킬 자체가 "한 bed 아래 여러 voice를 그룹으로 묶어 한 번에
     분석"하는 걸 정확히 이 용도로 지원한다(스킬 문서 "Every voice, not one of them" 절) —
     `carve.mjs --comp index.html`을 돌리면 bed(bgm)와 12개 voice를 자동으로 찾아 **하나의
     연속된 더킹 곡선**(EP15 기준 310개 포인트, 0~400초 연속)을 bgm 엘리먼트에 써준다.
     실행 후 **임시로 추가했던 12개 나레이션 엘리먼트는 반드시 지운다** — 실제 나레이션
     재생은 여전히 각 프레임 서브 컴포지션이 담당하므로, 루트에 남겨두면 이중 재생된다.
     (`@hyperframes/core`가 프로젝트에 devDependency로 설치돼 있어야 동작 —
     `npm i -D @hyperframes/core@^<hyperframes 핀 버전>`.)
  4. BGM 소스(곡)를 나중에 바꾸거나 나레이션을 재생성하면, 루트에 12개 임시 voice
     엘리먼트를 다시 추가해 carve.mjs를 재실행해야 한다 — 더킹 EQ·곡선은 그 시점의 실제
     오디오를 분석해서 만들어지므로 무효가 된다.
  5. 검증: 옛 프레임 경계였던 시각 근처(예: 39.88s)에서 `data-automation`의 `fx.n4.gain`
     레인 포인트를 뽑아, 그 지점에서 값이 리셋되지 않고 자연스럽게 이어지는지 확인한다
     (`node -e`로 JSON 파싱해서 특정 구간 포인트를 찍어보면 빠르다).
- **AI 생성 B롤에 워터마크가 찍혀 나올 수 있다(2026-09-08, EP14 확인)**: 프롬프트에 "no
  watermark"를 명시해도 도구(Veo 등)가 프레임 구석에 작은 로고성 아이콘을 고정 위치로 새겨
  넣는 경우가 있다. 발견 방법: ffmpeg로 여러 시점 프레임을 추출해 같은 좌표를 크롭해서
  겹쳐 보면(콘택트시트) 워터마크가 전체 구간에서 **완전히 고정된 픽셀 위치**에 있는지 확인
  가능(진짜 콘텐츠는 움직이지만 워터마크는 안 움직임). 고치는 법: (1) 자동 픽셀 감지(밝기+
  채도 임계값)는 피부톤·그림자에 오탐이 잦으므로 신뢰하지 말 것 — 대신 여러 시점을 같은
  좌표로 크롭해 눈으로 정확한 바운딩 박스를 잡는다. (2) 그 박스에 배경색으로
  `drawbox=t=fill`을 씌우기 **전에**, 인물(턱선·목선 등)이 전체 구간 어느 시점에도 그
  영역을 침범하지 않는지 여러 시점 콘택트시트로 먼저 확인한다(침범하면 paint-over가 아니라
  crop으로 가야 함). (3) 배경색 상수(`#0A1526`)를 그대로 채우면 실제 배경의 비네팅/그레인
  때문에 사각형 경계가 옅게 티 날 수 있다 — `drawbox`로 채운 뒤 그 영역(여유를 둔 더 큰
  범위)에 `gblur`를 한 번 더 씌워 경계를 배경에 자연스럽게 녹인다(ffmpeg
  `filter_complex`로 crop→gblur→overlay 체인). 검증은 줌 크롭과 실제 크기(줌 없이 풀프레임)
  둘 다로 한다 — 줌에서 안 보여도 실제 재생 크기에서 티 나거나, 반대로 실제 크기에서 안
  보여도 줌에서 아직 경계가 남아있을 수 있다.
- **효과음(SFX) 선정 기준(2026-09-06)**: 흔한 "띵동" 알림음이나 게임 효과음 느낌이 아니라,
  **고급스럽고 절제된 톤의 효과음**을 고른다(예: 부드러운 chime, 은은한 whoosh — EP11/EP12에서
  이미 쓴 라이브러리 안에서 고르되, 자극적이거나 유치하게 들리는 후보는 거른다).
- 최종 검수는 소리 켠 전체 재생과 무음 재생을 각각 한 번씩 한다. 전자는 발음·믹스·타이밍, 후자는 자막·시각적 이해를 확인한다.

## 실사·아바타·후처리

- 아바타는 사람이 화면에서 설명해야 할 때만 사용한다. 현재 채널의 기본 형식은 그래픽+나레이션이며, 아바타는 기본값이 아니다.
- 사람 실사나 아바타를 디자인 위에 올려야 할 때만 배경 제거를 검토한다. 투명 결과는 프로젝트에 보관하고 머리카락·손·빠른 움직임·처음/끝 프레임을 검수한다.
- 색보정과 미디어 효과는 이미지·영상 레이어에만 비파괴적으로 적용한다. 자막·일반 HTML 그래픽을 포함한 전체 화면에 일괄 적용하지 않는다.
- 보정은 노출·화이트밸런스·대비를 먼저 맞춘 뒤 스타일을 더한다. 글리치·CRT·ASCII 같은 강한 효과는 학습 내용을 돕는 명확한 이유가 있을 때만 사용한다.

- 스틸 검수는 배치·넘침 확인용이다.

### 렌더 마지막 5초는 유튜브 엔드스크린을 위해 화면 중앙을 통째로 비워둔다 (2026-09-07 확정, 2026-09-11 5초·전체중앙비움으로 확장)

위 규칙이 "유튜브 Studio에서 어떤 영상을 연결할지"라면, 이건 그 엔드스크린 UI가 실제로 겹쳐
뜰 **화면 자체를 미리 비워두는** 규칙이다 — 레거시 Remotion 파이프라인(`CLAUDE.md`의 "엔드스크린
Scene 규칙")에 있던 개념을 HyperFrames 영상(EP11부터)에도 적용한다.

- **마지막 씬의 끝 7~10초 구간은 콘텐츠를 최소화한다** — 카드·글자 카드·진행 점 같은 요소를 새로
  등장시키지 않고, 채널 워드마크 정도만 남긴 채 차분하게 정리한다. 이 7~10초 동안 유튜브가 화면
  위에 자기 엔드스크린 UI(구독 버튼, 다음 영상 카드)를 덮어씌우기 때문에, 그 밑에 뭘 그려도
  가려져서 안 보인다 — 헛수고가 아니라 아예 시청자를 방해하는 요소가 된다. (기존 3초에서
  2026-09-11 EP15 제작 중 사용자 요청으로 5초로 확장 — 엔드스크린이 화면에 자리 잡는 데
  3초는 너무 빠듯하다는 판단.)
- **문서화된 두 사각형(아래 표)만 피하는 걸로는 부족하다 — 이 7~10초 동안은 화면 중앙 전체를
  비워야 한다.** 채널 워드마크 같은 상시 마무리 요소도 **가운데에 두지 않고 좌상단 같은
  안전한 모서리로 옮긴다**(2026-09-11 확정 — EP14 Frame 12를 2026-09-08에 이렇게 고친 전례가
  있었는데 그때는 그 파일의 코드 주석에만 남고 이 문서로 승격되지 않아서, EP15를 처음 만들 때
  다시 가운데 배치로 되돌아갔던 실수가 있었다. 이번에 문서로 승격해 재발을 막는다). 이유:
  사용자가 유튜브 Studio에서 실제로 배치하는 구독 버튼·추천 영상/재생목록 카드 같은
  엔드스크린 요소가 화면 중앙 쪽에 오는 경우가 많아서, 우리 쪽 워드마크를 가운데 두면 그
  요소들과 겹쳐 경쟁하게 된다. 두 사각형 키프아웃은 **최소 요구사항**이지, 그 밖의 자리라면
  뭘 둬도 된다는 뜻이 아니다.

  | 영역(문서화된 최소 키프아웃) | 좌표 | 크기 |
  |---|---|---|
  | 우측 하단 | x 1620~1920, y 910~1080 | 300x170 |
  | 중앙 상단 | x 810~1110, y 0~170 | 300x170 |

  실제 적용 기준(EP14·EP15 공통): 워드마크는 좌상단(`left:6cqw; top:8cqh`, Noto Sans KR
  900 weight, 1.1cqw, letter-spacing 0.04em)에 작게 배치 — 두 키프아웃 사각형도 당연히
  피하고, 화면 중앙도 비워서 유튜브 UI에 자리를 내준다.
- **검증은 스틸/스냅샷으로 픽셀 단위로 한다** — 두 사각형 안에 실제로 아무것도 없는지, 그리고
  중앙이 실제로 비어 있는지 눈대중이 아니라 렌더된 프레임을 직접 확인한다(`hyperframes
  snapshot . --at <시각> --zoom "x,y,w,h"`로 키프아웃 영역만 잘라서 보면 빠르다).
- EP13까지는 이 규칙 이전에 이미 렌더가 끝나서 소급 적용하지 않는다. **EP14부터 새 규칙으로
  적용** — 각 프로젝트의 마지막 프레임(예: `12-summary.html`류) 스토리보드·구현 단계에서
  이 7~10초 구간을 명시적으로 설계할 것.
- **⚠️ 상단 진행바(progress-rail)처럼 "모든 프레임에 상시 등장하는 공통 요소"도 빠뜨리기 쉽다**
  (EP14 Frame 12에서 실제로 발견 — 2026-09-08, EP15에서도 같은 실수가 처음엔 반복됐다가
  2026-09-11에 같이 수정). progress-rail은 화면 전체 폭(`width:100%`)이라 3px 두께로 중앙
  상단 키프아웃 영역을 그대로 관통한다. 다른 11개 프레임에선 상시 보여야 하는 요소라서
  "당연히 있는 것"으로 넘어가기 쉬운데, **영상 전체에서 마지막 7~10초에 해당하는 건 오직
  마지막(12번째) 프레임의 끝부분뿐**이므로 그 프레임의 진행바만 이 구간에서 별도로
  페이드아웃시켜야 한다. 마지막 프레임을 만들 때 체크리스트에 "진행바도 이 7~10초 동안 지웠는가"를
  포함할 것 — 카드·문구 같은 새로 추가한 요소만 확인하고 상시 요소는 놓치기 쉽다.

## 업로드 패키지 변경 완료 조건

- **대시보드 자동 예약 업로드 (2026-11-06)**: 재연동할 때 채널 선택 화면에서 "이해하면 쉬운 영어"를 고른다. 다른 채널을 고르면 연동을 저장하지 않는다. 새 메인 썸네일(`thumbnail.jpg`)을 넣은 뒤 대기 큐에서 "이 썸네일 승인"을 눌러야 올라간다. 파일을 바꾸면 승인이 풀린다. 실패하면 그 편에서 멈추고 화면에 이유와 다시 시도 버튼이 나온다. 대시보드 서버가 켜져 있을 때만 올라간다(5분마다 확인, PC를 켜도 서버는 자동으로 켜지지 않음). 올라간 영상의 공개는 유튜브가 하므로 그때는 PC가 꺼져 있어도 된다. 고정 댓글은 예약 영상에 달 수 없어(403) 공개 뒤 직접 등록하고 패널의 "등록함"을 누른다. 올라간 뒤 끝 화면, 재생목록, 댓글 고정, 제목·썸네일 테스트는 스튜디오에서 직접 한다.

- 제목, 설명, 태그, 고정 댓글, 썸네일 문구 또는 썸네일 파일이 바뀌면 원본 콘텐츠 JSON과 출력 패키지를 함께 갱신한다.

- 통합 요약 HTML은 제목·문구·설명·태그·고정 댓글·공개 설정을 항목별 버튼으로 복사할 수 있어야 한다.

- **롱폼은 다국어 자막·번역 메타데이터도 기본 산출물이다**(2026-09-18 확정, EP17부터 —
  사용자: "자막도 계속 만들꺼니깐"). 매 에피소드 업로드 패키지에 아래를 갖춘다:
  - **언어 세트(기본값)**: 한국어(기본) + 영어·일본어·스페인어·베트남어·중국어 번체·중국어
    간체 6개 글로벌 언어. EP17에서 확정된 조합 — 다른 언어가 채널 성과상 더 필요해지면
    이 목록 자체를 갱신하고 이유를 남긴다.
  - **파일 3종**(폴더명 고정, 대시보드가 이 이름을 그대로 찾는다):
    1. `subtitles/subtitles-<언어코드>.srt` — 언어 코드는 `multilingual-metadata.json`의
       키와 정확히 같아야 한다(예: `ko`/`en`/`ja`/`es`/`vi`/`zh-tw`/`zh-cn`).
    2. `multilingual-metadata.json` — `{ "<코드>": { "lang": "...", "title": "...",
       "desc": "..." }, ... }` 구조. **`lang` 필드는 "원어 표기 (한국어 설명)" 형식으로
       쓴다** — 앞부분(예: `English`, `日本語`, `繁體中文`)은 유튜브 Studio 언어 목록에
       실제로 뜨는 원어 그대로 남겨 매칭용으로 쓰고, 괄호 안은 반드시 한국어로 쓴다
       (예: `English (영어 · 미국)`, `繁體中文 (번체 중국어 · 대만/홍콩)`) — 처음에
       `(Traditional Chinese - 台灣/香港)`처럼 영문으로 넣었다가 "이게 뭔지 알 수가 없다"고
       사용자가 재지적해서 전량 한국어로 고친 전례가 있다. 새로 언어를 추가할 때도 이 형식을
       처음부터 지킨다.
    - **⚠️ `title` 필드는 언어별로 100자(문자 수 기준) 제한을 반드시 지킨다**(2026-10-02
      확정, EP21에서 영어·스페인어·베트남어 3개 언어 제목이 142~145자로 유튜브 한도를
      넘어선 채로 작성됐다가 사용자가 직접 발견해 지적함 — 한국어·일본어·중국어는 표의문자라
      같은 분량을 담아도 글자 수가 훨씬 짧게 나와 이 문제가 안 보였고, 그래서 서구 언어권만
      조용히 한도를 넘기기 쉽다). 한국어 원본 제목의 분위기(충격·반전 훅)를 그대로 다
      옮기려다 보면 로망스어·베트남어처럼 조사·어미가 긴 언어에서 특히 쉽게 넘는다.
      **`multilingual-metadata.json`을 작성/수정할 때마다 매번 아래로 전수 검사**한다:
      ```bash
      node -e 'const ml=require("./output/upload-packages/<slug>/multilingual-metadata.json");for(const[c,d]of Object.entries(ml))console.log(c,[...d.title].length)'
      ```
      100을 넘는 언어가 있으면 핵심 훅은 유지하되 문장을 압축해서 다시 쓴다(예: "~라고
      읽으셨다면, 사실 완벽하게 속으신 겁니다" 류의 이중 절은 한 언어 안에서 하나만 남기는
      식). 제목을 다 쓴 뒤 검사하지 말고, 쓰는 그 자리에서 바로 검사해 재작업 범위를 줄인다.
    3. `multilingual-guide.txt` — 사람이 유튜브 Studio에 그대로 복사 붙여넣을 수 있는
       안내문(언어별 제목/설명 전문 + 등록 순서).
  - **대시보드는 이미 이 3개 파일 이름/구조를 그대로 읽도록 코드가 짜여 있다**
    (`scripts/youtube-analytics-server.mjs`의 `getEpisodesSummary()` → `youtube.
    multilingualVariants`, `renderTrackDetail()`의 "🌍 다국어 자막 & 번역 메타데이터" 카드) —
    **파일명 규칙만 지키면 다음 에피소드부터는 서버·클라이언트 코드를 다시 고칠 필요가
    없다.** 새 언어를 추가할 때도 마찬가지로 자동 인식된다(EP17에서 중국어 2종을 나중에
    추가했을 때 코드 수정 없이 바로 반영된 것으로 확인). 국기 이모지 매핑
    (`{ko:'🇰🇷', en:'🇺🇸', ...}`)에 없는 새 언어 코드를 추가할 때만 그 매핑 한 줄 추가가
    필요하다.
  - `/api/upload-package-asset/`는 `subtitles/` 같은 하위 폴더 경로도 서빙 가능하도록
    확장돼 있다(2026-09-18) — 새 하위 폴더를 또 만들 때도 이 라우트를 그대로 쓸 수 있다.
- 롱폼과 모든 쇼츠 업로드 패키지 카드 상단에는 정확한 KST 예약 공개 일시를 크게 표시하고 복사할 수 있어야 한다.
- 예약 공개 5분 후 고정 댓글 알림을 사용한다. 다음 `업무시작` 때 미완료된 고정 댓글·고정 확인·영상 연결 작업을 다시 최우선으로 안내한다.

## 업로드 후 대시보드 자동 동기화가 안 될 때 (2026-09-20 근본 원인 3건 확정)

"유튜브에 업로드·예약하고 동기화를 눌러도 업로드 패키지 카드와 아이디어 카드 상태가 안 바뀐다"는
증상이 EP19에서 재발했다(사용자: "이거 자동으로 되게 만들어 몇 번이나 수정했는데 왜 같은 문제가
발생하지"). 예전 수정들은 전부 제목 매칭 로직의 곁가지(변형 시안 누락, `\r\n` 버그)만 고쳤을 뿐,
아래 세 가지 진짜 원인은 이번에 처음 밝혀졌다. 비슷한 증상이 또 나오면 **곁가지 매칭 로직부터
의심하지 말고 이 세 가지부터 확인할 것**:

1. **`search.list`는 비공개·예약 영상에 대해 근본적으로 신뢰할 수 없다** —
   `syncUploadPackageStatusFromYouTube`가 videoId를 모를 때 제목으로 찾으려고
   `youtube/v3/search?forMine=true`를 썼는데, 이 API는 구글 문서상 **소유자가 조회해도
   비공개/예약 영상을 색인 지연·누락으로 못 찾는 경우가 흔하다.** 제목 매칭 로직이 아무리
   완벽해도 애초에 검색 결과에 그 영상이 안 잡히면 영원히 실패한다. → `getDashboard()`가 이미
   쓰고 있어 신뢰성이 검증된 **채널 자신의 "업로드" 재생목록**(`channels.list`로
   `relatedPlaylists.uploads` 조회 → `playlistItems.list`)으로 교체했다
   (`getRecentUploadsForMatching()`, 5분 캐시). 이 방식은 비공개 여부와 무관하게 소유자의
   모든 업로드가 나오고, 비용도 더 싸다(`search.list` 100 unit vs `playlistItems.list` 1 unit).
2. **같은 파일 경로를 그대로 재사용하는 자산(썸네일 등)은 브라우저 캐시로 최대 1시간 안 바뀐
   채 보일 수 있다** — `/api/upload-package-asset/`·`/api/video-project-asset/`가
   `Cache-Control: max-age=3600`으로 무조건 캐시하고 있어서, 파일 내용만 교체해도(예:
   `thumbnail-b.jpg`를 다른 디자인으로 교체) 같은 URL이라 브라우저가 새로 안 받아왔다.
   `Last-Modified` 기반 검증(`no-cache` + `If-Modified-Since` 비교)으로 바꿔, 파일이 실제로
   바뀌면 즉시 반영되고 안 바뀌었으면 그대로 304로 가볍게 응답하게 했다.
3. **아이디어 카드 ↔ 프로젝트 연결 자체가 저장되지 않고 있었다(가장 결정적)** —
   `/api/idea-board/history/register`가 "재호출하면 `episodeSlug`/`status`/`producedAt`이
   갱신된다"는 주석과 달리, 실제 코드는 `body`에서 이 값들을 전혀 읽지 않고 무조건 이전 값(또는
   `null`)만 넣고 있었다. 즉 이 값들은 애초에 API로 설정하는 게 불가능한 상태였다. body 값을
   우선하도록 고쳤다. **다음 신규 에피소드부터**: `BRIEF.md` 작성 직후처럼 제작 초기에
   `episodeSlug`(`output/upload-packages/<slug>-longform/`과 정확히 같은 slug)를
   `idea-board-history.json`에 걸어두는 걸 잊지 말 것 — 이게 비어 있으면
   `syncIdeaBoardHistoryFromPackages()`가 그 항목을 통째로 건너뛰어서, 위 1·2번을 다 고쳐도
   아이디어 카드까지는 절대 안 이어진다.

세 가지 다 코드로 고쳤고, EP19로 실제 동기화까지 성공하는 것을 확인했다
(`scripts/youtube-analytics-server.mjs`). 수정 후에는 항상 서버 재시작 →
`node scripts/test-client-syntax.mjs` → 실제 `/api/sync` 호출로 상태가 바뀌는지까지
검증할 것(코드가 고쳐졌다고 끝이 아니라, 실제 데이터가 갱신되는 것까지 봐야 진짜 완료다).

### 4번째 원인 — status.json을 에이전트가 손으로 고칠 때 (2026-09-28, EP20에서 재발)

같은 증상("동기화했는데 안 됨")이 EP20에서 또 나왔는데, 이번엔 위 1~3번 코드 버그가 아니라
**에이전트가 `status.json`을 직접 `Edit`으로 고치면서 실제 코드가 읽는 필드명을 안 쓴 것**이
원인이었다. `getEpisodesSummary()`(`scripts/youtube-analytics-server.mjs`
`syncUploadPackageStatusFromYouTube` 주변)가 실제로 읽는 필드는 **`scheduledFor`**
(camelCase, ISO 문자열)인데, 렌더 완료 직후 "예약 시각 갱신"을 `scheduled_publish_date`
(snake_case)라는 **존재하지 않는 필드명**으로 두 번이나 써넣었다 — 코드는 조용히 그 값을
무시하고(`if (!statusData.scheduledFor) return statusData;`) 동기화 시도 자체를 건너뛰었다.

또 하나, **유튜브 Studio에 실제로 올릴 때 `title.txt`/`title-variants.txt`에 있는 제목이
아니라 그 자리에서 새로 입력한 제목을 쓰면, 제목 매칭이 원천적으로 실패한다** — 이건
버그가 아니라 매칭 로직의 근본 한계(제목이 후보 목록에 아예 없으면 못 찾음)다. 이 경우
`videoId`를 실제 유튜브 영상 목록(`getFullDashboardData`가 이미 불러온
`recentVideos[]`)에서 직접 찾아 `status.json`에 다음 필드로 손으로 써넣을 것 —
**아래 스키마 그대로**(필드명이 틀리면 이번처럼 조용히 무시된다):

```json
{
  "status": "scheduled",     // 또는 "ready_to_upload" / "published"
  "videoId": "<실제 videoId>",
  "scheduledFor": "<ISO 문자열, 예: 2026-09-29T14:00:00Z>",
  "lastSyncedAt": "<과거 시각으로 두면 다음 /api/sync가 즉시 재검증함>"
}
```

수정 후에는 `curl http://localhost:3001/api/sync`로 강제 동기화하고,
`/api/episodes/summary`·`/api/idea-board/history`를 직접 호출해 실제 값이 바뀌었는지
확인할 것 — 화면(브라우저)만 보고 "안 바뀐다"고 판단하지 말고, 서버 응답 → (그래도 이상하면)
Playwright 등 헤드리스 브라우저로 실제 렌더된 DOM까지 직접 확인해서 "서버 데이터 문제"와
"브라우저/캐시 문제"를 구분할 것(EP20에서 이 둘을 구분 못 해 캐시를 의심하다 실제 원인을
늦게 찾음).

### 렌더 저장 위치 관례 (EP11부터 확립, 2026-09-10 명문화, 2026-10-08 파일명 검색 키워드 SEO 규칙 확정)

- **렌더 직후 패키지 자동 반영 (2026-11-09)**: PostToolUse 훅 `scripts/sync-render-to-package.mjs`가 렌더 성공 뒤 최신 영상을 패키지의 검색어 이름 영상 위에 복사한다. 예약·공개 상태, 10분 넘은 렌더 파일, 이름을 정할 수 없는 새 패키지는 건너뛴다. 테스트: `scripts/tests/sync-render.test.mjs`.

**항상 두 곳에 남긴다 — 하나만 쓰지 말 것:**

1. **`videos/<project>/renders/<project>_<타임스탬프>.mp4`** — 작업용 원본. `-o` 옵션 없이
   `npx hyperframes render`를 그 프로젝트 디렉터리 안에서 실행하면 자동으로 이 경로·이름
   패턴으로 저장된다(`renders/<name>.mp4` 기본값의 `<name>`이 `<프로젝트>_<타임스탬프>`로
   채워짐). 재렌더할 때마다 새 타임스탬프 파일이 쌓이므로, 여러 버전을 비교하거나 나중에
   원본을 다시 찾아야 할 때의 작업 이력 역할을 한다.
2. **`output/upload-packages/<project>/[핵심_검색_키워드].mp4`** — 최종 완성본 (SEO 검색 키워드 파일명).
   1번에서 나온 파일 중 실제로 쓸 것을 단순 `video.mp4`가 아닌 **"해당 영상의 핵심 타겟 검색 키워드를 하이픈/언더스코어로 연결한 파일명"**(예: `English_Pronunciation_Double_Consonants_Listening_Practice.mp4`)으로 복사해 둔다.
   유튜브 알고리즘은 업로드되는 원본 동영상 파일명(Raw Video Filename)도 초기 카테고리 및 검색어 가중치에 반영하므로, `video.mp4` 고정 파일명을 쓰지 않는다.

**쇼츠도 같은 두 곳에 남긴다 (2026-11-07 사용자 결정)**: 2번 자리는 `output/upload-packages/ep<번호>-shorts-<이름>/`이다. 검색어로 지은 영상 파일, `title.txt`, `description.txt`(4~13줄: 첫 줄에 롱폼 제목, 영상 속 단어, 원리 한두 줄, 해시태그 3개 — 쇼츠 설명란 링크는 눌리지 않으므로 주소 대신 제목), `tags.txt`, `pinned-comment.txt`, `subtitles/subtitles-ko.srt`(대시보드에 자막을 보이려면 `multilingual-metadata.json`에 `ko` 한 줄)를 넣는다. **`status.json`은 두지 않는다** — 자동 예약 업로드는 `status.json`이 있는 폴더만 대기열에 넣으므로, 두면 쇼츠가 롱폼의 월·목 자리를 차지한다. 대시보드는 폴더 이름의 번호로 같은 번호 롱폼 카드에 SHORTS-A 탭으로 붙여 보여 주고, 영상 파일은 롱폼과 같은 규칙(검색어 이름 우선)으로 찾는다(`scripts/upload-package-summary.mjs`). 영상 파일은 git에 올라가지 않으므로 렌더링한 PC에서 올리거나 직접 옮긴다. 스튜디오에서 예약하면 대시보드가 제목으로 영상을 찾아 대시보드 전용 `shorts-status.json`에 예약·공개 상태와 videoId를 적고 쇼츠 탭에 "예약 · 날짜"로 보여 준다(2026-11-08). 자동 업로드는 이 파일을 읽지 않는다(테스트로 막아 둠).
   제목·설명·태그·썸네일·고정 댓글(`title.txt`/`description.txt`/`tags.txt`/`thumbnail-*.jpg`/`pinned-comment.txt`/`index.html`)도 같은 폴더에 함께 두며, `index.html` 내 `<video>` 태그 및 `upload-checklist.txt`도 해당 키워드 파일명과 정확히 일치시킨다.

**렌더 명령은 `-o`로 업로드 폴더에 바로 쏘지 말고, 항상 1번(프로젝트 renders/)부터 실행한 뒤
2번(upload-packages)으로 복사하는 2단계로 할 것** — EP14에서 처음 이 규칙을 어기고 `-o`로
업로드 폴더에 바로 렌더했다가 사용자가 "왜 EP13이랑 다르게 저장했냐"고 지적한 뒤 정정한
전례가 있다. 두 경로 다 `.gitignore`의 `videos/**/renders/*.mp4` /
`output/upload-packages/**/*.mp4` 규칙으로 이미 커밋 제외 대상이라, 두 벌 보관해도 저장소
용량에는 영향 없다.

### 차세대 스톱모션 고도화 5대 워크플로우 (EP20 테스트 도입 확정, 2026-09-20)

단순 2컷 점멸 깜빡임이나 실시간 AI 생성의 한계를 넘어, 아날로그 스톱모션 장인 감성과 음성학적 도파민을 극대화하기 위해 EP20부터 아래 5대 워크플로우를 본격 테스트·도입한다:

1. **Whisper 음절 단위 실측 칼싱크 (Phoneme-Sync Reaction)**:
   - `assets/voice/*.words.json`의 밀리초 타임스탬프를 활용해, 제1강세 발화 순간 0.05초 캐릭터 바운스(`scale: 1.06`, `y: -8px`) & 눈 똥그래짐, 약화 모음 발화 순간 어깨/턱 드롭(`y: +6px`) 릴랙스를 완벽 동기화.
2. **물리적 종이 컷아웃 & 고무도장 콜라주 (Paper Collage & Rubber Stamp)**:
   - AI 전신 생성 대신, 검증된 캐릭터 위에 물리적 오브젝트(빨간 불합격 도장 쾅! 화면 2px 흔들림, 돋보기 굴절 1.4배 줌, 깃털 살랑살랑 드롭)가 날아와 꽂히는 수제 컷아웃 연출.
3. **아날로그 12fps 스텝 점프 (Stepped Jitter & Claymation Rhythm)**:
   - 기계적 60fps 대신 GSAP `ease: "steps(4)"` 또는 12fps 스텝 전환을 적용해 정통 스톱모션 특유의 아기자기한 손맛 부여 + 미세 종이 캔버스 흔들림(Paper Jitter 0.5~1px).
4. **시선 유도 키네틱 가이드 (Focal Point Steering)**:
   - 캐릭터의 시선과 손짓이 화면 내 핵심 카드를 향하게 하여 시청자의 시선을 1초도 놓치지 않고 강제 견인.
5. **사전 부품 라이브러리화 (Sprite Bank Pre-baking)**:
   - 영상 제작 중 즉흥적 AI 생성 도박 금지 ➔ 손 모양 5종, 표정 5종, 소품 10종을 투명 PNG로 사전 구축 후 코드에서 레고 블록 조립식으로 100% 안전 배치.


## HyperFrames 기술 주의 (AGENTS.md에서 옮김, 2026-11-13)

- **GSAP로 애니메이션하는 요소에는 CSS `transition`을 같이 걸지 말 것**(2026-09-18 확정,
  EP17 Frame 6·7·8 사례) — HyperFrames는 "단일 paused 타임라인을 seek해서 렌더링"하는
  게 핵심 전제인데, 같은 속성(예: opacity/transform)에 CSS `transition`이 남아있으면
  GSAP가 seek 시 즉시 계산해 넣은 최종값을 그 트랜지션이 다시 가로채 "직전 DOM 상태 →
  새 값"으로 실제 시간(wall-clock) 기준 0.2초짜리 트랜지션을 새로 시작해버린다 — 그 결과
  화면을 정확히 언제 캡처/렌더하느냐에 따라 요소가 보이거나 안 보이거나 하는, 영상
  타임라인과 무관한 비결정성 버그가 생긴다(EP17에서 5개 단어 카드가 t=10s·20s엔 안
  보이고 t=17s에만 보이는 식으로 나타남 — 실제 렌더 파이프라인이 프레임마다 seek하는
  방식이라 최종 영상에도 영향 줬을 수 있음). 새 프레임 작성 후
  `grep -n "transition:" compositions/frames/*.html`로 GSAP 대상 요소에 CSS transition이
  남아있지 않은지 훑어볼 것.
- **영문 알파벳 일부를 색깔 `<span>`으로 강조할 때, span이 "f"로 끝나는 글자 바로 뒤에서
  시작하면("fi", "fl" 등 리게이처 조합) 브라우저가 리게이처 글리프를 span 경계 너머로
  합성해 전체를 span 밖(앞쪽) 색으로 칠해버릴 수 있다**(2026-09-18 확정, EP17 Frame 11
  "first" 사례 — `f<span style="color:...">ir</span>st`로 "ir"을 묶었는데 실제로는 "i"까지
  검정으로 나옴, 픽셀 직접 샘플링으로 확인). 이런 단어 강조 텍스트 요소에는 기본적으로
  `font-variant-ligatures: none`을 걸어 리게이처 자체를 꺼둘 것.

**⚠️ `lt-neon-border`는 지금 설치가 안 된다**(CLI 0.8.27~0.8.29 확인). 카탈로그 명세서의 `files`에 `target`이 빠져 있어 `hyperframes add lt-neon-border`가 `Cannot read properties of undefined (reading 'replace')`로 실패한다. 네온 효과가 필요하면 EP12 Frame 4(`videos/ep12-want-wont/compositions/frames/04-examples.html`)처럼 CSS로 직접 구현하고, 나중에 `hyperframes add lt-neon-border`부터 다시 시도해 본다.

## 엔드스크린 구간 7~10초로 변경 (2026-11-13 사용자)
위 "렌더 마지막 5초" 절의 본문은 2026-11-13에 **7~10초**로 고쳤다(절 제목은 다른 문서가 이름으로 가리켜 그대로 둔다). 롱폼에만 적용하고 쇼츠에는 엔드스크린이 없다. 카드류를 넣는다면 유튜브 엔드스크린 요소 크기 이하이거나 정확히 맞고 서로 겹치지 않아야 한다(겹치면 업로드가 안 된다). **요소 크기는 아래 측정값을 쓴다.**

공식 도움말(`support.google.com/youtube/answer/6388789`, 2026-11-13 확인)에 적힌 것: 엔드스크린은 영상 마지막 **5~20초**에 넣고, 영상 길이가 **25초 이상**이어야 하며, 16:9 영상은 요소를 **4개까지** 넣을 수 있다. 같은 페이지는 요소의 가로세로 크기, 요소끼리 겹쳐도 되는지, 화면 가장자리에 놓아도 되는지는 적어 두지 않았다(웹의 제3자 안내는 서로 숫자가 달라 쓰지 않는다). 크기는 아래 스튜디오 화면 측정값을 쓰고, 겹침 금지는 사용자 경험 규칙이다(공식 문서에는 없다). 25초 미만 쇼츠에는 엔드스크린이 없을 가능성이 높지만 확인하지 못했다.

**엔드스크린 요소 크기 (2026-11-13, 사용자가 준 스튜디오 엔드스크린 편집기 스크린샷 861×536을 픽셀로 측정)**: 미리보기 영상 틀은 폭 약 857px(16:9). 동영상·재생목록 요소는 폭 약 279px(틀 폭의 32.6%)·높이 약 159px(33.0%)이고, 채널(구독) 요소는 지름 약 130~134px(15.2~15.6%)다. 1920×1080 영상에 대면 동영상·재생목록 약 625×356, 채널 약 292~300이다. 오차는 요소 그림자 때문에 틀 폭의 0.4% 안팎(1920 기준 7px 안팎)이다. 요소 위치는 사용자가 끌어 놓는 것이라 고정값이 아니다. 영상 안에 카드류를 넣는다면 위 크기 이하이거나 정확히 맞고 요소끼리 겹치지 않아야 한다. 정확한 값이 필요하면 편집기에서 요소를 눌러 크기를 다시 재서 이 문단을 고친다.
