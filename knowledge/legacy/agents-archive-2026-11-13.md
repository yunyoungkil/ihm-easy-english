## 원문: 대시보드 및 시스템 기능 설계 시 자동화 우선 원칙 (모든 대화 공통 적용, 2026-11-11 확정)

대시보드와 데이터 파이프라인의 기능을 추천, 추가, 업데이트, 설계할 때는 **반드시 사람의 수동 개입을 최소화하고 자동화를 최우선(Automation-First)**으로 한다. (2026-11-11 사용자 확정: "대시보드를 관리하는 것도 일이고, 사람이 할 일이 많아지면 데이터 오류 가능성이 커지므로 최대한 자동화해야 함")

**왜 이렇게 하나 (2026-11-11 사용자 설명)**: 사용자는 콘텐츠 제작 초보라 데이터를 모으고 분석할 시간과 경험이 없다. 그래서 **데이터 수집 → 판정 → 다음 기획 반영까지의 성장 루프를 에이전트, 대시보드, 스킬, 플러그인이 함께 알아서 돌린다.** 사람이 멈춰서 승인하는 곳은 **렌더, 썸네일, 업로드 세 군데뿐**이다. 그 밖의 데이터 정리, 판정, 기록, 버그 수리는 에이전트가 승인을 기다리지 않고 진행한 뒤 결과를 브리핑으로 알린다.
- **루프에 들어가는 숫자는 진짜여야 한다**: 자동 루프는 틀린 숫자를 받아도 멈추지 않고, 틀린 방향을 계속 자동으로 민다. 손으로 적은 숫자, 손으로 넣은 상태, 짐작한 연결, 빈 값을 대신 채운 기본값(예: 중앙값 자리의 100)은 루프에 넣지 않는다. 데이터가 없으면 "아직 없음"이나 "판정 보류"로 둔다.
- **표본이 작으면 판정하지 않는다**: 편당 조회수가 수십 회인 동안에는 한 편의 차이가 운에 가깝다. 자동 판정(승격·차단·성공 패턴)에는 최소 표본 조건을 걸고, 모자라면 "보류"로 남긴다.
- **기능을 늘리기보다 정직하게 줄인다**: 화면에서 쓰지 않는 기능과 코드는 정리한다. 자동화는 신호를 만들어 주지 않는다.
- **모은 데이터는 반드시 쓰인다 (2026-11-12 사용자 확정)**: 데이터는 대시보드를 꾸미려고 모으지 않는다. 기획, 제작, 판정 중 한 곳에 실제로 들어가야 하고, 들어갈 곳이 없으면 연결하거나 모으지 않는다. 데이터별 쓰임은 [`knowledge/data-consumption-map.md`](../data-consumption-map.md)에 적고, `data/youtube/`에 새 파일을 만들면 그 지도에 한 줄을 더한다(빠지면 `npm test`가 실패한다). 새 수집을 늘리기 전에 지도의 빈틈부터 메운다.
- **깃에 올리지 않는 산출물은 어느 PC에서든 저절로 다시 만들어지게 한다 (2026-11-12)**: 사용자는 같은 구성의 다른 PC에서도 일한다(주력 Claude Code, 토큰이 떨어지면 Antigravity 제미나이). 캡처·캐시처럼 이 PC에만 두는 것은 저장된 기록(시각 등)으로 다시 만들 수 있어야 하고, 대시보드 서버·Claude Code 세션 시작 훅·매일 루프 중 둘 이상이 빠진 것을 채운다. 제미나이 쪽에는 세션 훅이 없으니 훅 하나에만 기대지 않는다(예: 아웃라이어 리포트 캡처 `npm run outlier-frames`).
- **AI 분석 프롬프트에 검증 안 된 우리 틀을 넣지 않는다 (2026-11-12 사용자 확정)**: 우리 채널 철학(도파민 3단계 공식 등)은 아직 검증된 것이 아니다. 지금은 잘되는 채널에서 배우는 단계이고, 철학은 성장이 멈췄을 때 데이터로 굳힌다. 그래서 경쟁 영상·댓글을 분석하는 프롬프트에는 철학, 미리 정한 분류 목록(예: "상식 파괴형/공감 유발형 중 1개"), 내용 예시를 넣지 않는다. AI는 실제로 본 것을 원문 인용과 함께 서술하고, 분류는 쌓인 데이터를 코드가 묶어 나중에 붙인다. 시청자 정보(3060 국내 학습자)와 정책(전문용어·해외 일화 금지)은 넣어도 된다.

1. **사람의 수동 관리 작업 원천 배제**:
   - 데이터 복사/붙여넣기, URL 수동 등록, 수동 태깅/토글, 사후 결과 수동 판정 등 사람이 반복해서 확인하고 눌러야 하는 관리형 UI/기능은 설계 및 추천에서 원천 배제한다.
   - 대시보드는 사람이 관리하는 '작업장'이 아니라, **"AI가 백그라운드에서 스스로 처리한 결과와 성과를 한눈에 보는 현황판(Read-Only)"**과 **"절대적 승인 게이트(Approval Gate, 렌더/최종 업로드)"** 목적으로만 간결하게 유지한다.
2. **자율 순환 라이프사이클 필수화**:
   - 경쟁 채널, 소재, 데이터 파이프라인은 시스템이 백그라운드 데이터 연동(유튜브 API, 동기화, 자동 성과 대조)을 통해 스스로 **발굴 ➔ 수집 ➔ 제작 연계 ➔ 성과 판정 ➔ 승격/차단/삭제(졸업)**의 전 과정을 무인으로 완결해야 한다.
   - 경쟁 채널 데이터의 경우:
     - **자동 발굴**: 우리 채널 추천 동영상 유입 데이터(`trafficSources.suggestedVideos`)에서 자동 포착하여 후보군 등록.
     - **성과 연동 승격 (황금 광산)**: 해당 채널 소재를 활용해 제작한 영상이 7일 차 성과(같은 포맷 중앙값 대비 1.5배 이상)를 내면 자동으로 고정(`Gold Mine`)하여 소재를 집중 채굴.
     - **소재 소진 시 자동 삭제 (명예 졸업)**: 해당 채널의 벤치마킹 가능한 잔여 아웃라이어가 0개가 되면 자동으로 목록에서 삭제/보관.
     - **성과 부진 시 자동 차단 (블랙리스트)**: 해당 채널 소재를 활용한 영상이 2회 연속 성과 부진(중앙값 0.5배 미만) 시 자동으로 차단(90일 쿨다운).

## 원문: 영상 렌더링 전 사용자 검수 및 승인 필수 (2026-09-20 확정)

영상 렌더링은 수십 분의 고부하 리소스와 시간을 소모하므로, 사소한 오타나 시각적 수정 사항이 생기면 전체 렌더를 처음부터 다시 돌아야 하는 막대한 낭비가 발생한다. 사용자가 이전 대화에서 "다음 작업 진행해"라고 포괄적으로 지시했더라도, **렌더링은 반드시 멈춰서 사용자 검수를 받아야 하는 '절대적 승인 게이트(Approval Gate)'**이다:

1. **컴포지션 완성 및 자동 검수**: 프레임 구현 후 `npx hyperframes check`를 실행하여 린트·런타임·대비 검증을 100% 완료한다.
   - 이어서 `npm run check-terms -- videos/<프로젝트>`로 화면 글자, 대본 낭독문, 그림 프롬프트의 금지어를 검사하고 결과를 2번 보고에 넣는다. 2. **검수 요청 및 정지**: 린터 통과 결과, 전체 영상 길이(초/분), 주요 화면 구성 요약, 프리뷰/콘택트시트 준비 상태를 사용자에게 명확히 보고하고 **"화면과 타임라인을 검수해 주시고, 렌더링 진행 승인 여부를 알려주세요"**라고 요청한 뒤 작업을 멈추고 기다린다.
3. **명시적 승인 확인 후 착수**: 사용자가 직접 화면을 확인하고 **"렌더링 진행해", "렌더링해", "승인할게" 등 명시적으로 렌더링 시작을 지시한 경우에만** `render` 명령어를 실행한다.
4. **추정/자의적 승인 간주 절대 금지**: "체크를 통과했으니 바로 렌더를 돌립니다", "흐름상 렌더링 단계이므로 진행합니다" 등 에이전트의 자의적 판단으로 렌더링을 시작하는 행위를 일체 불허한다.
**렌더링이 끝나면 패키지에 자동 반영된다 (2026-11-09 사용자 요청)**: `.claude/settings.json`의 PostToolUse 훅(`scripts/sync-render-to-package.mjs`)이 렌더 명령이 성공한 뒤 최신 영상을 같은 이름의 `output/upload-packages/` 폴더(롱폼은 `-longform` 폴더 포함)로 복사한다. 패키지에 검색어 이름 영상이 이미 있을 때만 같은 이름으로 덮어쓴다. 예약·업로드·공개된 패키지, 10분보다 오래된 렌더 파일, 영상 이름을 정할 수 없는 새 패키지는 건드리지 않고 이유를 알린다. 이 훅은 Claude Code에서만 돌아가므로 다른 에이전트는 렌더 뒤 직접 복사한다. 새 패키지의 첫 영상은 검색어 이름을 사람이 정해 한 번 복사한다. `status.json`은 이 훅이 만들거나 고치지 않는다.

## 원문: 영상 내 시각적 도파민을 위한 일러스트 적극 생성 및 역할 분담 원칙 (2026-09-20 확정, 2026-09-21 EP20 사례로 구체화)

코드로 텍스트 박스나 억지 도형을 만들어 화면을 때우는 것은 작업도 어렵고 결과물도 밋밋하여 시청자의
이탈을 부른다. **콤피UI AI 이미지 제작을 도입한 이유 자체가 이것이다** — 코드로 카드를 그리거나
어설픈 일러스트·이모지로 애니메이션을 넣으면 퀄리티가 확 떨어지기 때문.

⚠️ **2026-09-20 첫 버전은 "일러스트=시각적 실체, 코드=동적 생명력"이라고만 적어뒀는데, 정작
EP20에서 이미지를 65~280px 작은 아이콘 박스에 가두고 나머지 화면을 전부 코드 카드로 채워버렸다**
(사용자: "기존 아바타 이미지 사용과 코드 카드 연출이 너무 난잡"). 원칙은 맞았는데 숫자가 없어서
실무자가 "작은 아이콘 + 큰 카드"도 그 원칙을 지킨 것처럼 착각할 여지가 있었다 — 그래서 아래처럼
구체적인 기준으로 다시 정한다:

1. **역할 분담과 크기 기준**:
   - **일러스트(AI 이미지 — 웹 Gemini / Google Flow / Imagen 등; 로컬 ComfyUI는 2026-11-12 전면 삭제)**: 상황 묘사, 비유 그래픽, 오브젝트 등 시각적 실체를
     담당하고, **그 장면의 시각적 주인공이어야 한다 — 화면의 최소 40% 이상**(배경 전체를 채우거나
     화면 절반을 차지하는 큰 패널)을 차지한다. 65~280px 같은 아이콘 크기 박스에 가두지 않는다.
     작은 보조 아이콘(진행 상태 아바타 등)은 **그 장면에 이미 큰 메인 이미지가 따로 있을 때만**
     추가로 허용된다 — "작은 아이콘 하나만 있고 나머지는 전부 카드"는 금지.
   - **텍스트는 기본적으로 코드로만 렌더링한다 — 단, 이건 과거 "로컬 ComfyUI가 글자를 거의 항상
     깨뜨린다"는 특정 모델의 한계 때문이었지, 모든 이미지 생성 도구에 적용되는 절대 규칙은
     아니다(2026-09-22 정정; 로컬 ComfyUI는 2026-11-12 코드·PC에서 완전 삭제).** 이미지 안 글자를
     깨뜨리는 도구를 쓸 때는 프롬프트에 항상 "no text"류 지시를 넣고 제목·카드 텍스트·정답·캡션 등
     화면에 나가는 모든 글자는 이미지가 완성된 뒤 HTML/CSS로 그 위에 얹는다. **반면 Google
     Flow(나노바나나)처럼 텍스트를 정확하게 그리는 도구(2026-09-22 EP20 Frame 3에서 "쾅!!"/
     "Word"/"Old" 전부 정확히 렌더링 확인)로 만들 때는** 그 장면에 **고정으로
     붙어있는 짧은 단어·의성어**(예: 의성어 "쾅!!", 말풍선 속 답 단어)는 이미지 안에 직접
     그려 넣어도 된다. 다만 **나레이션 타이밍에 맞춰 계속 바뀌어야 하는 동적 텍스트(하단
     캡션, 실시간으로 스왑되는 카드 문구 등)는 어떤 도구로 만들든 여전히 코드로 렌더링**
     한다 — 이미지에 굳어버린 텍스트는 타이밍을 맞추거나 다국어 자막으로 바꿀 수 없기
     때문이다.
   - **코드(HyperFrames/GSAP)**: 이미지들의 스톱모션 전환, 등장/퇴장 바운스, 글자 하이라이트
     동기화, 카운트다운 게이지, 사운드 싱크 등 동적 생명력만 담당한다. 코드가 화면의 주인공이
     되는(=카드·텍스트박스가 이미지보다 넓은 면적을 차지하는) 구도는 지양한다.
2. **이미지 전환은 "나레이션 길이에 맞춘 홀드"가 기본이고, "초당 8~12장 빠른 전환"은
   급작스러운 순간 반응에만 쓴다** (2026-09-22 EP20 Frame 1·2에서 실측 검증 후 확정 —
   이전 버전은 모든 캐릭터 리액션 시퀀스를 "3~5장을 초당 8~12장으로 전환"하라고만 규정
   했었는데, 그대로 Frame 1에 적용했더니 사용자가 재생을 보고 "너무 빨리 지나간다"고
   두 차례 지적했다. 원인은 "몇 초에 걸쳐 설명되는 내용"과 "0.5~1초 안에 순식간에
   벌어지는 반응"을 똑같은 속도로 취급한 것 — 나레이션 한 문장이 5~9초씩 이어지는
   구간에 이미지를 8~12fps로 넘기면 나레이션과 안 맞고 산만하기만 하다):
   - **기본(설명이 이어지는 구간)**: 이미지 한 장을 **그 장면에 대응하는 나레이션 문구가
     실제로 발화되는 구간만큼** 붙들고 있는다 — `assets/voice/NN.words.json`의 단어별
     실측 타임스탬프로 전환 시점을 정확히 맞출 것(추정값 금지). 전환 자체는
     `display:none/block` 하드 컷이 아니라 0.2~0.3초 크로스페이드로 부드럽게 넘기고,
     전환 순간에 카드 스케일을 살짝 펀치(1.02~1.1배)했다가 `back.out`으로 정착시키는
     정도의 물리감만 얹는다.
   - **급작스러운 반응(임팩트) 구간만 예외적으로 빠르게**: 실제로 "순식간에 벌어지는"
     리액션(예: 충격받아 0.5~0.8초 만에 양손이 번쩍 올라가는 순간)은 그 짧은 구간
     안에서만 여러 장(최소 3~5장)을 초당 8~12장으로 빠르게 전환해 진짜 스톱모션 질감을
     낸다(Frame 1의 충격 리액션 클라이맥스가 이 예외에 해당).
   - 어느 쪽이든 **이미지 2~3장을 8~10초씩 붙들고 있다가 하드 컷으로 바꾸는 것은 여전히
     금지**(EP20 최초 버전의 반례) — 홀드하더라도 전환은 항상 크로스페이드여야 한다.
3. **화면 모션 공백 방지**: 나레이션이 이어지는 구간에 시각적 변화 없이 멈춰 있는 '모션 공백'을
   방치하지 않는다. 공백 구간에는 나레이션의 감정과 핵심 내용을 시각적으로 증폭하는 스톱모션
   시퀀스(예: 경험담 공감 ➡️ 충격/혼란 ➡️ 아하! 깨달음)를 배치한다.

## 원문: 캐릭터 일관성 기준 및 아바타 활용 원칙 (2026-09-20 확정)

   - 12fps 스텝 점프(GSAP `ease: "steps(4)"`), 미세 화면 진동, 실측 음절 싱크 등 물리적 피직스를 결합하여 정통 카툰 애니메이션 완성도를 완성한다.

## 원문: 스크립트 작성 원칙 3~5번 (원문)

3. **6대 실전 스토리텔링 작법 원칙 (Callaway 6 Principles)**:
   - ① **사우스파크의 `But / Therefore` 인과 댄스**: `그리고(And then)` 식의 단순 지식 나열 절대 금지. `그런데(But)`로 문제/갈등을 열고 `그래서(Therefore)`로 해결하며 오픈 루프 지속.
   - ② **문장의 음악적 리듬 변주 & 톱니바퀴 대본 (Jagged Edge)**: 모든 문장의 길이가 비슷하면 TTS가 단조로워짐. 짧은 펀치 ➔ 중간 설명 ➔ 긴 문장의 변주. 줄 끝이 들쭉날쭉한 톱니바퀴 형태 유지.
   - ③ **독점 스토리 렌즈 (Story Lens)**: 남들과 똑같은 '교과서 문법 렌즈' 대신 '사진 찰칵 vs 동영상 재생', '게으른 혀의 소리 물리법칙' 등 독점 프리즘으로 비틀어 카테고리 오브 원 구축.
   - ④ **크리스토퍼 놀란식 결말 우선 설계 (Direction)**: 영상 맨 마지막 핵심 한 문장(시청자에게 줄 선물)을 먼저 확정하고 거꾸로 앞을 빌드업.
   - ⑤ **시각적 훅 우선주의 (Visual Hook)**: 눈이 귀보다 10배 빠르다. 첫 3초(Frame 1)에 소리보다 직관적인 시각적 충격(시뻘건 오답창, 충돌 그래픽)을 0.1초 만에 먼저 제시.
   - ⑥ **1:1 동반자 대화체 (Talking WITH, not AT)**: 불특정 다수 대상 강의가 아닌, 카메라 뒤 친한 친구 한 명에게 음성 메시지를 보내듯 편안하고 솔직하게 대화.
4. **상위 0.1% 시청 지속 시간(Retention) 스크립트 아키텍처 (Masterclass Architecture, 2026-09-28 확정)**:
   - ① **도입부 노동량 증명 훅 (Proof of Work Hook)**: 단순히 "오늘 OO 알려드릴게요" 식의 시작 절대 금지. 슬로모션 영상 수십 편 분석, 사전·음성학 논문 대조 등 화자가 들인 압도적 연구량을 1문장으로 증명하여 시청자에게 "내가 며칠 동안 고생할 걸 이 영상 하나로 거저먹는다"는 압도적 가치(Value Proposition)를 즉시 부여.
   - ② **프레임 간 무이탈 오픈 루프 체이닝 (Open-Loop Chaining)**: 각 파트(프레임) 끝에서 "이상으로 OO였습니다" 식의 완결형 닫힘 절대 금지 (시청자 이탈 급락 지점). 반드시 다음 파트를 안 보고는 못 배기게 만드는 새로운 의문이나 긴장(루프 브릿지)으로 끝맺어 롤러코스터식 연속 낙하 유도.
   - ③ **'우리(We)' 동반자 화법 (Talking WITH, not AT)**: 시청자를 가르치려 들거나 실수를 탓하는 훈계조 절대 금지. "학창 시절 우리 다 이렇게 배웠잖아요", "저도 외국인 앞에서 맨날 얼어붙었습니다"처럼 같은 편으로 묶은 뒤 솔직한 팩트로 해결책 제시.
   - ④ **실패와 오답의 시각화 (Show The Failure, Don't Just Tell)**: 정답만 예쁘게 보여주는 설명 금지. 우리가 흔히 저지르는 망가진 발음, 외국인의 당황하는 반응, 시뻘건 오답 창을 0.5초 만에 시각적으로 먼저 충격 요법으로 보여준 뒤 정답과 대조.
5. **다른 채널 레퍼런스 영상으로 톤을 보정할 때: "가짜 구체성" 라벨 금지 (2026-09-30 확정)**:
   - 사용자가 완전히 다른 장르(예: IT 툴 튜토리얼)의 실제 음성 전사본을 "이 톤으로 더 자연스럽게
     써줘"라고 참고 자료로 줄 수 있다. 이때 **레퍼런스의 진짜 자연스러움이 어디서 오는지부터
     정확히 짚을 것** — 표면적으로 문장 끝맺음(습니다→거든요 등)만 바꾸는 건 손질이지 자연스러움이
     아니다. 진짜 차이는 대개 **구체성**이다: 레퍼런스는 "오이맛 탄산음료", "경포 해변"처럼 손에
     잡히는 실제 사물·장소·상황을 예로 든다.
   - **"일상에서 자주 쓰는/마주치는 단어" 같은 카테고리 라벨을 붙이는 것은 구체화가 아니다** —
     "이게 일상적이다"라고 설명(tell)하는 것과 실제로 일상적인 장면을 보여주는(show) 것은 다르다.
     대신 그 단어가 실제로 쓰이는 구체적 장면 하나에 직접 묶을 것(예: "letter"를 다룰 땐 "일상에서
     자주 쓰는 단어" 대신 "편지 쓸 때 자주 쓰는 letter"로).
   - **레퍼런스의 모든 특징을 그대로 가져오지 않는다** — 장르가 다른 레퍼런스는 필러 단어("뭐",
     "일단"), 같은 말을 살짝 바꿔 반복하기, 해요체 같은 요소를 같이 갖고 있을 수 있는데, 이건
     이 채널이 EP11부터 지켜온 "차분하고 단단한 신뢰감의 실전 파트너 톤"(습니다체 기본)과 충돌할
     위험이 있다. 어떤 특징을 가져오고 어떤 특징을 버릴지는 매번 판단해서 근거를 남기고, 애매하면
     사용자에게 확인한다 — 통째로 베끼지 않는다.

## 원문: 스크립트 작성 원칙 10번 Gemini TTS 규격 (원문)

10. **Gemini 3.8 Flash TTS 직접 제작을 위한 스크립트 표준 규격 (2026-10-04 확정, 2026-10-07 개정, 모든 대화 공통 적용)**:
    - **복사용 순수 텍스트 코드 블록(` ```text `) 필수 분리**: 나레이션과 영어 발음 텍스트는 불필요한 마크다운 불릿이나 해설 괄호 없이, 드래그 한 번 또는 복사 버튼으로 즉시 Google AI Studio / Gemini TTS 입력창에 넣을 수 있는 독립된 ` ```text ` 코드 블록으로 작성한다.
    - **복사용 코드 블록 내 영문 지시문(Directive) 혼합 절대 금지 (순수 대본 100% 분리)**: 단일 텍스트 입력창에 `Say only the narration...` 같은 영문 지시문을 본문과 함께 넣으면, TTS 엔진이 앞의 지시문 텍스트까지 그대로 소리 내어 읽어버리는 치명적인 사고가 발생한다. 따라서 복사용 ` ```text ` 블록 내부에는 영문 지시문을 완전히 배제하고, 오직 소리 내어 읽을 **'순수 대본 텍스트'만 100% 분리**하여 제공한다. 보이스/톤 지시문은 코드 블록 외부의 메타데이터(가이드 표)에만 참고용으로 둔다.
    - **첫 단어 영문 시작 시 교포/이민자 억양 생성 방지 및 상투적 클리셰('솔직히') 남발 금지 (2026-10-09 확정)**: 문장의 첫머리가 영단어(예: `Sheep이랑...`, `Coffee나...`)로 시작하면 다국어 TTS 모델이 화자를 교포로 인식해 한국어 전체에 어색한 이민자 억양을 입혀버린다. 문장 첫머리는 반드시 100% 순수 한국어로 시작하되, **특정 단어(`솔직히`)를 매 에피소드마다 첫 단어로 기계적으로 반복하는 행위를 엄격히 금지**한다 (시청자에게 판에 박힌 AI 공식 대본 티를 냄). 첫머리는 상황에 맞게 다채롭게 시작한다: `학창 시절에...`, `영어 단어를 보다 보면...`, `우리가 흔히...`, `혹시...`, `분명히...`, 또는 부사 없이 직관적 질문으로 즉시 진입. 발음이 꼬이기 쉬운 영단어는 TTS 복사용 텍스트에 **한글 독음(예: `쉬잎`, `쉽`)**으로 적어 영상 화면 자막(`SHEEP vs SHIP`)과 TTS 낭독 텍스트를 철저히 분리한다.
    - **청취 명확성을 위한 핵심 목적격 조사(`을/를`) 필수 표기 원칙 (2026-10-09 확정)**: 유튜브 나레이션은 텍스트를 읽는 게 아니라 오디오를 '실시간 청취'하는 환경이므로, "귀 뚫어"처럼 조사가 빠지면 순간 소리를 놓쳤을 때 시청자가 문장 구조를 한 번에 직관적으로 파악하지 못해 인지 부하가 발생한다. 따라서 핵심 캐치프레이즈와 술어부에는 목적격 조사를 절대 생략하지 않고 명확하게 발음하도록 작성한다:
      - ❌ `귀 뚫어 드리겠습니다` ➔ ⭕ `귀를 뚫어 드리겠습니다`
      - ❌ `소리 뚫어 드리겠습니다` ➔ ⭕ `소리를 뚫어 드리겠습니다`
    - **0-패딩 파일명(WAV ID) 사전 확정**: 오디오 생성 및 타임라인 싱크 시 혼선을 방지하기 위해 `assets/voice/01_f01_hook.wav`, `en_coffee.wav` 등 명확한 파일명을 각 세그먼트마다 지정한다.
    - **음성 제작 진행 체크리스트 제공**: 스크립트 상단에 파일명, 화자, 텍스트 요약, 예상 시간, 진행 상태(`[ ]`)를 한눈에 볼 수 있는 제작 시트를 배치한다.
    - **원어민 단어 오디오 재사용 설계 (듣기 롱폼)**: 반복되는 단어는 1개 파일당 1회씩 깨끗하게 생성하고 타임라인(HyperFrames)에서 루프로 재생하며, 섞어 듣기나 복습 프레임에서는 새로 생성하지 않고 기존 단어 파일들을 재배열 재생하도록 설계한다.
    - **시청자용 텍스트에서 교육학 전문 용어 배제**: 시청자가 직접 듣는 나레이션이나 화면 카드에는 '드릴(drill)' 같은 교수 설계 용어를 절대 쓰지 않고, '반복 듣기', '소리 연습', '집중 듣기' 등 친숙한 일상어로 쓴다.
    - **단어 읽기 시 끝소리 급단절(뚝뚝 끊김/클리핑) 방지 및 음향 블렌딩 표준 (2026-10-07 확정)**: 단어 뒤에 마침표(`.`)가 있거나 단독 단어만 제공되면 TTS 엔진이 급브레이크를 밟아 끝소리를 칼같이 잘라버리는 스태카토 현상이 발생한다. ① **TTS 텍스트**: 단어 나열 시 마침표를 금지하고 반드시 쉼표(`,`)나 줄임표(`...`)를 붙여 끝소리 여운(Decay)을 유도한다. ② **배치 분할**: `split-batch-voice.mjs`로 자를 때 끝부분에 최소 0.25초(250ms) 여운 패딩과 끝 50ms 페이드아웃(`afade=t=out`) 필터를 적용한다. ③ **오디오 믹싱**: 영상 배경에 은은한 앰비언스 BGM(볼륨 8~10%)을 깔아 디지털 완전 무음(Dead Silence)을 메우고 단어 간 1.5~2초 호흡을 유지한다.
