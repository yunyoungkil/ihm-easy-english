# 제작 규칙

## 제작 단계와 상태 기록

- 모든 영상은 [영상 제작 표준 워크플로우](VIDEO_WORKFLOW.md)의 10단계를 따른다.
- 새 영상 프로젝트는 루트에 `STATUS.md`를 만들고 [STATUS 템플릿](templates/STATUS.template.md)의 상태 값과 승인 게이트를 사용한다.
- 작업 시작 시 `STATUS.md`의 `현재 단계`와 `다음 행동`을 먼저 확인한다.
- 대본, 스토리보드, 디자인, 렌더, 업로드 승인은 서로 독립적으로 기록하며 추정해서 승인하지 않는다.
- 단계가 바뀌거나 실패·새 결정이 생기면 `STATUS.md`를 즉시 갱신하고 상세 근거는 관련 에피소드 문서와 월별 로그에 둔다.

## 시청자

- 핵심 대상은 40~60대 영어 왕초보다.
- 전문 용어보다 익숙한 단어와 한글 발음을 먼저 보여준다.
- 한 문장에는 하나의 정보만 둔다.
- “철자 묶음”보다 “끝의 같은 네 글자”, “바로 앞 음절”보다 “셜 바로 앞부분”처럼 말한다.
- 틀렸다고 비난하지 않고 규칙을 발견하게 한다.

## 쇼츠 화면

- 1080×1920.
- 상단·하단 플랫폼 UI 안전영역을 지킨다.
- 사용자의 결정에 따라 우측 버튼 안전영역은 별도로 비우지 않는다.
- 영어 철자 발화 시 해당 철자 색을 변경한다.
- 한글 발음 발화 시 해당 음절 색을 변경한다.
- 핵심 이해 구간에서는 요소 위치를 안정시키고, 전환·예시 구간에서 리듬을 만든다.
- 효과음은 모든 장면 전환에 넣지 않고 질문·정답·CTA 등 의미 있는 박자에만 사용한다.

## 색상

- 나레이션과 동기화되는 영어 철자 강조: `#FF0000`.
- 나레이션과 동기화되는 한글 음절 강조: `#008EFF`.
- 노란 카드 박스는 핵심 단어에만 사용한다.

## TTS

- Charon, ko-KR을 채널 기본 목소리로 유지한다.
- 쇼츠는 자연 발화보다 약간 빠르게 하되 설명은 또렷하게 한다.
- 퀴즈의 질문 나레이션에는 화면에 제시된 영어 단어의 **정답 발음이나 정답 단어를 절대 넣지 않는다**. 영어 철자는 화면으로만 보여주고, 음성은 `첫 번째 단어입니다. 어떻게 읽을까요?`처럼 문제 순서와 질문만 말한다.
- 퀴즈는 `정답이 포함되지 않은 질문 → 1.2~1.6초 생각 시간 → 정답 발음 공개 → 원리 설명` 순서를 지킨다.
- 대본 검수 때 화면 문구를 보지 않고 질문 음성 문장만 따로 읽어도 정답을 추론하거나 들을 수 없는지 확인한다.
- 무료 한도를 넘는 호출은 비용 견적과 사용자 승인 없이 실행하지 않는다.
- TTS는 익숙한 영어 발음을 자동 교정할 수 있으므로 오답 예시는 반드시 실제 청취한다.
- `커머시알`은 `커머. 시. 알?`처럼 문장 경계로 분리해야 자동으로 `커머셜`이 되는 것을 막을 수 있었다.
- 음성을 교체하면 해당 `.whisper-scratch` 캐시를 삭제한 뒤 다시 전사한다.
- Whisper 전사문은 발음 판정의 최종 근거가 아니다. 실제 청취가 우선이다.

## HyperFrames 제작 기준

- HyperFrames 프로젝트 폴더의 HTML·자산·타임라인은 하나의 동일한 원본이다. Studio에서 한 편집도 같은 소스에 반영되므로 별도 복사본으로 취급하지 않는다.
- 나레이션 영상은 `BRIEF.md`(목적), `STORYBOARD.md`(장면 순서), `SCRIPT.md`(확정 원고), `frame.md`(시각 기준), `index.html`/`compositions/`(실제 결과)를 함께 둔다.
- 승인된 구조에서만 제목·단어·색 등 반복되는 항목을 변수로 만든다. 디자인 검증 전에는 무리하게 공용화하지 않는다.
- 최종에 필요한 음성·이미지·영상·폰트는 반드시 프로젝트 내부에 복사하고, 원본과 가공본은 이름으로 구분한다. 임시 URL·브라우저 세션·렌더 시점 네트워크 파일은 쓰지 않는다.

## HyperFrames 워크플로 선택

### 기본 원칙

- 워크플로는 화면 스타일이 아니라 **입력과 제작 목적**으로 고른다. 먼저 맞는 전용 워크플로가 있는지 확인하고, 없을 때만 `General Video`를 쓴다.
- 새 대본으로 만드는 영어 교육 영상은 기본적으로 `Faceless Explainer`다. 실제 촬영 영상이 없고, 초보자가 하나의 발음 원리를 이해하도록 타이포그래피·도식·예시를 새로 구성하는 현재 채널의 정상 제작에 가장 맞는다.
- 이미 만든 음성·참고 디자인·여러 자산을 조합해 구조를 직접 설계하는 실험 또는 맞춤형 편집은 `General Video`로 만든다. EP8 Softboard 테스트가 이 경우다.
- 한 번 선택한 워크플로는 결과와 무관하게 고집하지 않는다. 입력 조건이 바뀌면 아래 표로 다시 판정하고, 변경 이유를 해당 에피소드 문서에 남긴다.

| 입력·목적 | 기본 워크플로 | 우리 채널에서의 사용 |
|---|---|---|
| 확정 대본 또는 주제, 실제 촬영 영상 없음, 한 가지 원리를 설명 | `Faceless Explainer` | 새 롱폼과 새 쇼츠의 기본. 대본 → 스토리보드 → 그래픽·도식·자막·음성 순으로 제작 |
| 기존 내레이션·참고 이미지·복수 자산을 조합하거나, 장면 구조를 직접 실험 | `General Video` | Softboard 같은 설명 장면 실험, 기존 영상 재구성, 전용 시퀀스 |
| 3~10초짜리 독립 그래픽, 나레이션 없음 | `Motion Graphics` | 인트로 스팅, 퀴즈 정답 공개, 규칙 임팩트, CTA 전환용 부품. 본편 전체에는 사용하지 않음 |
| 실제 토킹헤드 영상은 그대로 두고 자막만 추가 | `Embedded Captions` | 향후 사람 출연 영상에만 사용 |
| 실제 토킹헤드 영상에 발화 동기 그래픽을 추가 | `Talking-head Recut` | 향후 사람 출연 영상을 바꾸지 않고 보강할 때만 사용 |
| 음악의 박자가 영상 구조를 결정 | `Music-to-Video` | 음악 중심 오프닝·브랜드 영상처럼 예외적인 경우만 사용 |
| 웹사이트·앱 화면을 소개 | `Product Launch Video` | 채널 교육 영상에는 기본적으로 해당 없음 |
| 리더십·내부 검토용 클릭형 자료 | `Slideshow` | MP4가 아니라 탐색형 발표 자료가 필요할 때만 사용 |
| GitHub PR 변경 내용을 설명 | `PR to Video` | 채널 제작과 무관; 개발 공유에만 사용 |

### 제작 요청에 반드시 확정할 항목

새 영상 요청은 아래 여섯 가지를 짧게 확정해 `BRIEF.md`에 남긴다. 다음 작업자는 채팅을 다시 읽지 않고 이 문서에서 재개한다.

1. 시청자와 한 편을 본 뒤 얻어야 할 한 가지 이해
2. 플랫폼·비율·목표 길이(롱폼 16:9 / 쇼츠 9:16)
3. 대본 상태(초안 또는 확정), 실제 음성을 반드시 유지해야 하는지
4. 제공 자산과 수정 금지 자산
5. 화면 리듬·모션 톤, 피해야 할 표현·효과
6. 두 장면 이상이면 스토리보드를 먼저 검토할지, 자동 제작으로 바로 초안을 만들지

### 검수와 반복

- 미리보기를 켠 상태에서 작은 수정 단위로 반복한다. 미리보기 없는 수정은 결과를 보지 못한 추측이다.
- 렌더 전 `lint`와 `check`를 모두 통과해야 한다. `check`는 런타임 오류, 넘침, 충돌, 모션, 대비를 검사하므로 생략하지 않는다.
- `Motion Graphics`로 만든 짧은 부품도 본편에 넣기 전 실제 나레이션·자막·전환과 함께 재생해 타이밍을 확인한다.

## 미디어·음성·자막

- 미디어마다 역할을 하나만 둔다: 음성은 설명, 이미지는 한 개념의 이해, 음악은 리듬, 효과음은 의미 있는 행동 보강이다. 역할이 겹치면 더 분명한 하나를 남긴다.
- 영상과 자막은 실제 음성 전사와 동기화한다. 자동 전사 뒤 고유 단어·철자·한글 발음·문장 구분을 반드시 확인한다.
- 내레이션이 중심인 영상은 실제 발화 타이밍에 화면을 맞춘다. 추정 씬 길이에 화면을 억지로 맞추지 않는다.
- 음악은 음성 아래에 두고, 효과음은 질문·정답·핵심 연결처럼 의미 있는 순간에만 쓴다. 침묵은 필요하면 그대로 둔다.
- 최종 검수는 소리 켠 전체 재생과 무음 재생을 각각 한 번씩 한다. 전자는 발음·믹스·타이밍, 후자는 자막·시각적 이해를 확인한다.

## 실사·아바타·후처리

- 아바타는 사람이 화면에서 설명해야 할 때만 사용한다. 현재 채널의 기본 형식은 그래픽+나레이션이며, 아바타는 기본값이 아니다.
- 사람 실사나 아바타를 디자인 위에 올려야 할 때만 배경 제거를 검토한다. 투명 결과는 프로젝트에 보관하고 머리카락·손·빠른 움직임·처음/끝 프레임을 검수한다.
- 색보정과 미디어 효과는 이미지·영상 레이어에만 비파괴적으로 적용한다. 자막·일반 HTML 그래픽을 포함한 전체 화면에 일괄 적용하지 않는다.
- 보정은 노출·화이트밸런스·대비를 먼저 맞춘 뒤 스타일을 더한다. 글리치·CRT·ASCII 같은 강한 효과는 학습 내용을 돕는 명확한 이유가 있을 때만 사용한다.

## 검수

- 스틸 검수는 배치·넘침 확인용이다.
- 전체 재생 검수 없이 영상 완료로 표시하지 않는다.
- 질문 나레이션 종료 → 생각 시간 → 정답 공개 순서를 확인한다.
- 질문 나레이션이 목표 단어의 정답 발음을 먼저 말하지 않는지 모든 문제를 확인한다.
- 자막, 철자 색상, 한글 색상, 모션이 실제 발화와 맞는지 확인한다.
- 완료·업로드 상태는 추정하지 않는다.

## 공개 일정과 엔딩 화면 연결 규칙

지금까지는 EP9 제작 때 실제로 한 것만 있고 정식 규칙으로 적힌 적이 없었다(2026-08-25 확인). 다음 편부터 아래를 기본값으로 따른다 — 특별한 이유가 있으면 에피소드 문서에 이유와 함께 예외를 남긴다.

- **공개 순서·간격**: 롱폼 → +2일 → Track A → +2일 → Track B, 시각은 매번 20:00 KST 고정(EP9 실측: 8/23·8/25·8/27 20:00).
- **엔딩 화면 연결 영상은 항상 직전 편(previous episode)이다.** "다음 편"이 아니다 — 시청자가 시리즈를 거꾸로 이어보게 유도하는 것이 목적이고, 다음 편이 아직 없어서 어쩔 수 없이 쓰는 임시값이 아니다. 다음 편이 나온 뒤에도 바꾸지 않는다(EP9 실측: `endScreenVideo` = EP8, `previousVideo`와 동일한 영상).
- 시즌 마지막 편(EP10)처럼 정말 이전 편이 없는 경우에만 다른 연결을 검토한다.

## 업로드 패키지 변경 완료 조건

- 제목, 설명, 태그, 고정 댓글, 썸네일 문구 또는 썸네일 파일이 바뀌면 원본 콘텐츠 JSON과 출력 패키지를 함께 갱신한다.
- 변경 후 `npm run upload-summary`로 사람이 보는 통합 요약 HTML을 다시 만든다.
- 요약 HTML에서 최종 썸네일, 제목, 문구가 최신 상태인지 확인해야 작업이 완료된 것으로 본다.
- 통합 요약 HTML은 제목·문구·설명·태그·고정 댓글·공개 설정을 항목별 버튼으로 복사할 수 있어야 한다.
- 롱폼 업로드 패키지에는 엔딩 화면에 연결할 영상의 썸네일·제목·영상 ID·URL을 함께 표시한다(연결 대상은 위 규칙대로 직전 편).
- 롱폼과 모든 쇼츠 업로드 패키지 카드 상단에는 정확한 KST 예약 공개 일시를 크게 표시하고 복사할 수 있어야 한다.
- 예약 공개 5분 후 고정 댓글 알림을 사용한다. 다음 `업무시작` 때 미완료된 고정 댓글·고정 확인·영상 연결 작업을 다시 최우선으로 안내한다.

## 출력 폴더

- 사람이 영상을 찾는 기준 폴더는 `output/00-VIDEOS`다.
- 업로드 대기 영상은 `READY_TO_UPLOAD`, 공개 완료 영상은 `PUBLISHED`에 둔다.
- 제목·설명·태그·썸네일·고정 댓글은 기존 `output/upload-packages`에 둔다.
- 렌더 완료 상태를 변경할 때 `00-VIDEOS`의 상태 폴더도 함께 갱신한다.
