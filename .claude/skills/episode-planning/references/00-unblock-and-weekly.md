# Phase 0: 막힌 곳 풀기 (0-A 대청소 · 0-B 주간 점검 · 0-C 시작 브리핑)

새 영상을 기획하기 전에 "이미 만든 것이 시청자에게 닿고 있는지"부터 본다. 영상이 대기열에 쌓여 있거나 리뷰가 밀려 있으면, 새 기획보다 그걸 푸는 게 조회수에 먼저 영향을 준다.

- **0-A 대청소**: 쌓인 일이 많을 때 한 번 크게 치운다. 업로드 대기 3편 이상, 또는 밀린 리뷰 3편 이상이면 0-A로 간다.
- **0-B 주간 점검**: 대청소가 끝난 뒤 매주 가볍게 돈다.
- **0-C 시작 브리핑**: 새 대화의 첫 답변마다 짧게 보고한다.

공통 규칙:
- vidIQ는 쓰지 않는다. 우리 채널 숫자는 대시보드(`npm run analytics`, 포트 3001), 상태 확인은 프로젝트 자체 YouTube 연동을 쓴다(`CLAUDE.md` "우리 채널 자체 유튜브 데이터는 vidIQ보다 프로젝트 자체 연동을 먼저 쓴다").
- 숫자는 `POST /api/sync` 직후 `GET /api/dashboard`, `/api/episodes/summary` 응답 값만 쓰고 `range`를 같이 적는다.
- `status.json`은 손으로 고치지 않는다(`knowledge/production-rules.md` "4번째 원인 — status.json을 에이전트가 손으로 고칠 때").
- 업로드는 대시보드 자동 예약 업로드(`decideNextUpload`)나 사용자가 스튜디오에서 직접 한다. 에이전트가 우회 경로를 만들지 않는다(`CLAUDE.md` Client Script Integrity 5번).

## 0-A. 대청소 (쌓였을 때 한 번)

1. **실제 공개 상태 확인**
   - `npm run growth-check`를 돌린다. 이 스크립트는 `data/youtube/catalog.json`(대시보드 동기화 결과)을 기준으로 공개 여부를 본다.
   - 동기화가 오래됐으면 `/api/sync`부터 하고 다시 돌린다. 그래도 맞지 않으면 `knowledge/production-rules.md` "업로드 후 대시보드 자동 동기화가 안 될 때" 절을 순서대로 확인한다.
2. **공개 일정표와 업로드 체크리스트**
   - 미공개 편을 언제 올릴지 표로 만든다. 롱폼은 **월·목 밤 11시, 주 2회**다(2026-11-06 사용자 확정, `knowledge/production-rules.md` "공개 일정과 엔딩 화면 연결 규칙"). 대시보드 예약 설정(`data/youtube/publish-rules.json`)이 다르게 바뀌어 있으면 그 값을 따르고 바뀐 사실을 알린다. 쇼츠 공개 요일은 `knowledge/channel-strategy.md` "주간 목표" 표를 따르고, 미정이면 사용자에게 묻는다.
   - 편마다 업로드 전에 남은 일을 `upload-checklist.txt`와 `knowledge/now.md`에서 읽어 함께 적는다(새 메인 썸네일, 썸네일 승인, 금지어 항목 등).
   - 같은 방식·형식이 연달아 나가면 "같은 틀 반복"으로 보일 수 있으니, 사이에 쇼츠를 끼울 수 있는지 함께 제안한다(Phase 12).
3. **밀린 리뷰 숫자만 먼저 채우기**
   - 공개 7일이 지난 영상의 `REVIEW.md` "실제" 칸에 `/api/sync` 직후 숫자만 채운다. 판정과 `success-patterns.json` 승격은 이 단계에서 하지 않는다. 판정은 Phase 2에서 그 형식이 필요할 때 Phase 11로 한다.
4. **전후 비교**: 마지막에 `npm run growth-check`를 다시 돌려 막힌 곳이 얼마나 줄었는지 보여 준다.

**멈춤 지점**: 2번 공개 일정표는 사용자 확인을 받는다. 나머지는 보고하고 계속한다.

## 0-B. 주간 점검 (매주)

1. `npm run growth-check -- --save`로 새로 막힌 곳만 찾는다. 결과는 `knowledge/growth/check-YYYY-MM-DD.md`에 저장된다. 형식 배분과 표본 판정도 여기서 나온다.
2. `/api/sync` 직후 숫자로 이번 주를 본다: 조회수·구독자 증감, 롱폼 vs 쇼츠 비중, 상위 트래픽 소스 3개, 검색 유입 비중, 최근 영상 시청 지속률. `knowledge/channel-strategy.md` "주간 목표"와 나란히 적는다.
3. 공개 7일·28일이 된 영상이 있으면 Phase 11 진행 (48시간 판정은 작은 표본 노이즈 방지로 폐지됨).
4. Phase 11의 **중단 규칙**에 걸린 방식·형식이 있는지 확인한다(`05-performance-review.md` 4절).
5. `marketing:performance-report` 스킬로 한 장 요약: 핵심 숫자 표(출처·범위 포함) → 잘된 것 1~2개 → 막힌 것 1~2개 → **이번 주 할 일 최대 3개**. 할 일은 "EP25 썸네일 승인"처럼 이번 주 안에 끝낼 수 있는 행동으로 쓴다.
6. 결과는 `knowledge/growth/weekly-YYYY-MM-DD.md`에 남긴다(같은 날짜 파일이 있으면 읽고 갱신).

**멈춤 지점**: 없음. 보고하고 끝낸다.

## 0-C. 시작 브리핑 (새 대화의 첫 답변)

첫 답변을 아래 브리핑으로 연다. 사용자 요청이 함께 있으면 브리핑 바로 뒤에 처리한다. Claude Code에서는 훅이 안내와 점검 결과를 넘겨준다.

1. `CLAUDE.md` 세션 시작 규칙대로 `git pull` 확인과 대시보드 실행을 먼저 한다.
2. 훅이 넘겨준 "브리핑 재료"를 쓴다. 훅은 마지막 동기화가 12시간보다 오래됐으면 먼저 대시보드 동기화를 부른다(`scripts/briefing-sync.mjs`). 재료에 "대시보드가 꺼져 있어 동기화 못 함"이라고 나왔거나, `git pull`로 새 내용을 받았거나, 훅 결과가 없으면 대시보드를 켠 뒤 `npm run briefing:sync`와 `npm run growth-check -- --json`(결과의 `briefing`)으로 재료를 다시 만든다. 훅이 없는 에이전트도 이 두 명령으로 같은 재료를 만든다.
3. `knowledge/now.md` "▶ 다음 할 일"(훅이 넘겨준다)과 `knowledge/channel-strategy.md` "주간 목표" 표를 읽는다.
4. 이 틀로 보고한다(2026-11-09 사용자 결정으로 개편). 조건이 맞지 않는 줄은 빼서 평소 4~5줄, 많아도 7줄로 쓴다.

```markdown
**브리핑** (episode-planning 0-C · 동기화 11/9 09:00, 통계 ~11/7)
- 최근 7일: 조회 43회 (지난주 42회, +1), 구독 0명 (목표 1,000회 · 3명)
- 최근 공개 성적: EP24 롱폼 2일째 — 조회 40회, 평균 시청률 38%
- 쇼츠→롱폼: 쇼츠 피드 조회 900회, 쇼츠 링크로 넘어온 조회 7회
- 다음 공개: EP25 11/12 23:00
- 이번 주 할 일: 1) 새 댓글 2개 답하기 2) EP25·26 쇼츠 화면 3) EP23 7일 리뷰
- 남은 수리: 3개 (다음: 쇼츠 CTR 기준 따로 두기)
```

| 줄 | 언제 쓰나 | 숫자 출처 |
|---|---|---|
| 제목 | 항상. 쓰는 스킬 이름, 동기화 시각, 통계 마지막 날 | `analytics-latest.json` |
| 최근 7일 | 항상. 지난주 대비와 주간 목표 | 날짜별 조회·구독(`daily`) |
| 최근 공개 성적 | 7일 안에 공개된 영상이 있을 때. 통계가 아직 없으면 "통계 아직 없음" | `catalog.json` + 영상별 성과 |
| 쇼츠→롱폼 | 관련 동영상을 단 쇼츠(쇼츠 패키지)가 공개되고 하루가 지난 뒤 | 최근 7일 유입 경로(`trafficSources7d`) |
| 다음 공개 | 48시간 안에 공개가 있거나 업로드가 실패했을 때 | 패키지 `status.json`·`shorts-status.json` |
| 이번 주 할 일 | 항상. 답 없는 새 댓글이 있으면 넣는다. "공개 후 할 일"이 있으면 맨 앞에 넣는다 | "▶ 다음 할 일", 댓글 `replyCount`, 공개 후 할 일 |
| 남은 수리 | `(차차)` 항목이 있을 때 | "▶ 다음 할 일" |

- **공개 후 할 일 (2026-11-09 사용자 요청)**: 공개 14일 안의 영상에서 사람이 스튜디오에서 할 일을 코드(`growth-rules.mjs`의 `afterPublishTasks`)가 자동으로 만든다. 롱폼 고정 댓글(대기 표시나 자동 등록 실패가 남아 있을 때, 대시보드 "등록함"을 누르면 사라짐), 쇼츠 "관련 동영상"에 같은 편 롱폼 지정(롱폼이 공개되고 쇼츠가 올라가 있을 때), 쇼츠 고정 댓글(쇼츠 공개 뒤). `now.md`에 손으로 적지 않아도 된다. 사용자가 끝냈다고 하면 `data/youtube/after-publish-done.json`에 `{"EP25-shorts:related": "2026-11-13"}`처럼 키와 날짜를 적는다.
- **썸네일 없는 패키지 (2026-11-09)**: `thumbnail.jpg`가 없고 아직 공개되지 않은 패키지가 있으면 코드(`growth-rules.mjs`의 `thumbnailGaps`)가 이름을 알려 준다. 할 일 줄에 넣는다. 쇼츠 썸네일은 대본 확정 직후 그림 프롬프트와 함께 만든다(`06-shorts-and-next-watch.md`).
- 형식 판정(쇼츠·롱폼 배분), 밀린 리뷰, 업로드 대기, 작은 표본은 줄로 쓰지 않는다. 결론이 몇 주째 같아 매일 보여 줄 이유가 없어서다. 판정이 바뀌거나 밀린 리뷰가 생기면 할 일 줄에 넣는다.
- 유입 경로 전체, 영상별 클릭률, 구독 출처, 경쟁 채널은 브리핑에 넣지 않고 0-B 주간 점검에서 본다.
- 제목 줄에 쓰는 스킬 이름(`episode-planning 0-C`)을 적는다(2026-11-09 사용자 요청). "사용자 결정" 항목이 있으면 브리핑 끝에 한 줄로 묻는다. 파일로 저장하지 않는다.
- **남은 수리 (2026-11-09 사용자 결정)**: "▶ 다음 할 일"에서 `(차차)`가 붙은 항목은 급하지 않은 수리다. 할 일 줄에 넣지 않고 마지막에 "남은 수리" 한 줄(개수와 다음 하나)로 알린다. 간단한 문제는 발견한 자리에서 바로 고치고, 시간이 드는 것만 `(차차)`로 남긴다. 없으면 이 줄은 뺀다.
- 할 일은 "▶ 다음 할 일"의 앞쪽 항목부터 최대 3개 적는다. 목록이 비어 있으면 이번 주 안에 끝낼 수 있는 행동을 고르고, 형식 판정이 나오면 그 일을 먼저 넣는다.
- 이 단계는 읽기만 한다. 업로드, 승인, 공개 일정 변경, 유료 호출, `success-patterns.json` 갱신은 하지 않는다.
- 주간 목표가 미정이면 해당 칸에 "미정"이라 적고, 정할지 한 번 묻는다. 답을 기다리느라 요청 처리를 미루지 않는다.
- 답을 받거나 일을 끝내면 그 대화에서 "▶ 다음 할 일"을 바로 고친다(끝난 항목 삭제, 새 일 추가).
- 브리핑은 대화당 한 번이다. 이어 가는 대화에서는 하지 않고, 사용자가 빼라고 하면 그 대화에서는 생략한다.

**멈춤 지점**: 없음.

## 지표를 사용자에게 말할 때

초등학생도 알아듣게 한 줄 풀이를 붙인다.

| 지표 | 쉬운 뜻 |
|---|---|
| 노출 클릭률(CTR) | 썸네일을 본 사람 중 누른 비율 |
| 평균 시청률 | 영상의 몇 %까지 봤나 |
| 검색 유입 | 검색해서 들어온 조회 |
| 추천 유입 | 다른 영상 옆이나 홈에 떠서 들어온 조회 |
| 구독 전환 | 이 영상을 보고 구독한 수 |
