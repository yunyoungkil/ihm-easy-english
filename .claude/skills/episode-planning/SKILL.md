# 영어 발음 채널 에피소드 기획 마스터 워크플로우

## 이 스킬의 범위

이 스킬은 **소재 발굴 → 제목/썸네일 문구 → 스크립트(목차+본문)까지**를 담당한다.
그 이후 단계(TTS 생성, whisper 타임스탬프 추출, AI 일러스트, HyperFrames 프레임 구현,
렌더링, 업로드 패키지)는 이 스킬의 범위가 아니다 — 기존 `knowledge/VIDEO_WORKFLOW.md`와
`hyperframes` 스킬로 그대로 이어간다. 이 스킬을 억지로 그 뒤 단계까지 확장하지 않는다.

**대시보드(`scripts/youtube-analytics-server.mjs`)의 자동 추천 로직(`idea-board.mjs`,
A/B 시뮬레이터의 가상 CTR 점수)을 대체하는 워크플로우다** — 그 도구들이 캐시해 둔
`data/youtube/*.json` 스냅샷 숫자를 그대로 인용하지 않는다. 매 단계마다 그 자리에서
라이브로 다시 조회하거나 웹 검색한 근거로 판단한다(이유: 2026-10-03에 외부에서 받은
분석이 캐시된/오래된 숫자를 최신 수치인 것처럼 섞어 써서 조회수를 2배, 롱폼 비중을
40배 틀리게 계산한 사고가 있었다 — `knowledge/logs/2026-10.md` 참고).

## 전체 진행 원칙

- **단계별 진행, 매 단계 끝에 멈추고 사용자 승인을 기다린다** — 사용자가 "계속"이라고
  하거나 수정 지시를 주기 전까지 다음 단계로 넘어가지 않는다.
- **조언은 데이터와 팩트로 직언한다**(CLAUDE.md 기존 원칙) — 장점만 말하지 않고, 리스크·
  반례·숫자가 안 맞는 부분은 그대로 지적한다.
- **이 채널의 기존 규칙과 충돌하지 않는다** — `brand-persona.md`, `thumbnail-strategy.md`,
  `production-rules.md`, `CLAUDE.md`의 스크립트/썸네일/렌더링 규칙은 이 스킬 안에서
  다시 설명하지 않고 그대로 따른다. 이 문서는 "기획 진행 순서"만 정의한다.

## PHASE 1 — 라이브 데이터 분석 (캐시 금지)

이번이 몇 번째 기획이든, **이 단계의 숫자는 이번 세션에서 직접 다시 받아온 값만 쓴다.**

1. **우리 채널 현재 상태(라이브)**: 분석 대시보드 서버(포트 3001)가 떠 있는지 확인하고,
   없으면 `npm run analytics`로 띄운다. 그다음
   - `POST http://localhost:3001/api/sync` 로 강제 새로고침을 먼저 호출한다(캐시된
     스냅샷이 아니라 지금 유튜브 API에서 새로 받아오게 하기 위함).
   - 그 직후 `GET http://localhost:3001/api/dashboard`, `/api/episodes/summary`로
     조회수·구독자·트래픽 소스·검색어·영상별 시청 지속률을 받는다.
   - `data/youtube/analytics-latest.json` 등 파일을 열어서 그 안의 숫자를 바로 인용하지
     않는다 — 반드시 `/api/sync` 직후 응답값을 근거로 쓴다. 범위(최근 N일/3개월/누적)를
     혼동하지 않도록 매번 응답의 `range` 필드를 확인하고 표에 명시한다.
2. **이미 다룬 소재 확인(라이브)**: `GET /api/catalog` 또는 `/api/episodes/summary`의
   실제 제목 목록, 또는 `videos/*/BRIEF.md`를 직접 스캔해서 지금까지 다룬 발음 규칙
   목록을 새로 뽑는다. `idea-board-history.json`은 참고만 하고 그 파일의 완결성을
   신뢰하지 않는다(과거에 등록 누락 버그가 있었음).
3. **시청자 페인포인트·경쟁 채널(웹 검색, 라이브)**: 그 시점 기준으로 WebSearch를 실제
   실행해서 (a) 한국 성인 영어 학습자가 발음 관련해서 실제로 검색/질문하는 표현,
   (b) 경쟁 채널 최근 인기 영상 제목 패턴을 확인한다. `audience-dna.json` 등 과거
   스냅샷은 "그때 한 번 모은 참고 자료"로만 취급하고, 이번 분석에서 재확인되지 않은
   내용을 그대로 근거로 쓰지 않는다.
4. **산출물**: 아래 표로 "지금 채널의 진짜 현실"을 정리한다 — 숫자마다 어느 API 호출/
   어느 검색에서 나왔는지 출처를 반드시 붙인다.

   | 항목 | 값 | 출처 |
   |---|---|---|
   | 조회 범위 | (API 응답의 range) | /api/sync 응답 |
   | 롱폼 vs 쇼츠 조회수 비중 | | |
   | 최근 에피소드 시청 지속률 추이 | | |
   | 상위 트래픽 소스 3개 | | |
   | 검색 유입 비중 | | |
   | 이미 다룬 발음 규칙 목록 | | |

끝나면 정확히 다음으로 마무리한다: **"소재 후보로 넘어가려면 '계속'을 입력하세요."**
멈춘다.

## PHASE 2 — 소재 아이디어 생성

Phase 1에서 확인한 데이터만 근거로 영어 발음/리딩 규칙 후보 **10개**를 생성한다.

| 후보 | 핵심 검색 키워드(실제 검색창에 칠 법한 구체적 문구) | 타겟 페인포인트 | 기존 소재와 차별점 | 근거(Phase 1 어느 항목) |
|---|---|---|---|---|

- 이미 다룬 규칙과 **70% 이상 겹치는 소재는 제외**한다(제외한 이유도 한 줄로 밝힌다).
- "일상에서 자주 쓰는 단어" 같은 막연한 라벨이 아니라, 실제 검색 가능한 구체적 키워드로
  적는다(`CLAUDE.md`의 "가짜 구체성 라벨 금지" 원칙 재사용).

번호로 선택하거나 직접 다른 소재를 입력하도록 안내한다. 멈춘다.

## PHASE 3 — 분량/포맷 결정

이 채널의 기본 포맷은 롱폼(8~10분)이다. **프레임 수는 11개로 고정돼 있지 않다** —
실제로 지난 에피소드들도 11~15개로 제각각이었다(소재가 필요로 하는 비트 수가 매번
달랐기 때문). 사용자에게 다음을 확인한다:

- 롱폼 단독으로 갈지, 롱폼+파생 쇼츠(1~2개) 세트로 기획할지.
- 쇼츠를 같이 간다면, 어느 장면(퀴즈/반전 포인트)을 쇼츠용 훅으로 뺄지 이 단계에서
  미리 정해 둔다(스크립트를 다 쓴 뒤 나중에 고민하면 연결이 끊어진다).

멈춘다.

## PHASE 4 — 제목 & 썸네일 문구

`thumbnail-strategy.md`/`CLAUDE.md`의 기존 규칙(채널명 썸네일 표기 금지, 텍스트 5단어
이하, 클로즈업 시안 필수, 플랫 앵커 텍스트+골드 알약+무지 배경, A/B/C 시안 간 인물/구도
차별화)은 그대로 지킨다. **다만 A/B 시뮬레이터의 가상 CTR 점수(Gemini 채점)에 기대지
않고, 아래 체크리스트로 직접 판단한 근거를 말로 설명한다:**

- 검색 의도 키워드가 제목 앞부분에 구체적으로 들어가는가
  (❌ "아무도 몰랐던 원어민 소리의 비밀" / ⭕ "water 발음, 미국인은 왜 워러라고 할까")
- 호기심 갭이 있는가(정답을 주지 않고 궁금증만 유발하는가)
- 구체성이 있는가(일반 라벨이 아니라 실제 단어·장면·숫자)

3개 제목 시안 + 클로즈업 포함 썸네일 문구 3종을 만들고, 시안마다 "왜 이게 통할 것
같은지" 한 줄 근거(위 체크리스트 중 어느 항목을 충족하는지)를 붙인다.

사용자가 시안을 고르면(예: "A") **그 자리에서 바로** 썸네일 이미지 생성 프롬프트까지
작성해서 멈추지 않고 이어서 진행한다. **유튜브는 제목·썸네일을 3개까지 올려 실제
Test & Compare(A/B 테스트)를 할 수 있다** — 그래서 "사용자가 고른 시안"은 최종
업로드본일 뿐, 나머지 두 시안도 실제 A/B 테스트용으로 다 같이 쓰인다(EP17~21 전부
A/B/C 3종을 실제로 만들어 테스트에 올린 전례). **3개 시안 전부의 프롬프트를 만든다
— 고른 1개만 만들고 나머지를 미루지 않는다.**

- `knowledge/google-ai-studio-prompting.md`(Gemini 전용 프롬프트 기본 모델, CLAUDE.md
  기존 규칙)의 서술형 구조(Subject/Setting/Lighting/Shot/Text/Aspect Ratio)로 영어
  프롬프트를 쓴다.
- `thumbnail-strategy.md`의 기존 규칙을 그대로 지킨다: 채널명 배지 금지, 텍스트 5단어
  이하, A/B/C 시안 간 인물 표정·구도 차별화, 클로즈업 시안(화면 40~50%, 얼굴 중심)은
  **사용자가 고른 시안 기준으로 1개만 추가**(클로즈업은 모바일 전용 1개면 충분, 3개
  시안 전부에 클로즈업을 만들 필요는 없음 — 상세는 `thumbnail-strategy.md`), 플랫
  앵커 텍스트+골드 알약+무지 배경(소품/글로우/3D 금지 — NEGATIVE 프롬프트로 명시).
- 결과물: **일반 썸네일 A/B/C 3개 + 선택 시안의 클로즈업 1개, 총 4개 프롬프트.**
- 저장 위치: `videos/<프로젝트>/prompts/thumbnail-prompts.md` (파일이 없으면 새로
  만들고, 있으면 기존 파일을 `Read`로 먼저 확인한 뒤 이어서 추가한다 — 새 파일처럼
  가정하고 덮어쓰지 않는다. CLAUDE.md의 "새 영상 프로젝트 안의 파일을 쓸 때도 먼저
  확인" 원칙과 동일).
- 저장 직후 `BRIEF.md`의 "확정된 제목·썸네일" 섹션에 "이미지 프롬프트는
  `prompts/thumbnail-prompts.md`에 저장됨"이라고 한 줄 남긴다(다음에 또 "프롬프트
  어디 있어?"라고 묻지 않도록).

멈춘다.

## PHASE 5 — 스크립트 목차(아웃라인)

**다른 에피소드의 프레임 이름·순서·개수를 템플릿으로 가져다 쓰지 않는다.** 과거
에피소드 목차는 참고만 하고(어떤 비트가 있었는지 감 잡는 용도), 이번 소재가 실제로
필요로 하는 비트만 그 자리에서 새로 설계한다 — "콜드오픈→빅퀘스천→원리→패턴확장→
..." 같은 고정 골격에 내용을 끼워 맞추면, 이 소재엔 필요 없는 비트가 끼거나(불필요한
분량 늘리기), 이 소재만의 반전 포인트가 남들과 똑같은 자리에 눌려 들어가서 어색해진다.

`CLAUDE.md`의 "상위 0.1% 시청 지속 시간 스크립트 아키텍처"(Proof of Work Hook, 오픈
루프 체이닝, We 화법, 실패 시각화)와 도파민 3단계 공식(게으른 혀의 소리 지름길 → 패턴
확장 → 반전 꿀팁)은 **프레임 뼈대가 아니라 체크리스트**로 쓴다 — 이 소재 고유의
구조를 먼저 자유롭게 짠 뒤, 그 구조가 이 원칙들을 챙기고 있는지 검토하는 순서다.
반대로 먼저 원칙별 프레임 슬롯을 만들고 내용을 채우지 않는다.

프레임 수는 그 소재가 필요로 하는 만큼이다(11개가 기준이 아니다). 프레임별로 1줄
요약 + 그 프레임이 도파민 3단계 중 어디에 해당하는지 표시한다.

**첫 프레임(훅)의 첫 문장은 항상 Phase 4에서 확정한 썸네일 알약 문구/제목이 한 약속을
그 자리에서 지키는 문장으로 시작한다** — 예를 들어 알약 문구가 "다 '드'로 읽으셨죠?"
였다면, 훅 첫 문장이 바로 그 지적("네, 저도 한동안 다 드로만 읽었습니다" 식)을
받아서 시작해야 한다. 썸네일을 보고 클릭했는데 영상이 그 약속과 다른 이야기로
시작하면 바로 이탈하기 때문이다(이 채널의 "대화체 핑퐁 훅" 원칙과 결합해서 쓸 것 —
`brand-persona.md` 참고).

**예시는 일반적인 한국 사람이 실제로 겪었을 법한 경험에서 가져온다 — 훅뿐 아니라 이
단계와 Phase 6 전체에 적용한다**(`CLAUDE.md`/`AGENTS.md` "예시는 일반적인 한국 사람이
실제로 겪었을 법한 경험에서 가져온다" 절, 2026-10-03 확정 — EP22 작성 중 사용자가
직접 지적한 뒤 채널 공통 규칙으로 승격됨):

- 훅을 쓰기 전에 **"시청자가 지금 왜 이 영상을 클릭해서 보고 있는가"를 먼저 생각하고
  그 동기를 훅에 녹인다.** 특정 친구 한 명의 일화("친구가 이렇게 말했다")를 곧장
  쓰지 않는다 — 그보다 거의 모든 시청자가 겪었을 공통 경험(학교에서 단순화해 배운
  방식과 실제가 다르다는 배신감, 리스닝·회화에서 실제로 막혔던 경험)을 우선한다.
- 이 점검은 훅 한 군데로 끝내지 않는다. 본문 중간의 예시 단어·문장·상황도 전부
  "보통의 한국 성인이 실제로 마주칠 법한 장면"인지 매번 확인한다.

**단어가 흔하다고 예문이 현실적인 게 아니다 — 모든 예문을 하나의 구체적 실제 장면에
묶는다**(`CLAUDE.md`/`AGENTS.md` "모든 예문은 하나의 구체적 실제 장면에 묶는다" 절,
2026-10-03 확정 — 위 원칙을 지켰다고 생각했는데도 EP22에서 "현실적이지 않다"고 다시
지적받은 뒤 정확한 원인을 찾음):

- "He wanted some coffee", "That was a wicked plan"처럼 **단어를 보여주려고 지어낸
  문장**은, 단어 자체는 흔해도 "문법책 예문" 냄새가 나서 비현실적으로 느껴진다.
- 예문을 프레임마다 따로 지어내지 않는다. 그 대신 **Frame 1(훅)에서 이미 깔아둔
  하나의 구체적 장면(미드 대사, 친구에게 보내는 문자, 인스타그램 캡션, 면접, 여행
  등)을 스크립트 끝까지 끌고 가서**, 본문의 모든 단어·문장 예시를 그 장면 하나에
  묶는다 — 프레임마다 다른 맥락의 문장이 따로 노는 걸 피한다.
- 예문을 쓴 뒤 스스로 점검: "이 문장을 실제로 누가, 어떤 상황에서 말하거나 볼 법한가"를
  구체적으로 답할 수 있는가? 답이 "그냥 이 단어를 보여주려고"면 다시 쓴다.

## PHASE 6 — 전체 내레이션 스크립트

`brand-persona.md`의 톤(가식 없는 실전 학습 파트너, "당신 탓이 아니에요" 류 금지)을
따르고, `scripts/narration-lint.mjs`가 걸러내는 위험 패턴(TION/TURE/IC/SION 단독 표기,
하이픈 나열)을 미리 피해서 작성한다 — 나중에 TTS 생성 단계에서 다시 고치지 않도록.

**나레이션은 글이 아니라 말이다 — 쓰기 전에 소리 내어 말해본다는 생각으로 쓴다**
(`CLAUDE.md`/`AGENTS.md` "나레이션은 글이 아니라 말이다" 절, 2026-10-03 확정):

- **같은 문장 틀을 반복하지 않는다** — "~되는 겁니다", "~한 거죠", "~이었던 거죠"처럼
  명사형으로 끝맺는 틀을 문장마다 반복하면 "AI가 쓴 글"처럼 들린다. 문장을 맺는 틀
  자체를 매번 다르게 가져간다(3번 원칙 "문장의 음악적 리듬 변주"와 같은 결의 문제).
- 문장을 쓴 뒤 소리 내어(또는 속으로 실제 발화 속도로) 읽어보고 "진짜 이렇게 말하나?"
  스스로 반문한다. 뻣뻣하게 들리면 어미만 바꾸지 말고 문장 자체를 사람이 실제로
  뱉는 순서·호흡으로 다시 짠다.
- 한 문장에 "~해서, ~해서, ~했다"처럼 여러 동작을 접속사로 줄줄이 엮지 않는다 — 길면
  두 문장으로 쪼갠다. 접속절을 길게 나열하는 건 말이 아니라 글의 습관이다.

**초등학생도 보고 들으면 알아들을 수 있게 쓴다.** 타겟 시청자는 성인(3060)이지만,
설명 자체는 그 어떤 전문용어도 없이 풀어 써야 진짜 쉬운 것이다:

- "유성음/무성음/동화(assimilation)/음운 현상" 같은 언어학 용어를 나레이션에 그대로
  쓰지 않는다. 같은 원리를 몸으로 느낄 수 있는 쉬운 말로 바꾼다(예: "목에 손을 대고
  소리 내보면 부르르 떨리는 소리가 있고 안 떨리는 소리가 있어요" 처럼).
  용어는 화면 자막·치트시트 라벨에만 작게 보조로 쓸 수 있다.
- 비유는 이미 알고 있는 어른의 경험이 아니라, **누구나(어린아이도) 바로 몸으로 알 수
  있는 감각**(목의 떨림, 입 모양, 소리의 길이 등)을 쓴다 — `CLAUDE.md`의 "Show, Don't
  Tell" 원칙과 같은 방향이다.
- 문장은 한 번에 하나의 생각만 담고, 중간에 접속사로 여러 절을 묶지 않는다. 길어지면
  쉼표에서 끊어 짧은 문장 두 개로 나눈다.
- 다 쓴 뒤 스스로 점검: "이 설명에 아직 모르면 이해 못 할 단어가 남아있나?"를 문장
  하나하나 확인하고, 남아있으면 더 쉬운 말로 바꾼다.

완성되면 다음을 명시하고 멈춘다: **"스크립트까지 완료됐습니다. 이후 TTS 생성 →
whisper 타임스탬프 → HyperFrames 프레임 구현은 `VIDEO_WORKFLOW.md`/`hyperframes`
스킬로 이어서 진행합니다."**
