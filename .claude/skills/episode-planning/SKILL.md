# 영어 발음 채널 에피소드 기획 마스터 워크플로우

## 이 스킬의 범위

이 스킬은 **우리 채널 현실 점검 → 콘텐츠 유형 선택 → 경쟁 채널 스캔(틈새 찾기) → 소재 → 제목/썸네일 문구 → 스크립트(목차+본문) → 시각적 디자인(비주얼 스타일) 선택 → 영상 삽입용 일러스트/영상 프롬프트 제작 → 공개 후 성과 리뷰**까지 담당한다.
그 사이 기술적 제작 단계(TTS 생성, whisper 타임스탬프 추출, HyperFrames 프레임 구현,
렌더링, 업로드 패키지)는 기존 `knowledge/VIDEO_WORKFLOW.md`와 `hyperframes` 스킬로 그대로 이어간다.

**대시보드(`scripts/youtube-analytics-server.mjs`)의 자동 추천 로직(`idea-board.mjs`,
A/B 시뮬레이터의 가상 CTR 점수)을 대체하는 워크플로우다** — 그 도구들이 캐시해 둔
`data/youtube/*.json` 스냅샷 숫자를 그대로 인용하지 않는다. 매 단계마다 그 자리에서
라이브로 다시 조회하거나 웹 검색한 근거로 판단한다(이유: 2026-10-03에 외부에서 받은
분석이 캐시된/오래된 숫자를 최신 수치인 것처럼 섞어 써서 조회수를 2배, 롱폼 비중을
40배 틀리게 계산한 사고가 있었다 — `knowledge/logs/2026-10.md` 참고).

## 전체 진행 원칙

- **단계별 진행, 매 단계 끝에 멈추고 사용자 승인을 기다린다** — 사용자가 "계속"이라고
  하거나 수정 지시를 주기 전까지 다음 단계로 넘어가지 않는다.
- **조언은 데이터와 팩트로 직언한다**(CLAUDE.md 기존 원칙) — 장점만 말하지 않고, 리스크·
  반례·숫자가 안 맞는 부분은 그대로 지적한다.
- **이 채널의 기존 규칙과 충돌하지 않는다** — `brand-persona.md`, `thumbnail-strategy.md`,
  `production-rules.md`, `CLAUDE.md`의 스크립트/썸네일/렌더링 규칙은 이 스킬 안에서
  다시 설명하지 않고 그대로 따른다. 이 문서는 "기획 진행 순서"만 정의한다.
- **성과는 예측과 나란히 기록한다** — 소재를 고를 때 예상을 적어 두고, 공개 후 실제 결과와
  비교한다(Phase 11). 그래야 분석이 잘 됐는지, 어느 가정이 틀렸는지 알 수 있다.
- **같은 유형끼리만 비교한다** — 강의형 롱폼과 듣기형 쇼츠처럼 방식이나 형식이 다른 영상의
  성과를 한 줄로 섞지 않는다(`channel-strategy.md`의 "같은 역할과 유사한 길이끼리 비교" 원칙).

## PHASE 1 — 라이브 데이터 분석 (캐시 금지)

이번이 몇 번째 기획이든, **이 단계의 숫자는 이번 세션에서 직접 다시 받아온 값만 쓴다.**

1. **우리 채널 현재 상태(라이브)**: 분석 대시보드 서버(포트 3001)가 떠 있는지 확인하고,
   없으면 `npm run analytics`로 띄운다. 그다음
   - `POST http://localhost:3001/api/sync` 로 강제 새로고침을 먼저 호출한다(캐시된
     스냅샷이 아니라 지금 유튜브 API에서 새로 받아오게 하기 위함).
   - 그 직후 `GET http://localhost:3001/api/dashboard`, `/api/episodes/summary`로
     조회수·구독자·트래픽 소스·검색어·영상별 시청 지속률을 받는다.
   - `data/youtube/analytics-latest.json` 등 파일을 열어서 그 안의 숫자를 바로 인용하지
     않는다 — 반드시 `/api/sync` 직후 응답값을 근거로 쓴다. 범위(최근 N일/3개월/누적)를
     혼동하지 않도록 매번 응답의 `range` 필드를 확인하고 표에 명시한다.
2. **이미 다룬 소재 확인(라이브)**: `GET /api/catalog` 또는 `/api/episodes/summary`의
   실제 제목 목록, 또는 `videos/*/BRIEF.md`를 직접 스캔해서 지금까지 다룬 발음 규칙
   목록을 새로 뽑는다. `idea-board-history.json`은 참고만 하고 그 파일의 완결성을
   신뢰하지 않는다(과거에 등록 누락 버그가 있었음).
3. **시청자 페인포인트(웹 검색, 라이브)**: WebSearch를 실제 실행해서 한국 성인 영어
   학습자가 발음 관련해서 실제로 검색하고 질문하는 표현을 확인한다. 경쟁 채널 분석은
   여기서 하지 않고 Phase 3에서 한다. `audience-dna.json` 등 과거 스냅샷은 "그때 한 번
   모은 참고 자료"로만 취급하고, 이번 분석에서 재확인되지 않은 내용을 근거로 쓰지 않는다.
4. **산출물**: 아래 표로 "지금 채널의 진짜 현실"을 정리한다 — 숫자마다 어느 API 호출/
   어느 검색에서 나왔는지 출처를 반드시 붙인다.

   | 항목 | 값 | 출처 |
   |---|---|---|
   | 조회 범위 | (API 응답의 range) | /api/sync 응답 |
   | 롱폼 vs 쇼츠 조회수 비중 | | |
   | 최근 에피소드 시청 지속률 추이 | | |
   | 상위 트래픽 소스 3개 | | |
   | 검색 유입 비중 | | |
   | 이미 다룬 발음 규칙 목록 | | |

5. **대기 중인 리뷰 확인**: `videos/*/REVIEW.md`가 없고 `output/upload-packages/*/status.json`의
   `publishedAt`(또는 `scheduledFor`)이 7일 또는 28일 이상 지난 영상이 있는지 본다. 있으면
   Phase 2로 가기 전에 **Phase 11을 먼저 진행한다**고 알리고, 그 결과를 Phase 4의 근거로 쓴다.

끝나면 정확히 다음으로 마무리한다: **"다음은 콘텐츠 유형 선택입니다. 기본값(강의 방식, 형식은
소재별로 결정)으로 가려면 '계속'을 입력하세요. 다르게 정하려면 방식과 형식을 말씀해 주세요."**
멈춘다.

## PHASE 2 — 콘텐츠 유형 선택

두 가지를 정한다. 이 선택이 **스캔 대상 채널, 아웃라이어 기준, 나중의 성과 비교**를 모두 정한다.

### ① 방식 — 영상이 무엇을 하는지

- **강의**: 규칙을 설명하고 가르친다. 예: "왜 CAT은 캣인데 KING은 킹일까?" (우리 채널 기본)
- **듣기**: 계속 틀어놓고 들으면서 익히는 콘텐츠다(2026-10-04 사용자 정의). 긴 대화·팟캐스트, 또는 같은 문장 패턴을 반복해서 들려주는 드릴이 해당한다. **나레이션은 설명이 필요한 프레임과 드릴 시작 전 한 줄에만 넣는다**(2026-10-04 사용자 지침). 설명 프레임은 규칙, 예외, 정리다. 드릴 항목을 반복하는 동안에는 나레이션을 넣지 않는다. 초등학생에게 가르치듯 핵심만 말한다. 음성은 학습 대상 음성(원어민 드릴)이다. 이 영상이 어떤 학습용인지는 제목·썸네일·화면 카드로 알린다(2026-10-04 사용자 지침). 듣기형 채널 상위 영상은 전부 26~30분 롱폼이었다.
- **혼합**: 듣기 자료에 규칙 해설을 음성으로 붙인다. 나레이션 규칙을 그대로 적용한다.
- **혼합**: 듣기 자료에 규칙 해설을 붙인다. 검증된 채널이 아직 없어서 **가설로만** 쓴다.

### ② 형식 — 영상 길이와 역할

- **롱폼**: 신뢰 형성, 깊은 학습, 수익화 시청 시간 확보 (`knowledge/channel-strategy.md`).
- **쇼츠**: 신규 시청자 도달, 구독자 획득.
- **세트**: 쇼츠로 들어와서 관련 롱폼으로 연결한다(채널 전략의 "쇼츠 CTA는 롱폼으로 연결" 원칙).

### 기본 추천

- **방식은 강의가 기본이다.** 우리 채널이 강의형이고, 이번 스캔의 토픽 근거는 강의형 채널에서만 나오기 때문이다.
- **형식은 소재마다 역할로 고른다.** 도달이 목적이면 쇼츠, 깊이가 목적이면 롱폼이다. 우리 쇼츠 상위 5개 중 4개가 테스트형이라서, 도달형 소재는 테스트 쇼츠가 근거가 있다.

### 방식에 따라 스캔 대상이 정해진다

| 방식 | 스캔 대상 | 쓰는 근거 |
|---|---|---|
| 강의 | 강의형 채널 (`채널 방식 태그` 표 참고) | 토픽 + 형식 |
| 듣기 | 듣기형 채널 | **형식만.** 토픽 근거로 쓰지 않는다 |
| 혼합 | 두 그룹 모두 | 형식 + 토픽 (가설로 표시) |

### 형식별 주의

- **롱폼**: 현재 스캔 방식(채널별 상위 5개) 그대로 쓸 수 있다.
- **쇼츠**: 스캔은 롱폼과 쇼츠의 상위 5개를 따로 저장한다(`topOutliersByFormat`, 2026-10-04 변경). 쇼츠 판정은 **길이 60초 이하** 기준이다. 유튜브 Data API는 쇼츠 분류값을 주지 않으므로(분류값은 우리 채널 Analytics에서만 받을 수 있음) 이 근사치를 쓴다. 최근 50개 중 쇼츠가 0개인 채널은 "쇼츠 근거 없음"으로 적는다.
- **세트**: 같은 소재로 쇼츠와 롱폼을 함께 만든다. 스캔은 형식마다 한 번씩 본다.

### 기록

선택 결과(방식, 형식, 이유)를 스캔 문서 맨 위에 적고, `videos/<프로젝트>/REVIEW.md`의 "예측" 칸 위에도 적는다. Phase 11에서 같은 방식·형식끼리 비교하기 위해서다.

끝나면 **"이 유형으로 스캔을 진행하려면 '계속'을 입력하세요."**라고 안내하고 멈춘다.

## PHASE 3 — 경쟁 채널 스캔 (틈새 찾기)

**채널은 사용자가 준 주소만 쓴다.** 스킬이 임의로 채널을 골라 분석하지 않는다. 주소가
없으면 여기서 멈추고 달라고 요청한다. 같은 채널의 주소가 여러 개면(예: `/videos`가 붙은 것과 아닌 것)
한 번만 스캔한다.

### 채널 방식 태그 (제가 채널 성격으로 붙인다)

새 채널을 받으면 **다음 기준으로 제가 방식 태그를 붙이고**, 스캔 문서에 적는다. 사용자가 다르게
보면 바꾼다.

- **강의**: 제목에 규칙·수업·총정리·"N강"·"읽는 법" 같은 표현이 있고, 영상이 규칙을 설명한다.
- **듣기**: 제목에 Conversation·Podcast·Practice·Listening 같은 표현이 있고, 27분 이상 대화나 팟캐스트 형식이다.
- **혼합**: 듣기 자료에 해설이 붙은 것이 확인될 때만 쓴다.

| 채널 | 방식 태그 | 근거 |
|---|---|---|
| 우리 채널 (이해하면 쉬운 영어) | 강의 | 규칙 설명 시리즈 (쇼츠 테스트형은 혼합 가설의 출발점) |
| 9988영어 | 강의 | "읽는 법", "총정리", "이중모음 1 of 6" |
| 본즈 기초 영어 | 강의 | "기초 파닉스 수업", "까막눈 탈출" |
| 봄날영어학교 | 강의 | "수업", "덩어리철자 공부" |
| 어션영어 BasicEnglish | 강의 | "기초영어 1강: Be동사" 강의 번호 |
| learn english online | 듣기 | "English Conversation Practice", 27분 대화 |
| Speak English With Class | 듣기 | "English Podcast For Learning English" |

### 스캔 절차

1. **실행**: 채널마다 `node scripts/market-demand.mjs --channel="<주소>"`를 실행한다. 한글
   핸들은 URL 인코딩된 주소를 그대로 넣어도 된다. **매번 다시 돌린다**(캐시 금지). 채널당
   할당량 1이라 비용이 거의 없다.
2. **근거**: 이번 실행이 출력한 JSON만 쓴다. `data/youtube/market-demand.json`의 옛 값을
   열어서 섞지 않는다. 롱폼 근거는 `topOutliersByFormat.long`, 쇼츠 근거는
   `topOutliersByFormat.short`를 읽는다. `formatCounts`(롱·쇼츠·판정불가 개수)를 품질 체크에 쓴다.
3. **거르기**:
   - 선택한 방식에 맞는 채널만 본다. 듣기형 채널은 토픽 판정에서 빼고 형식 참고용으로만 쓴다.
   - 올린 지 7일 이상인 영상만 배율로 판단한다. 7일 미만은 "관찰 중"으로 따로 둔다 — 조회
     초반이라 배율이 크게 흔들린다.
   - 기준선(평소 하루 조회수 중앙값)이 10회 미만인 채널은 배율 대신 절대 조회수로 본다.
   - **구독자 수는 거르는 기준으로 쓰지 않는다.** 2026-10-04 분석에서 구독자가 비슷한 두
     채널(28.4만, 22.7만)의 기준선이 85배 가까이 차이 났다.
4. **아웃라이어 기준(작업 기준값)**: 기준선 대비 배율 **5배 이상**, 올린 지 **7일 이상**인
   영상. 이 값은 스캔을 2~3번 해본 뒤에 다시 조정한다.
5. **주제 묶기**: 제목에서 주제 클러스터를 만든다. **두 단계로 묶는다** — 넓은 주제(예:
   "영어 읽기: 철자를 소리로")와 좁은 주제(예: "긴 단어 덩어리", "이중모음", "기초 파닉스
   입문"). 한 영상은 좁은 클러스터 하나에만 넣는다.
6. **판정** (2026-10-04 실측으로 조정됨):
   - **니치 수요 있음**: 넓은 주제에서 아웃라이어를 낸 채널이 **2곳 이상**이고, 그중 **올린 지
     30일 이내** 아웃라이어가 있다.
   - **좁은 수요 있음**: 같은 조건을 좁은 클러스터에서 2곳 이상 만족한다.
   - **단일 채널 신호**: 좁은 클러스터에서 1곳만 만족한다. 다음 스캔이나 웹 검색으로 확인할 때까지
     소재 근거로 단독 사용하지 않는다.

   > **왜 두 단계로 나누는가**: 2026-10-04에 강의형 네 채널을 실측했을 때, 좁은 주제 세 개(이중모음·
   > 기초 파닉스 입문·긴 단어 덩어리)는 각각 **채널 1곳씩만** 최근 아웃라이어를 냈다. 2곳 기준을
   > 좁은 주제에 그대로 쓰면 아무것도 통과하지 않는다. 넓은 주제("영어 읽기")는 세 채널
   > 모두에서 나왔다.

7. **분석 품질 체크** (분석이 잘 됐는지 판단하는 근거다. 스캔 문서에 적는다):
   - 분석한 채널이 몇 곳인가(2곳 미만이면 판정 자체를 보류).
   - 채널별 상위 5개 중 7일 이상 된 영상의 비율(낮으면 배율 신뢰도가 낮다).
   - 기준선 10회 미만 채널이 있는가.
   - 한계 명시: 저장되는 것은 상위 5개뿐이라 조회 분포(얼마나 자주 뜨는지)는 알 수 없다.
   - 쇼츠를 선택했다면 "쇼츠 근거 부족" 여부.
8. **스캔 문서**: 날짜가 붙은 문서 `knowledge/competitor-channels-YYYY-MM-DD.md`를 만든다
   (같은 날 두 번째면 `-2`, 세 번째면 `-3`을 붙인다). 맨 위에 **선택한 방식·형식**, 채널 방식
   태그 표, 채널별 상위 5개, 클러스터 판정, 품질 체크, 한계를 적는다. 이 문서는 Phase 11에서
   "스캔 판정이 실제로 맞았는지" 확인할 때 쓴다. JSON(`market-demand.json`)은 스크립트가 자동
   저장하므로 따로 쓰지 않는다.
9. 끝나면 **"틈새 후보를 만들려면 '계속'을 입력하세요."**라고 안내하고 멈춘다.

## PHASE 4 — 소재 후보 (10개)

Phase 1에서 확인한 우리 채널 현실, Phase 2의 유형 선택, Phase 3의 클러스터 판정, 대기 중이던 리뷰(Phase 11)의
교훈, `data/youtube/success-patterns.json`(비어 있으면 "없음"이라고 적는다)만 근거로 쓴다.
**웹 검색 결과는 근거 칸을 따로 두고 "웹"이라고 표시한다** — 채널 근거와 섞지 않는다.
**듣기형 채널은 토픽 근거로 쓰지 않는다.**

| 후보 | 핵심 검색 키워드(실제 검색창에 칠 법한 구체적 문구) | 타겟 페인포인트 | 근거 클러스터(판정 등급) | 근거 영상(채널·제목 앞부분·배율·올린 지) | 우리 커버(BRIEF 대조) | 차별 각도 | 예측(우리 최근 조회 중앙값 대비 예상 범위와 이유) |
|---|---|---|---|---|---|---|---|

- 이미 다룬 규칙과 **70% 이상 겹치는 소재는 제외**한다(제외한 이유를 한 줄로 밝힌다).
  **30~70% 겹치는 소재는 제외하지 않고, 차별 각도를 반드시 적는다.**
- "일상에서 자주 쓰는 단어" 같은 막연한 라벨이 아니라, 실제 검색 가능한 구체적 키워드로
  적는다(`CLAUDE.md`의 "가짜 구체성 라벨 금지" 원칙 재사용).
- 경쟁 채널이 쓰는 제목 방식(검색어를 슬래시로 나열, 실생활 장면을 키워드로 쓰기)은 참고만
  하고, 문장을 베끼지 않는다.
- **예측 칸은 나중에 Phase 11에서 쓰므로 비워 두지 않는다.** 근거가 약하면 "근거 약함"이라고 적는다.
- **쇼츠 후보는 쇼츠 근거가 부족하다는 사실을 함께 적는다**(Phase 2 형식별 주의 참고).

번호로 선택하거나 직접 주제를 입력하도록 안내한다. 선택되면 `videos/<프로젝트>/REVIEW.md`를
만들고 "예측" 칸을 적는다. 이 파일이 이미 있으면 `Read`로 먼저 확인한 뒤 이어서 적는다
(CLAUDE.md "새 영상 프로젝트 안의 파일을 쓸 때도 먼저 확인" 원칙). 템플릿은 Phase 11 아래에 있다.

## PHASE 6 — 제목 & 썸네일 문구

`thumbnail-strategy.md`/`CLAUDE.md`의 기존 규칙(채널명 썸네일 표기 금지, 텍스트 5단어
이하, 클로즈업 시안 필수, 플랫 앵커 텍스트+골드 알약+무지 배경, A/B/C 시안 간 인물/구도
차별화)은 그대로 지킨다. **다만 A/B 시뮬레이터의 가상 CTR 점수(Gemini 채점)에 기대지
않고, 아래 체크리스트로 직접 판단한 근거를 말로 설명한다:**

- 검색 의도 키워드가 제목 앞부분에 구체적으로 들어가는가
  (❌ "아무도 몰랐던 원어민 소리의 비밀" / ⭕ "water 발음, 미국인은 왜 워러라고 할까")
- 호기심 갭이 있는가(정답을 주지 않고 궁금증만 유발하는가)
- 구체성이 있는가(일반 라벨이 아니라 실제 단어·장면·숫자)

3개 제목 시안 + 클로즈업 포함 썸네일 문구 3종을 만들고, 시안마다 "왜 이게 통할 것
같은지" 한 줄 근거(위 체크리스트 중 어느 항목을 충족하는지)를 붙인다.

사용자가 시안을 고르면(예: "A") **그 자리에서 바로** 썸네일 이미지 생성 프롬프트까지
작성해서 멈추지 않고 이어서 진행한다. **유튜브는 제목·썸네일을 3개까지 올려 실제
Test & Compare(A/B 테스트)를 할 수 있다** — 그래서 "사용자가 고른 시안"은 최종
업로드본일 뿐, 나머지 두 시안도 실제 A/B 테스트용으로 다 같이 쓰인다(EP17~21 전부
A/B/C 3종을 실제로 만들어 테스트에 올린 전례). **3개 시안 전부의 프롬프트를 만든다
— 고른 1개만 만들고 나머지를 미루지 않는다.**

- `knowledge/google-ai-studio-prompting.md`(Gemini 전용 프롬프트 기본 모델, CLAUDE.md
  기존 규칙)의 서술형 구조(Subject/Setting/Lighting/Shot/Text/Aspect Ratio)로 영어
  프롬프트를 쓴다.
- `thumbnail-strategy.md`의 기존 규칙을 그대로 지킨다: 채널명 배지 금지, 텍스트 5단어
  이하, A/B/C 시안 간 인물 표정·구도 차별화, 클로즈업 시안(화면 40~50%, 얼굴 중심)은
  **사용자가 고른 시안 기준으로 1개만 추가**(클로즈업은 모바일 전용 1개면 충분, 3개
  시안 전부에 클로즈업을 만들 필요는 없음 — 상세는 `thumbnail-strategy.md`), 플랫
  앵커 텍스트+골드 알약+무지 배경(소품/글로우/3D 금지 — NEGATIVE 프롬프트로 명시).
- 결과물: **일반 썸네일 A/B/C 3개 + 선택 시안의 클로즈업 1개, 총 4개 프롬프트.**
- 저장 위치: `videos/<프로젝트>/prompts/thumbnail-prompts.md` (파일이 없으면 새로
  만들고, 있으면 기존 파일을 `Read`로 먼저 확인한 뒤 이어서 추가한다 — 새 파일처럼
  가정하고 덮어쓰지 않는다. CLAUDE.md의 "새 영상 프로젝트 안의 파일을 쓸 때도 먼저
  확인" 원칙과 동일).
- 저장 직후 `BRIEF.md`의 "확정된 제목·썸네일" 섹션에 "이미지 프롬프트는
  `prompts/thumbnail-prompts.md`에 저장됨"이라고 한 줄 남긴다(다음에 또 "프롬프트
  어디 있어?"라고 묻지 않도록).
- 제목 체크리스트에 한 줄 더: 경쟁 채널의 검색어 나열 방식과 실생활 장면 키워드(간판,
  표지판 등)는 참고만 한다. 문장을 베끼지 않는다.
- **듣기 방식이면 학습 유형을 제목과 썸네일에 드러낸다**(2026-10-04 사용자 지침 — 나레이션이 없어서

  - ⚠️ **'드릴(drill)' 등 일반인이 직관적으로 모르는 전문·교육학 용어 사용 절대 금지 (제목·썸네일 칩·카피·나레이션·화면 전 영역, 2026-10-10 영구 확정)**:

    - ⭕ 친숙한 일상어 (3060 국내 성인 학습자가 0.1초 만에 체감하는 단어):

  - 제목 앞부분에 학습 유형 표기를 넣는다. 예: `[30분 듣기]`, `[반복 듣기]`.

  - 칩은 학습 유형 표기이지 채널명 배지가 아니다. 채널명 배지 금지 규칙과 구별한다.

## PHASE 7 — 스크립트 목차(아웃라인)

**듣기 방식이면** 목차는 나레이션 구간이 아니라 **드릴 구간과 화면 카드**로 짠다. 프레임마다
'무엇을 듣는지'(드릴 묶음, 항목당 반복 횟수와 쉼 길이)와 '화면에 무엇을 보여주는지'(카드 문구)를
적는다. 나레이션 구간은 훅(첫 프레임) 하나뿐이다.

**다른 에피소드의 프레임 이름·순서·개수를 템플릿으로 가져다 쓰지 않는다.** 과거
에피소드 목차는 참고만 하고(어떤 비트가 있었는지 감 잡는 용도), 이번 소재가 실제로
필요로 하는 비트만 그 자리에서 새로 설계한다 — "콜드오픈→빅퀘스천→원리→패턴확장→
..." 같은 고정 골격에 내용을 끼워 맞추면, 이 소재엔 필요 없는 비트가 끼거나(불필요한
분량 늘리기), 이 소재만의 반전 포인트가 남들과 똑같은 자리에 눌려 들어가서 어색해진다.

`CLAUDE.md`의 "상위 0.1% 시청 지속 시간 스크립트 아키텍처"(Proof of Work Hook, 오픈
루프 체이닝, We 화법, 실패 시각화)와 도파민 3단계 공식(게으른 혀의 소리 지름길 → 패턴
확장 → 반전 꿀팁)은 **프레임 뼈대가 아니라 체크리스트**로 쓴다 — 이 소재 고유의
구조를 먼저 자유롭게 짠 뒤, 그 구조가 이 원칙들을 챙기고 있는지 검토하는 순서다.
반대로 먼저 원칙별 프레임 슬롯을 만들고 내용을 채우지 않는다.

프레임 수는 그 소재가 필요로 하는 만큼이다(11개가 기준이 아니다). 프레임별로 1줄
요약 + 그 프레임이 도파민 3단계 중 어디에 해당하는지 표시한다.

**첫 프레임(훅)의 첫 문장은 항상 Phase 6에서 확정한 썸네일 알약 문구/제목이 한 약속을
그 자리에서 지키는 문장으로 시작한다** — 예를 들어 알약 문구가 "다 '드'로 읽으셨죠?"
였다면, 훅 첫 문장이 바로 그 지적("네, 저도 한동안 다 드로만 읽었습니다" 식)을
받아서 시작해야 한다. 썸네일을 보고 클릭했는데 영상이 그 약속과 다른 이야기로
시작하면 바로 이탈하기 때문이다(이 채널의 "대화체 핑퐁 훅" 원칙과 결합해서 쓸 것 —

### ⚠️ 듣기/드릴 방식 영상의 화면 시각화 절대 필수 규칙 (2026-10-08 확정)

1. **한글/영어 음절 분리 표기(가운뎃점 `·`) 100% 필수 표출 (EP24, EP25 누락 방지)**:

### Gemini 3.8 Flash TTS 직접 제작을 위한 스크립트 표준 규격 (2026-10-04 확정)

   - ⚠️ **원인**: 단어 뒤에 마침표(`.`)가 있거나 단어만 단독 제공되면 TTS 엔진이 즉각 급브레이크를 밟아 끝소리(파열음·모음 감쇄)를 칼같이 잘라버리고, 영상에서 뚝뚝 끊기는 스태카토 현상이 발생함.
   - **TTS 텍스트 규칙 (쉼표 배치)**: 단어 나열 시 마침표(`.`)를 엄격히 금지하고, 반드시 쉼표(`,`)나 줄임표(`...`)를 붙여 작성한다 (예: `sheep, ship, feet, fit,`). 쉼표가 있어야 AI가 뒤에 말이 이어지는 것으로 인식해 끝소리를 부드럽게 늘여주고 자연스러운 숨 여운(Decay)을 남긴다.
   - **배치 오디오 분할 규칙 (여운 패딩 + 페이드아웃)**: `split-batch-voice.mjs`로 긴 오디오를 단어별로 자를 때, 소리가 잦아드는 끝부분에 최소 **0.25초(250ms) 이상의 여운 패딩(Padding Tail)**을 포함하고, 끝 0.05초(50ms)에 부드러운 페이드아웃(`afade=t=out`) 필터를 적용하여 소리가 스르륵 감쇄되도록 처리한다.
   - **영상 오디오 믹싱 규칙 (배경 앰비언스)**: 영상 배경에 잔잔한 로파이/어쿠스틱 앰비언스 BGM을 은은하게 깔아(볼륨 8~10%), 단어 사이의 디지털 완전 무음(Dead Silence)을 메우고 편안한 공간감을 부여한다. 단어 간 반복 간격은 최소 1.5초~2.0초의 호흡을 유지한다.

아래 나레이션 규칙(말투, 문장 길이, TTS 린트, 초등학생 수준 설명)은 **모든 콘텐츠의 나레이션**(강의, 혼합, 듣기 훅 포함)에 적용한다. 다음 규칙도 모든 나레이션에 적용한다.

- **책 글투 금지**: 글을 읽는 것처럼 쓰지 않고, 유튜브에서 말하듯 쓴다. 일상에서 아무도 쓰지 않는 표현은 쓰지 않는다. 예: "입은 한 번만 움직여요", "~할 수 있습니다", "~하는 것입니다", "~라고 볼 수 있습니다", "~를 익혀 봅시다". 같은 뜻을 사람이 실제로 말하는 표현으로 바꾼다. 예: "그냥 한 번만 소리 내면 돼요".
- **초등학생이 한 번 듣고 알아듣는 말만 쓴다**: 한자어와 학술어를 피하고, 문장마다 생각 하나만 담는다.
- **소리 내어 읽고 판단한다**: 쓴 뒤 말하듯 읽어서 어색하면 말하는 문장으로 고친다.
- **사람이 녹음한 것처럼 쓴다**: 유튜브에서 진행자가 카메라 앞에서 말하는 리듬으로 쓴다. 짧게 말하고 끊는다. "근데", "그냥", "보면", "그러니까" 같은 말버릇을 자연스럽게 쓴다. 질문을 던지고 바로 답하는 흐름을 쓴다. 문장 길이가 전부 같으면 읽는 글처럼 들리므로 길이를 섞는다. 어미는 채널 톤 규칙(`brand-persona.md`)을 따른다.
- **TTS는 기본적으로 사용자가 직접 만든다**(2026-10-04 사용자 지침): 스크립트가 끝나면 음성을 바로 만들지 않는다. 사용자가 직접 만들지, 나에게 맡길지 매번 먼저 묻는다. 맡기면 유료 호출 전에 원화 견적을 알린다.
- **말투만 사람처럼, 경험은 지어내지 않는다**: "사람이 녹음한 것처럼"은 말투의 기준이다. 진행자가 직접 한 경험("제가 해 봤더니")을 만들어 넣지 않는다. 경험은 사용자가 확인해 준 것만 쓴다(CLAUDE.md 9번 원칙). 특히 **해외 카페 주문 등 국내 거주자가 겪지 않은 가짜 에피소드를 지어내는 행위를 영구 금지**하고, 철저히 국내 성인 학습자의 일상·미드·학창시절 경험에 기반한다(2026-10-10 확정).

`brand-persona.md`의 톤(가식 없는 실전 학습 파트너, "당신 탓이 아니에요" 류 금지)을
따르고, `scripts/narration-lint.mjs`가 걸러내는 위험 패턴(TION/TURE/IC/SION 단독 표기,
하이픈 나열)을 미리 피해서 작성한다 — 나중에 TTS 생성 단계에서 다시 고치지 않도록.

**나레이션은 글이 아니라 말이다 — 쓰기 전에 소리 내어 말해본다는 생각으로 쓴다**
(`CLAUDE.md`/`AGENTS.md` "나레이션은 글이 아니라 말이다" 절, 2026-10-03 확정):

- **같은 문장 틀을 반복하지 않는다** — "~되는 겁니다", "~한 거죠", "~이었던 거죠"처럼
  명사형으로 끝맺는 틀을 문장마다 반복하면 "AI가 쓴 글"처럼 들린다. 문장을 맺는 틀
  자체를 매번 다르게 가져간다(3번 원칙 "문장의 음악적 리듬 변주"와 같은 결의 문제).
- 문장을 쓴 뒤 소리 내어(또는 속으로 실제 발화 속도로) 읽어보고 "진짜 이렇게 말하나?"
  스스로 반문한다. 뻣뻣하게 들리면 어미만 바꾸지 말고 문장 자체를 사람이 실제로
  뱉는 순서·호흡으로 다시 짠다.
- 한 문장에 "~해서, ~해서, ~했다"처럼 여러 동작을 접속사로 줄줄이 엮지 않는다 — 길면
  두 문장으로 쪼갠다. 접속절을 길게 나열하는 건 말이 아니라 글의 습관이다.

- **초등학생도 보고 들으면 알아들을 수 있게 쓴다**: 타겟 시청자는 성인(3060)이지만,
  설명 자체는 그 어떤 전문용어도 없이 풀어 써야 진짜 쉬운 것이다:
  - "유성음/무성음/동화(assimilation)/음운 현상" 같은 언어학 용어를 나레이션에 그대로
    쓰지 않는다. 같은 원리를 몸으로 느낄 수 있는 쉬운 말로 바꾼다(예: "목에 손을 대고
    소리 내보면 부르르 떨리는 소리가 있고 안 떨리는 소리가 있어요" 처럼).
    용어는 화면 자막·치트시트 라벨에만 작게 보조로 쓸 수 있다.
  - 비유는 이미 알고 있는 어른의 경험이 아니라, **누구나(어린아이도) 바로 몸으로 알 수
    있는 감각**(목의 떨림, 입 모양, 소리의 길이 등)을 쓴다 — `CLAUDE.md`의 "Show, Don't
    Tell" 원칙과 같은 방향이다.
  - 문장은 한 번에 하나의 생각만 담고, 중간에 접속사로 여러 절을 묶지 않는다. 길어지면
    두 문장으로 나눈다.

- **작위적 번역투·과장된 위협·기괴한 신체 비유 엄격 금지 (2026-10-07 확정, 사용자 피드백 반영)**:
  - ❌ **절대 금지 표현**:
    - "속으신 겁니다", "완전히 속았습니다" 같은 가식적 위협·도발 어투 (일상 대화에서 아무도 안 씀).
    - "턱에 힘을 주느냐 빼느냐", "귀에 힘을 집중하시고" 같은 기괴하고 어색한 번역투 신체 비유.
    - "단숨에 꿰뚫어 드립니다", "충격적인 반전이 숨어 있습니다" 같은 과장된 약장수 톤.
  - ⭕ **반드시 쓸 실제 일상 구어 표현**:
    - 시청자의 속마음을 솔직하게 짚는 친구 화법: "Sheep이랑 Ship, 솔직히 둘 다 그냥 '쉽'으로 읽고 계셨죠?"
    - 누구나 0.1초 만에 따라 할 수 있는 손에 잡히는 일상 행동 비유:
      - "웃듯이 입꼬리를 양옆으로 싹 당기면서 내는 소리"
      - "그냥 멍때리듯이 입에 힘을 툭 빼고 내는 소리"
      - "편하게 귀로 한번 따라가 보세요"
    - 학창 시절 단순화해 배운 상식("장모음은 길게, 단모음은 짧게")과 실제 미드/영화에서 겪는 현실 고민("근데 미드를 보면 원어민들은 길게 끄는 것 같지도 않은데 구분해서 말하거든요")을 자연스럽게 핑퐁 대조.

  쉼표에서 끊어 짧은 문장 두 개로 나눈다.
- 다 쓴 뒤 스스로 점검: "이 설명에 아직 모르면 이해 못 할 단어가 남아있나?"를 문장
  하나하나 확인하고, 남아있으면 더 쉬운 말로 바꾼다.

완성되면 다음을 명시하고 멈춘다: **"스크립트 및 음성/타임라인 실측이 완료되었습니다. 다음은 화면에 적용할 시각적 디자인(비주얼 스타일)을 선택하는 단계(Phase 9)입니다. 계속 진행하려면 '계속'을 입력하세요."**

## PHASE 9 — 시각적 디자인(비주얼 스타일) 선택

스크립트 및 whisper 단어 타임스탬프 추출이 완료된 후, 이미지/비디오 프롬프트를 작성하기 전에 **화면 연출과 삽입 일러스트/영상에 적용할 전체 시각적 디자인 스타일을 사용자가 직접 선택하는 단계**다.

> **기준 참고 문서**: `public/ALI_AI_VAULT_VOX-STYLE_ANIMATION_MASTER_PROMPT.ko.md`
> (VOX 마스터 프롬프트의 PHASE 7 비주얼 스타일 선택 시스템을 채널 환경에 맞게 로컬라이즈)

### 1. 시각적 디자인 스타일 옵션

사용자에게 아래 5가지 옵션을 표와 함께 명확히 제시하고 선택을 요청한다:

1. **[옵션 1] 웜크림 네오브루탈리즘 (채널 시그니처 표준)**
   - **특징**: 차분한 웜크림(`#F4EFE6`) 배경 + 2.5px 블랙 볼드 외곽선 + 선명한 하드 섀도우 + 골드/레드 알약 캡슐 뱃지 + 현대적 플랫 타이포그래피.
   - **추천**: 가독성이 최우선인 규칙 설명, 파닉스 강의 및 30분 집중 반복 듣기 영상.
2. **[옵션 2] 컬러풀 VOX 에디토리얼 페이퍼 콜라주 (프리미엄 다큐 스타일)**
   - **특징**: 아카이브 종이, 흑백/컬러 하프톤 사진 컷아웃, 코발트 블루/틸/앰버/크림 시네마틱 컬러 블로킹, 마스킹 테이프, 브라스 핀, 부드러운 물리적 레이어 그림자.
   - **추천**: 일상 생활 스토리텔링, 실전 회화 맥락, 지적 호기심과 고급스러운 몰입감을 주는 에디토리얼 콘텐츠.
3. **[옵션 3] 모노크롬 에디토리얼 (다큐멘터리 수사물 스타일)**
   - **특징**: 오래된 신문지(Newsprint), 타자기 활자, 낡은 사전 스크랩, 거친 크림슨 레드 마커 원형 표시 및 머스타드 악센트, 다큐멘터리 증거물 느낌의 흑백 위주 아날로그 질감.
   - **추천**: 훅(Hook)에서의 오답 고발, 발음 비밀 파헤치기, 충격적 반전 규명.
4. **[옵션 4] 빈티지 스케치노트 & 다이어그램 (조음·물리법칙 특화)**
   - **특징**: 구강 단면도, 혀의 이동 경로, 소리 파형을 손그림 만화/스케치노트 다이어그램과 크래프트지 메모 패드로 친근하게 해설하는 스타일.
   - **추천**: 발음 조음 위치(혀, 입술, 목구멍) 및 소리 충돌/탈락 메커니즘 시각화.
5. **[옵션 5] 자동 선택 (Auto Select)**
   - 영상의 주제와 프레임 구성에 가장 어울리는 비주얼 스타일을 에이전트가 자동 판단하여 적용.

### 2. 선택 안내 및 멈춤 규칙

위 옵션을 제시한 후, 정확히 다음과 같이 질문하고 멈춘다:

> **"어떤 시각적 디자인 스타일로 진행할까요? 1~5번 중 번호를 선택하시거나, 원하시는 스타일 방향을 말씀해 주세요."**

**사용자가 번호나 스타일 방향을 선택하기 전까지 이후 프롬프트 작성을 절대 임의로 진행하지 않고 멈춘다.**

## PHASE 10 — 영상 삽입용 일러스트(이미지) & 영상(Image-to-Video) 프롬프트 시스템

사용자가 Phase 9에서 선택한 시각적 디자인 스타일에 맞추어, **영상 화면에 삽입할 핵심 일러스트(이미지)와 이를 움직이게 만드는 5초 스톱모션 영상(Image-to-Video) 프롬프트**를 체계적으로 작성하여 저장하는 단계다.

### ⚠️ 절대 원칙: HyperFrames 구현 가능 여부 필터링 (골든 룰, 2026-10-05 확정)

**"하이퍼프레임(HTML/CSS/GSAP/SVG)으로 구현이 어려운 영상 및 이미지만 제작한다. 하이퍼프레임으로 제작 가능한 것은 절대 이미지·영상 프롬프트로 만들지 않는다."**

AI 이미지·영상 생성은 비용과 리소스를 소모하며, 텍스트 오타(typo), 폰트 불일치, 해상도 저하 위험이 있다. 반면 HyperFrames는 완벽한 폰트 렌더링, 100% 타이포그래피 무결점, 정밀한 밀리초 단위 GSAP 애니메이션 제어가 가능하다. 따라서 다음 기준을 철저히 적용하여 대상을 선별한다:

❌ **프롬프트 생성 절대 금지 (HyperFrames 코드로 완벽히 구현 가능한 것)**:
- 텍스트 카드, 단어 블록, 테두리(border), 그림자(box-shadow), 라운드 코너
- 알약 캡슐 뱃지(pill badge), 넘버링 칩(`①, ②`), 태그, 버튼
- 단순 기하학적 다이어그램 (카드 좌우 비교, 2개 카드 결합, CSS 화살표/구분선)
- 텍스트 등장/퇴장 모션 (슬라이드, 팝, 페이드, 바운스 등 GSAP 애니메이션)
- 단어별/음절별 컬러 하이라이트 (whisper 연동 워드 트래킹)
- 한글/영어 음절 분리 표기 뱃지 (`[쉬 · 입]` vs `[쉽]`, `[푸 · 울]` vs `[풀]`, `wan · ted`) — 드릴 카드 렌더링 시 100% 필수 포함
- **타겟 학습 접미사/음소 분리 강조 필수 (2026-10-09 확정)**: 단어 전체를 통색으로 칠해 타겟 발음(-ed, -s 등)이 묻히는 것을 영구 금지. 어간은 뉴트럴 블랙(`#111111`) + 타겟 접미사에만 규칙별 고대비 강조 컬러(`-ed` [t]=코랄 레드, [d]=블루, [ɪd]=그린) 적용.
- **컴포지션 UI 텍스트 자동 줄바꿈 절대 방지 (`white-space: nowrap`, 2026-10-09 확정)**: 상단 알약(`eyebrow-pill`), 라벨, 메인 단어 카드(`word-text`)는 예기치 못한 줄바꿈으로 찌그러지지 않도록 `white-space: nowrap` 및 반응형 폰트 크기 계산 필수 적용.
- 실전 대화 문장 내 핵심 짝단어 컬러/밑줄 하이라이트 및 발화 펄스 바운스 애니메이션 — 100% 필수 포함
- 퀴즈 질문 박스, 정답 공개 박스, 체크리스트, 요약 그리드/표
- 텍스트가 메인인 모든 그래픽

⭕ **프롬프트 생성 필수 대상 (HyperFrames 코드로 구현이 불가능하거나 극히 비효율적인 것)**:
- **실제 사물/공간/인물 컷아웃**: 실제 테이크아웃 커피잔, 빈티지 카페 배경, 인물 표정 컷아웃, 사실적인 손 제스처 등
- **인체 해부학적 조음 기관**: 구강 단면도, 혀의 해부학적 근육 굴절, 성대 진동 등 복잡한 유기체 일러스트
- **물리적 아날로그 재질 오브젝트**: 손으로 거칠게 찢은 고해상도 종이 섬유 질감, 실제 금속 황동 핀/클립의 사실적 반사, 꼬인 실 등 복잡한 3D 텍스처
- **실제 연속 동작이 필요한 5초 비디오 클립**: 커피를 내려놓는 손동작, 입술이 닫혔다가 터지는 실제 입모양 슬로모션 등

### 1. 비주얼 비트 선정 (필터링 통과 대상만 엄선)
위 원칙에 따라, **HyperFrames로 구현할 수 없는 핵심 실물 일러스트 및 영상 클립만 1~3개 내외로 최소화**하여 선별한다. 단순 텍스트 카드를 화면에 보여주는 프레임은 프롬프트를 만들지 않고 HyperFrames 코딩 단계로 직행한다.

### 2. 선택된 스타일 블록 주입 및 이미지 프롬프트 작성
Phase 9에서 확정된 스타일에 따라 프롬프트의 재질/색상/조명 블록을 결정하고 고품질 영문 서술형 프롬프트를 작성한다:
- 화면비: `16:9` 와이드 가로형.
- 구도: 전체 화면의 60~75%를 차지하는 지배적인 히어로 피사체 1개 + 보조 요소 최대 3개, 넉넉한 네거티브 스페이스.
- 표준 엔딩 문구 필수 포함:
  > "Everything must look physically assembled from real paper pieces rather than digitally illustrated. No cartoon appearance, no glossy CGI, no 3D-rendered look, no gradients, no clutter, no watermark, no unnecessary logos, and no text other than the specifically requested label. Premium editorial documentary aesthetic, 16:9, ultra-detailed, 8K."
- 복사용 순수 텍스트 코드 블록(` ```text `) 분리 제공.

### 3. 이미지를 이용한 영상(Image-to-Video) 애니메이션 프롬프트
생성된 일러스트를 Runaway Gen-3, Luma Dream Machine, Kling, Pika, Google Flow 등에 입력하여 **5초 길이의 햅틱 스톱모션 클립**으로 변환하는 애니메이션 마스터 지시문이다:
- **카메라 (Camera)**: 5초 내내 **완전 고정(Locked static shot)**. 줌, 팬, 틸트, 회전, 흔들림, 트랜지션, 모핑, 객체 변형 금지.
- **0.0~3.5초 (Assembly Phase)**:
  - 빈 배경 위로 배경 종이 조각 안착 ➔ 메인 히어로 컷아웃이 부드러운 종이 마찰(drag)과 함께 슬라이드 안착 ➔ 보조 요소/라벨/테이프/스탬프가 촉각적(tactile)으로 착착 결합.
  - 리얼한 물리적 스톱모션 타이밍과 요소별 미세 레이어 그림자 안착.
  - 3.5초 시점에 원본 공급 이미지와 정확히 100% 동일하게 완성.
- **3.5~5.0초 (Living Poster Phase)**:
  - 완성된 콜라주 상태를 고정 유지(Living poster).
  - 종이 모서리의 미세한 펄럭임(lift), 하프톤 질감의 은은한 호흡 등 극도로 절제된 미세 생동감만 허용. 위치·크기·형태 변형 일체 금지.
- **오디오 (Audio)**: 나레이션/음악 없음. 종이 스치는 소리, 카드보드 탭, 테이프 압착, 스탬프 임팩트 등 섬세한 아날로그 앰비언스.

### 4. 산출물 및 저장 규칙
- **저장 위치**: `videos/<프로젝트>/prompts/visual-prompts.md`
- 파일이 이미 존재하면 `view_file`로 먼저 확인한 뒤 안전하게 작성/갱신한다.
- 작성이 완료되면 사용자에게 프롬프트 목록과 생성 가이드를 안내하고 승인을 받는다.

## 기술적 제작 및 업로드 패키지 빌드 시 영상 파일명 검색 키워드(SEO Tags) 명명 규칙 (2026-10-08 확정)

이 스킬로 기획한 영상이 컴포지션 구현 후 렌더링되어 업로드 패키지(`output/upload-packages/<project>/`)로 빌드될 때, **영상 파일명은 반드시 타겟 검색 키워드(SEO Tags)를 사용하여 저장**한다:

1. **배경**: 유튜브 알고리즘은 사용자가 업로드하는 원본 동영상 파일명(Raw Video Filename)도 초기 검색 색인(Indexing) 및 영상 주제 분류의 중요한 메타데이터 신호로 읽는다.
2. **원칙**:
   - `video.mp4` 같은 단순/추상적 파일명 저장 **엄격 금지**.
   - 해당 에피소드의 **타겟 핵심 검색 키워드(영문 SEO 키워드 또는 한글/영문 검색어 조합)**를 언더스코어(`_`) 또는 하이픈(`-`)으로 연결하여 명확하게 명명한다.
   - 예시:
     - EP23 (같은 자음 두 개 발음): `English_Pronunciation_Double_Consonants_Listening_Practice.mp4`
     - EP24 (장모음 [iː] vs 단모음 [ɪ]): `English_Pronunciation_Long_Short_I_Vowel_Pairs_Listening_Drill.mp4`
3. **업로드 패키지 연동**:
   - `output/upload-packages/<project>/` 내 최종 영상 파일을 해당 키워드 파일명으로 배치한다.
   - 업로드 대시보드(`index.html`), `upload-checklist.txt`에도 동일한 파일명을 연동하여, 사용자가 유튜브 스튜디오에 업로드할 때 검색 키워드가 포함된 파일 그대로 드래그 앤 드롭할 수 있도록 지원한다.

## PHASE 11 — 공개 후 성과 리뷰 & 다음 기획에 되먹임

이 스킬로 만든 영상이 공개된 뒤, **Phase 4에서 적어 둔 예측과 실제 결과를 나란히 비교해서
다음 기획에 반영하는 단계**다.

**언제**: 공개 후 **7일**과 **28일**이 지났고 `REVIEW.md`가 없는 영상. Phase 1 항목 5에서
자동으로 찾고, 사용자가 "리뷰해줘"라고 하면 바로 진행한다.

**비교 대상**: 같은 **방식과 형식**의 영상끼리만 비교한다. 예를 들어 강의형 롱폼 결과를
듣기형 쇼츠 결과와 한 줄로 섞지 않는다.

**절차**:
1. **라이브 조회**: `/api/sync`를 호출한 뒤 `/api/dashboard`에서 그 영상의 조회수, CTR, 시청
   지속률을 받는다. 응답에 필드가 없으면 "데이터 없음"이라고 적는다 — 값을 추정해서 채우지 않는다.
   출처(호출 시각)를 표에 적는다.
2. **예측과 비교**: `REVIEW.md`의 "예측" 칸(Phase 4에서 미리 적은 것)을 고치지 않고, 실제 값을
   바로 아래에 나란히 적는다.
3. **판정**: 맞았던 가정과 틀렸던 가정을 나눠 적는다. Phase 3 스캔의 **클러스터 판정이 실제로
   맞았는지도** 같이 적는다. 이것이 경쟁 채널 분석이 쓸모 있었는지 확인하는 근거다.
4. **A/B 결과**: 유튜브 Test & Compare에서 나온 제목·썸네일 승자를 적는다. 아직 없으면
   "없음"이라고 적는다.
5. **확정과 가설을 나눈다**:
   - **확정**: 2편 이상에서 같은 교훈이 확인된 것만 적는다.
   - **가설**: 1편에서만 나온 것은 가설로만 둔다.
6. **교훈 승격**: 확정된 교훈만 `data/youtube/success-patterns.json`에 올린다. 스키마는
   `{videoId, title, ctr, retentionRate, coreSuccessFactor, reusableHook, reusableAnalogy}`이고
   `videoId`가 키다(`youtube-analytics-server.mjs`의 `upsertSuccessPatterns`와 같은 형식).
   파일을 쓰기 전에 기존 entries를 읽고 보존한 채 추가한다. **쓰기 전에 사용자에게 확인받는다.**
   대시보드의 매트릭스 AI 진단(`/api/matrix/diagnose`)도 같은 파일에 쓰지만 유료 호출이라,
   비용을 원화로 먼저 알리고 승인받은 뒤에만 쓴다.
7. **다음 영상에 적용할 것**: 한 줄만 적는다. Phase 4의 다음 기획이 이 줄을 근거로 읽는다.

**표본에 대한 정직한 기준**: 우리 채널은 영상 수가 적어서 **0.1% 단위의 성장은 측정할 수
없다.** 이 단계의 현실적인 목표는 "매 편 예측을 적고, 틀린 가정을 하나씩 지워 나가는 것"이다.
리뷰 문서에 "측정으로 확인된 것"과 "아직 가설인 것"을 반드시 나눠 적는다. 0.1%의 성장을
약속하거나 그렇게 보이게 쓰지 않는다.


## 부록: 대시보드 자동 추천과 이 워크플로우의 차이

| | 대시보드 자동 추천(`idea-board.mjs`) | 이 워크플로우 |
|---|---|---|
| 데이터 소스 | `data/youtube/*.json` 캐시 스냅샷 | 매번 `/api/sync` 라이브 재조회 + 채널 스캔 실행 + 웹 검색 |
| 유형 | 구분 없음 | 방식(강의/듣기/혼합) × 형식(롱/쇼츠/세트)을 먼저 정함 |
| 제목/썸네일 평가 | Gemini AI 가상 CTR 점수 | 검색의도·호기심갭·구체성 체크리스트로 직접 판단 |
| 중복 소재 방지 | `idea-board-history.json` 조회 | 실제 카탈로그/프로젝트 폴더 라이브 스캔 |
| 성과 피드백 | 매트릭스 AI 진단(유료) | 예측과 실제를 `REVIEW.md`에 나란히 기록, 같은 유형끼리 비교, 2편 이상 확인된 것만 승격 |
| 진행 방식 | 대시보드 버튼 클릭, 결과 일괄 생성 | 단계별 진행, 매 단계 사용자 승인 대기 |

둘은 서로 대체재다 — 이 워크플로우를 쓸 때는 대시보드 자동 추천 결과를 섞어서 인용하지
않는다. 반대로 대시보드로 빠르게 훑어보고 싶을 땐 기존 방식을 그대로 쓴다.
